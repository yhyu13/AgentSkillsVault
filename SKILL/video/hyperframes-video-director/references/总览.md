# 总览：把视频制作变成可恢复的工程

[整理稿入口](README.md) · [能力路由](能力路由.md) · [制作方法](制作方法.md) · [验收规则](验收规则.md) · [来源与依赖](来源与依赖.md) · [项目卡模板](项目卡模板.md)

## 1. 能力模型

```text
用户目标 / 已有项目
        ↓
状态判断：回答、局部操作、恢复、还是新建？
        ↓
hyperframes：意图与路线契约 → BRIEF.md
        ↓
10 条领域路线中的一条（按交付物选择）
        ↓
按需要调用 10 项横向支撑能力
        ↓
检查 → 最终预览 → 用户批准 → 渲染 → 输出验证
        ↓
本地交付；发布另行授权
```

HyperFrames 用 HTML 承载 composition，用 `data-*` 声明时间、画布、媒体与结构。动画必须能按时间 seek；同一时间和相同输入应产生确定画面。不能把网页里的时钟、随机交互或实时网络当作视频时间轴。

## 2. 完整能力清单：21 项

以下目录均位于专家包的 `skills/` 下，且本次核对到实际 `SKILL.md`。
分类是本整理稿对职责的归纳，不改变原包注册信息。

### 2.1 主入口：1 项

| 技能 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| `hyperframes` | 识别项目状态；恢复 brief；新任务意图收集；路线选择；制作与审阅契约 | 不替代领域路线的具体制作，也不包办全部横向能力 |

`hyperframes-director` 是专家/代理入口，名称来自 `agents/hyperframes-director.md`，**不计作第 22 个技能**。本地没有 `skills/hyperframes-director/SKILL.md`。

### 2.2 领域路线：10 项

| 技能 | 典型输入 | 目标交付 | 关键边界 |
| --- | --- | --- | --- |
| `remotion-to-hyperframes` | 明确要迁移的 Remotion React 源码 | HyperFrames 工程与迁移比较证据 | 不是反向迁移，也不是任意源码转视频 |
| `slideshow` | 大纲、脚本或已有页面 | 可导航的 HyperFrames 演示稿 | 不是单文件线性 MP4 |
| `embedded-captions` | 本地现成单主体讲话视频 | 加字幕层的原片 | 适用门槛严格；不用于图文信息卡包装 |
| `talking-head-recut` | 本地讲话、访谈或播客视频 | 与转录同步的图文卡片包装 | 不按内容重剪原片；名称里的 recut 容易误导 |
| `music-to-video` | 音乐或从视频提取的音轨 | 节拍/能量驱动的视频 | 音乐必须驱动结构；不加网站采集与旁白路线 |
| `motion-graphics` | 短文字、数据、logo、图形或真实来源素材 | 短 MP4 或透明 overlay | 通常短于 10 秒、无旁白；当前 Windows 未在声明支持范围内 |
| `pr-to-video` | GitHub PR 引用、代码差异 | 变更说明、功能发布或修复讲解 | 必须读取真实 PR；不是网站宣传采集 |
| `product-launch-video` | 网站 URL、产品 brief 或脚本 | 产品宣传、展示或站点导览 | 展示真实站点依赖可信 capture 或用户素材 |
| `faceless-explainer` | 主题、文章、笔记、脚本 | 无真人出镜的解释视频 | 视觉可设计生成，但不能把示意数据冒充真实证据 |
| `general-video` | 自定义创作、素材编辑、长片等 | 通用 composition 与视频 | 也是 `flow: companion` 的执行入口；不是“任何需求随便做” |

### 2.3 横向支撑：10 项

| 技能 | 核心职责 | 最小产物或判断 |
| --- | --- | --- |
| `hyperframes-core` | composition、时间、源片段、轨道、子合成、变量、确定性 | 正确挂载、正确时间窗、正确媒体 seek |
| `hyperframes-animation` | 原子动效、复杂场景蓝图、转场、runtime adapter | 有理由的动作组合，统一可 seek 的动画 |
| `hyperframes-keyframes` | 主体姿态、镜头推进、缩放、遮罩、SVG、3D 与诊断 | 起始/过程/结束姿态有可核对画面 |
| `hyperframes-creative` | 品牌、排版、叙事、节奏、设计规范和分镜 | 可执行的设计与叙事决定，而非泛泛形容词 |
| `hyperframes-audio` | 已放入时间轴的轨道混音、FX、automation、carve、总线 | 声音之间不互相遮蔽，预览与导出使用一致处理 |
| `hyperframes-cli` | 初始化、检查、采样、预览、渲染、诊断、发布等 | 实际命令、退出码、日志和输出文件 |
| `hyperframes-registry` | 查找、安装、接线可复用 blocks/components | 来源明确、挂载正确、依赖齐全 |
| `hyperframes-studio` | 对话/修改边界、可编辑时间轴组织、安全区 | 轨道可读、内容可定位、布局便于继续编辑 |
| `media-use` | 素材解析、生成、转录、处理、复用与来源记录 | 冻结的本地文件、用途和 provenance |
| `figma` | 导入静态资产、品牌 token、组件、动作和分镜状态 | 本地化素材与可追踪绑定；不是渲染时访问 Figma |

**依赖方向：**横向能力支持路线，不能因“需要音乐”就改掉整个视频路线；Studio 管编辑界面与组织，core 管真正的时间与媒体行为。

## 3. 先按请求状态分流

按以下顺序取**第一条匹配项**；不要把新任务访谈套在已有项目上。

| 优先状态 | 正确处理 |
| --- | --- |
| 明确要求把既有 Remotion 迁移到 HyperFrames | 直接进入迁移路线，跳过新建 brief 访谈 |
| 对既有项目明确要求检查、诊断、预览、渲染、发布或批量导出 | 只做该操作；笼统的“继续”不视为渲染/发布授权，须明确确认 |
| 提问、暂停、只有想法而没有明确改动 | 先回答或给方案；用户要求不改时，不写工程 |
| 在既有项目里要求一部新片 | 同片的新版本/裁切版可增补记录；不同路线或画幅宜新建工程，避免覆盖 |
| 明确局部修改 | 先读目标文件，仅改该目标及必要关联，再重跑受影响验证 |
| 已有 `BRIEF.md` | 读 `workflow`、`flow` 与确认项；`companion` 转 `general-video` 执行，不重问 brief |
| 无 brief，但有 `hyperframes.json` 或 `STORYBOARD.md` | 从已有文件恢复；无法唯一识别路线时只问路由问题 |
| 全新制作 | 收集必要意图，确认路线和制作简报后进入路线 |

## 4. 四层项目事实

| 层 | 文件 | 回答的问题 |
| --- | --- | --- |
| 意图 | `BRIEF.md` | 给谁看、传达什么、什么格式、哪些决定已确认？ |
| 叙事/镜头 | `STORYBOARD.md`；部分路线使用专用 JSON | 每段具体展示什么、何时出现、为什么需要？ |
| 视觉 | `frame.md` → `design.md` → `DESIGN.md` | 用什么品牌、字体、配色、构图和约束？ |
| 实现 | `index.html`、`compositions/`、媒体与验证产物 | 真正做了什么、何时发生、输出是否符合要求？ |

- 设计规范按上面的优先级取第一个存在的文件；frontmatter 是可机读规范，正文是语义补充。
- 用户明确更改意图时更新 brief；只改变中间 checkpoint 行为时，更新 storyboard 的 `mode`，不要重写已确认的 `flow`/`storyboard`。
- 构建后应让计划与实际时长对齐，但不能偷偷改变已确认目标来回避实现问题。
- 原资料对个别布局、预览时机和模板写法有差异，见[来源与依赖](来源与依赖.md)，不要把摘要当作完整源码替代品。

## 5. 蒸馏后保留的工作原则

1. 目标与输入先于工具和风格。
2. 用户明确指定对象，就只改该对象；不要替用户扩大到整片。
3. 先复用真实素材与合适组件，再补缺；不要为“丰富”擅加旁白、音乐、字幕或转场。
4. 先解决叙事与画面关系，再增加动画复杂度。
5. 保留原始来源、确认项和每次重要改动，让下一次继续不依赖聊天记忆。
6. 用实际文件、日志与视觉证据描述完成度；“应该可以”不是完成状态。
