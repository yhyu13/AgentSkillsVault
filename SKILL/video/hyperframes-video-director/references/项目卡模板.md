# 项目卡模板：让制作可以接着做，而不是重新猜

[整理稿入口](README.md) · [总览](总览.md) · [能力路由](能力路由.md) · [制作方法](制作方法.md) · [验收规则](验收规则.md) · [来源与依赖](来源与依赖.md)

## 1. 使用方式与边界

- 将本模板的记录复制到**真实视频项目**，再按实际情况填写；不要求为此创建新的技能或运行脚本。
- 这是基于共享项目卡 v1 的中文扩展示例，字段是文档约定，不声称 CLI 会自动解析或执行它。
- `BRIEF.md` 是意图真源，分镜是镜头计划，composition 是实现；项目卡是状态/证据索引，不取代这些文件。
- 不把凭据、完整敏感日志、未授权的源素材或虚构输出写进卡中。
- 未知用 `null` 或空数组；尚未执行写 `pending` / `unverified`，不能把示例路径写成已存在的证据。
- 续做先重读当前工程与用户改动，再更新卡；旧卡不能覆盖新文件。

## 2. 可直接填写的 JSON 骨架

以下所有 ID、路径字段与证据字段均为空值示例，**不是已经创建的项目**。

```json
{
  "schema_version": "project-card-cn-1",
  "project_id": null,
  "project_root": null,
  "run_id": null,
  "workflow": null,
  "stage": "planned",
  "brief": {
    "path": "BRIEF.md",
    "exists": false,
    "sha256": null,
    "workflow": null,
    "flow": null,
    "storyboard": null,
    "mode": null,
    "audience": null,
    "goal": null,
    "message": null,
    "destination": null,
    "duration_seconds": null,
    "aspect_ratio": null,
    "fps": null,
    "language": "zh-CN",
    "angle": null,
    "voiceover_mode": null
  },
  "route_basis": {
    "requested_deliverable": null,
    "input_type": null,
    "why_this_route": null,
    "rejected_routes": []
  },
  "dependencies": [],
  "decisions": {
    "user-confirmed": [],
    "model-proposed": [],
    "unknown": []
  },
  "shots": [],
  "assets": [],
  "components": [],
  "steps": [],
  "outputs": [],
  "blockers": [],
  "next_action": null,
  "updated_at": null
}
```

`stage: planned` 只表示模板的初始记录位置，不证明已有可运行工程。非视频交付（仅分镜、演示稿、迁移工程）在 `route_basis.requested_deliverable` 明确标注，不为套状态链假装生成了 MP4。

## 3. 字段填写规则

| 字段 | 填什么 | 避免什么 |
| --- | --- | --- |
| `project_id` / `run_id` | 稳定的项目标识 / 本次制作或验证标识 | 把每轮对话当成新项目 |
| `project_root` | 实际绝对路径；相对文件路径都以此为基准 | 指向专家包目录或文档目录 |
| `brief` | 意图文件是否存在、哈希、已确认摘要 | 把模型建议混入确认值；把 `flow` 与 `mode` 混同 |
| `decisions` | 每项的内容、来源、时间、受影响文件/镜头 | 只有“已确认”却无法追溯确认内容 |
| `shots` | 镜头 id、起止、源文件、asset_ids、状态、证明时间 | 认为分镜 JSON 会自动执行 |
| `assets` | asset_id、真实路径、来源、权利、状态、证据 | 把待生成/占位素材写成 processed |
| `components` | 名字、block/component、来源版本、接线状态 | 编造 registry 名字或把下载等同接线完成 |
| `steps` | 实际阶段、命令、退出码、证据、未覆盖项 | 没有运行却填 exit_code 0 |
| `outputs` | 实际文件、哈希、probe、视觉/声音核验状态 | 把旧输出绑定到新工程版本 |
| `blockers` | 阻塞、影响、责任条件、补救方案 | 只写“环境问题”却不说明缺什么 |
| `next_action` | 一个可执行的下一步及前置授权 | “继续全部完成”但没有范围与条件 |

### 3.1 依赖记录片段

每个需要的依赖独立记录，不把“本地有脚本”写成“环境可用”：

```json
{
  "name": null,
  "kind": "tool-or-provider-or-model",
  "required_for": null,
  "required_version": null,
  "detected_version": null,
  "status": "unverified",
  "authorization": "unknown",
  "evidence": null,
  "fallback": null
}
```

建议状态：`unverified`、`ready`、`missing`、`blocked`。只有实际预检成功才能填 ready；`fallback` 不得把真实来源变成虚构素材。

### 3.2 镜头/卡片记录片段

```json
{
  "shot_id": null,
  "status": "outline",
  "src": null,
  "start": null,
  "end": null,
  "source_media_start": null,
  "asset_ids": [],
  "purpose": null,
  "on_screen_copy": null,
  "motion_intent": null,
  "proof_times": [],
  "confirmed": false,
  "evidence": []
}
```

- `status` 可用 `outline` / `built` / `animated`，只表示该镜头制作进度。
- `start/end` 是合成时间，`source_media_start` 是源内偏移，不能混用。
- talking-head 可另记 `card_id`、`zone`、`accentIndex`、`transcript_ref`；专项 JSON 保持原 schema。
- music-to-video 可另记 `audiomap_ref`、`span_sec`、`pacing`、`anchor_refs`，不要强塞成所有路线必填。

### 3.3 素材记录片段

```json
{
  "asset_id": null,
  "path": null,
  "type": null,
  "source": null,
  "source_version": null,
  "rights": "unknown",
  "status": "planned",
  "used_by": [],
  "sha256": null,
  "evidence": []
}
```

状态可区分 `planned`、`resolved`、`processed`、`adopted`、`blocked`。生成/处理结果必须指向实际本地文件；`rights` 记录授权范围或 unknown，不因“网上能下载”就写可商用。

### 3.4 执行步骤片段

```json
{
  "stage": null,
  "status": "pending",
  "command": null,
  "exit_code": null,
  "payload_ok": null,
  "evidence": [],
  "source_revision": null,
  "findings": [],
  "skipped_reason": null
}
```

`payload_ok` 用于必须检查 JSON 的命令，例如 `doctor --json`；其退出码 0 不足以判通过。`source_revision` 可记文件哈希或明确工程版本，用来识别验证是否已过期。

### 3.5 输出记录片段

```json
{
  "path": null,
  "format": null,
  "run_id": null,
  "sha256": null,
  "probe": null,
  "actual_duration_seconds": null,
  "width": null,
  "height": null,
  "fps": null,
  "audio_verified": false,
  "visual_proof_times": [],
  "visual_verified": false,
  "verification_evidence": [],
  "publish": {
    "status": "not_requested",
    "authorization": null,
    "receipt": null
  }
}
```

`probe` 保存实际 ffprobe 摘要，不写预期参数。未听音/未检查视频就保留 false。发布状态与本地文件验证分开，`not_requested` 不代表失败。

### 3.6 阻塞与下一步片段

```json
{
  "blocker_id": null,
  "reason": null,
  "affected_shots": [],
  "evidence": null,
  "required_input_or_authorization": null,
  "safe_alternatives": []
}
```

`next_action` 写“要做什么、依据哪份文件、需要什么前置条件、怎样判断完成”。例如“补齐真实产品截图后重新采集/导入并核对页面一致性”，不要写“降级随便做一版”。

## 4. 简短的人类可读状态栏

每次交接可附以下内容，详细证据仍在项目卡：

```text
状态：planned / checked / previewed / rendered / verified（仅选有证据的一项）
目标：给谁看，传达什么，交付哪种格式。
已确认：输入、画幅、时长、声音、路线与已批准分镜。
已完成：实际落地的文件/镜头。
依据：brief、分镜、设计规范与本次证据路径。
发现：已修复问题与仍待检查的问题。
阻塞：缺失依赖、授权或素材；影响范围。
下一步：一个明确动作，以及启动所需条件。
```

## 5. 续做核对清单

- [ ] 重读当前请求与工程，不以聊天摘要代替文件。
- [ ] 核对 brief 与项目卡路径/哈希；确认用户是否改过文件。
- [ ] 读取最近失败和未验证项，不重跑已成功且未受影响的昂贵步骤。
- [ ] 只更新受改动影响的镜头、素材、步骤与输出状态。
- [ ] 检查输出是否对应当前源文件；不对应则重新验证或导出，旧证据不能继承。
- [ ] 保留用户确认项；模型新建议另列，不覆盖已锁定布局或文案。
- [ ] 下一步涉及外部上传、下载费用、登录、覆盖或发布时，先确认授权。
- [ ] 交付时明确本地完成范围；未渲染/未听音/未发布如实说明。
