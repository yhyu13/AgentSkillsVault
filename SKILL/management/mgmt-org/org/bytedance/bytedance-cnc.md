# 字节跳动 · Context, not Control

> 用信息替代指令，用透明替代管控——让每个决策者拥有完整的上下文，而非等待上级的命令。

## 核心理念

Context, not Control 解决的核心问题是：**组织规模扩大后，如何避免决策瓶颈？**

传统管理依赖Control（控制）：审批、指令、层级汇报。层级越多，信息衰减越严重，决策越慢。字节跳动的解法是反其道而行——不增加控制节点，而是把决策所需的上下文（Context）充分同步给每个人，让离现场最近的人自主决策。

核心命题：管理者的职责不是告诉员工"怎么做"，而是把"是什么"和"为什么"同步给所有人。

## 框架结构

```
Context, not Control
│
├── 三层Context（供给端：给什么信息）
│   ├── 战略层：方向 + 为什么走这个方向
│   ├── 业务层：数据 + 竞品动态 + 用户反馈
│   └── 意义层：价值观 + 使命 + 长期愿景
│
├── 四层Control替代（消除端：去掉什么控制）
│   ├── 信息透明 → 替代 → 信息控制
│   ├── OKR对齐 → 替代 → 指令下达
│   ├── 飞书协作 → 替代 → 审批流程
│   └── 数据驱动 → 替代 → 经验判断
│
└── 前提条件
    └── 高人才密度（无此条件，Context退化为放任）
```

## 关键模块

### 模块1：三层Context供给

- 定义：管理者需要持续向组织注入的三类信息，构成分布式决策的认知基础
- 输入：战略决策、业务数据、文化价值观
- 输出：全员共享的决策上下文
- 关键动作：
  - 战略层：每次重大决策后公开"为什么这样选"，而非只传达结论
  - 业务层：数据看板全员可见，竞品分析定期推送，用户原声不经过滤
  - 意义层：CEO在双月会上阐述价值观与长期方向，回答"我们为什么存在"
- 常见误区：只给战略层Context不给业务层，导致员工知道方向但无法判断具体行动；把Context等同于培训，实际上Context是持续的信息同步而非一次性灌输

### 模块2：四层Control替代

- 定义：用四种机制逐一替代传统管控手段，实现"不控而治"
- 输入：传统管控痛点（审批慢、信息断层、经验主义）
- 输出：分布式决策能力
- 关键动作：
  - 信息透明替代信息控制：OKR全员可见，飞书文档默认公开，鼓励群聊不单聊
  - OKR对齐替代指令下达：目标自下而上提议、自上而下对齐，而非上级分解任务
  - 飞书协作替代审批流程：跨部门协作通过飞书群组即时推进，减少层层审批
  - 数据驱动替代经验判断：A/B测试结果自动标记，正向实验自动进入发布队列
- 常见误区：以为去掉审批就是去掉流程，实际上是用更轻量的协作机制替代；以为信息透明等于信息过载，实际上需要结构化呈现（OKR、看板、双月会）

### 模块3：前提条件——高人才密度

- 定义：Context, not Control 能否生效，取决于接收Context的人是否具备自主决策的能力
- 输入：招聘标准、人才密度指标
- 输出：组织是否具备分布式决策的前提
- 关键动作：
  - 招聘时重底层素质（理性、逻辑、企图心）而非履历title
  - 保持高标准招聘+高强度淘汰，确保人才密度>业务复杂度
  - 年轻人快速承担核心职责（60%校招生2年内晋升）
- 常见误区：在人才密度不足时强行推行CnC，结果变成放任自流；以为CnC等于不要管理，实际上CnC是更高要求的管理——管理者要从"下指令"转为"造上下文"

## 决策启发式

| 场景 | 判断规则 | 来源 |
|------|---------|------|
| 团队反复请示同一类问题 | 说明Context供给不足，应补充该类信息的透明度 | CnC核心逻辑 |
| 决策质量参差不齐 | 检查人才密度是否匹配，若不足则先提升人才密度再放权 | 前提条件 |
| 跨部门协作卡在审批 | 用飞书群组+OKR对齐替代审批链路 | 四层Control替代 |
| 管理者成为瓶颈 | 该管理者在用Control而非Context，需转为信息同步模式 | CnC定义 |
| 信息已透明但决策仍慢 | 检查是否缺少业务层Context（数据/竞品/用户反馈） | 三层Context |
| 新业务方向不明 | 补充战略层Context：明确方向+阐述为什么 | 三层Context |

## 适用场景

### 最适合

- 知识密集型组织，决策需要大量专业判断
- 快速变化的市场环境， centralized decision-making 来不及响应
- 人才密度高的团队，成员具备自主决策能力
- 信息可结构化、可数字化的业务（互联网、软件、数据驱动型）

### 不适合

- 人才密度低、成员缺乏自主决策能力的团队（CnC退化为放任）
- 强合规行业（金融、医疗），某些决策必须走审批流程
- 危机时刻需要快速集中决策的场景（CnC在日常有效，紧急时需切换为Command模式）
- 信息难以结构化的传统制造业一线

## 实施检查清单

- [ ] OKR是否全员可见（包括CEO的OKR及完成进度）
- [ ] 飞书文档是否默认公开而非默认私密
- [ ] 跨部门协作是否通过群组推进而非层层审批
- [ ] 管理者是否定期同步"为什么"而非只传达"做什么"
- [ ] 数据看板是否全员可访问
- [ ] 人才密度是否达到自主决策的门槛
- [ ] 是否有机制让一线员工直接获取用户反馈
- [ ] 双月会/全员会是否包含战略层Context的同步

## 诚实边界

1. **前提条件严苛**：CnC不是万能药，没有高人才密度就是放任。很多公司学字节学不像，根本原因是人才密度不够。
2. **信息过载风险**：全员透明不等于全员消化。信息需要结构化呈现，否则噪声淹没信号。
3. **危机场景失灵**：CnC在日常运营中高效，但紧急危机时需要集中指挥，字节内部也有"战时机制"的切换。
4. **文化依赖**：CnC需要"坦诚清晰"的文化土壤，如果组织文化是"报喜不报忧"，信息透明就变成信息表演。
5. **公开资料局限**：以上分析全部基于公开信息，字节内部CnC的实际落地细节（如哪些场景仍保留Control）未公开。
