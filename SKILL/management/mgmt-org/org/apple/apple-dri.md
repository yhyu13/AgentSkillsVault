# Apple · DRI责任制

> 每个关键决策和交付物指定一个直接责任人——集体负责等于无人负责，DRI让问责归位到个人。

## 核心理念

DRI责任制解决的核心问题是：**为什么大组织里事情搞砸了却找不到该负责的人？**

答案指向一个结构性陷阱：集体负责。当一群人对某个结果"共同负责"时，责任被稀释到每个人头上只剩几分之一，最终谁都不觉得自己是那个该站出来的人。项目延期是"团队的问题"，决策失误是"大家讨论的结果"，交付质量差是"流程的问题"——没有人被点名，没有人被追责，也没有人真正在意。

Apple的解法极其直接：给每个关键决策和交付物指定一个DRI（Directly Responsible Individual，直接责任人）。DRI不是团队领导，不是项目经理，而是那个对结果负最终责任的人。事情成了，DRI拿功劳；事情砸了，DRI扛后果。没有灰色地带，没有"大家都有责任"的逃逸通道。

核心命题：**问责的原子单位是个人，不是团队——集体负责是组织最大的问责漏洞。**

## 关键模块

### 模块1：DRI定义——直接责任人

- 定义：DRI是某个关键决策或交付物的直接责任人，对该结果负最终责任
- 输入：关键事项清单
- 输出：每个事项对应一个命名的DRI
- 关键动作：
  - DRI的全称是Directly Responsible Individual——"直接"意味着没有中间层，"负责"意味着结果好坏追溯到个人，"个人"意味着问责的原子单位是一个人
  - DRI的指定在事项立项时就完成——不是事后追责时才找谁该负责，而是事前就明确谁该负责
  - 一个事项一个DRI——多个DRI等于没有DRI，这是DRI制度最硬的规则
  - DRI的名字与事项绑定——在Apple内部，每个会议议程项、每个项目里程碑、每个交付物旁边都标注DRI姓名
- 常见误区：以为DRI就是项目经理——项目经理管过程，DRI管结果；以为DRI必须亲自做所有事——DRI负责确保事情做成，不等于DRI自己动手做每件事

### 模块2：DRI≠团队领导——最适合原则

- 定义：DRI的指定依据是"谁最适合对结果负责"，而非"谁是团队领导"
- 输入：事项的专业领域 + 团队成员的能力和知识
- 输出：最合适的DRI人选
- 关键动作：
  - 团队领导可能是DRI，也可能不是——如果团队领导不是最了解该事项的人，就不应该是DRI
  - 最适合原则意味着DRI可能是一线专家——一个对产品细节了如指掌的设计师可以是产品决策的DRI，即使团队里有更高级别的管理者
  - DRI身份随事项变化——同一个人在不同事项上可能是DRI，也可能不是；不同事项的DRI可以是不同的人
  - 最适合原则的判断标准：谁对结果最有影响力 + 谁最了解相关情况 + 谁最能推动事情完成
- 常见误区：默认让管理者当DRI——管理者不一定是最适合负责的人；以为DRI身份固定——DRI是事项级别的指定，不是人级别的头衔

### 模块3：避免集体负责——问责归位

- 定义：DRI制度的核心目标是消灭"集体负责=无人负责"的问责漏洞
- 输入：组织中的责任模糊地带
- 输出：每个模糊地带都被一个DRI覆盖
- 关键动作：
  - "集体负责"是DRI要消灭的反模式——当一群人对某个结果"共同负责"时，责任被稀释，每个人都可以说"不是我的问题"
  - Apple的做法：在任何可能产生责任模糊的场合，第一件事是问"谁是DRI？"——如果没有人能回答，说明DRI指定缺失，必须立即补上
  - 问责归位不是甩锅——DRI不是替罪羊，而是事前明确、事中推动、事后承担的完整责任链
  - 集体负责的典型症状：会议讨论了但没有结论、项目延期但没人觉得是自己的问题、决策反复推翻但没人对错误决策负责
- 常见误区：以为DRI制度就是找替罪羊——DRI是事前指定而非事后追责；以为DRI意味着其他人不用参与——DRI负责最终结果，但执行过程可以是团队协作

### 模块4：DRI的决策权——一人拍板

- 定义：DRI拥有所负责事项的最终决定权，不需要集体投票或层层审批
- 输入：需要决策的议题
- 输出：DRI做出的最终决定
- 关键动作：
  - DRI的决策权是DRI制度的必然延伸——如果DRI对结果负责但不拥有决策权，问责和权力就脱节了
  - DRI可以听取意见，但最终决定权在DRI一人——不需要一致同意，不需要投票表决
  - 决策速度是DRI制度的副产品——一人拍板比委员会讨论快得多
  - DRI决策不是独裁——DRI的权力限定在所负责的事项范围内，且DRI对结果负责的约束本身就是对权力的制衡
- 常见误区：以为DRI可以随意拍板——DRI的决策权与问责绑定，拍错板要承担后果；以为DRI不需要听取意见——DRI拥有最终决定权，但明智的DRI会充分收集信息再做决定

### 模块5：DRI在Apple的实践——无处不在

- 定义：DRI制度在Apple不是某个部门的管理工具，而是全公司的基础管理语法
- 输入：Apple的组织设计和文化
- 输出：DRI渗透到每个工作场景
- 关键动作：
  - 会议中的DRI：Apple的会议议程每项都标注DRI——讨论某功能时，DRI是那个功能的产品负责人；讨论某技术方案时，DRI是那个方案的架构负责人
  - 项目中的DRI：每个项目里程碑有DRI——不是整个项目一个DRI，而是每个关键交付物各有DRI
  - 危机中的DRI：出问题时第一反应是"谁是DRI"——不是开会讨论"谁的责任"，而是直接找到DRI
  - Apple的组织设计与DRI制度深度耦合——职能型组织（按专业而非按产品线分组）使得DRI可以在专业领域内做出高质量决策
- 常见误区：以为DRI只在项目场景使用——DRI适用于任何需要明确问责的场景，包括日常运营、危机处理、跨部门协作

## 决策启发式

| 场景 | 判断规则 | 来源 |
|------|---------|------|
| 是否需要指定DRI | 如果事项的结果需要有人负责→必须指定DRI；如果事项无关紧要→可以不指定 | DRI定义 |
| 谁应该是DRI | 如果某人最适合对结果负责（影响力+了解程度+推动力）→指定为DRI；如果默认让管理者当DRI→重新评估 | 最适合原则 |
| 多人争当DRI | 如果多人都认为自己最适合→由上级指定一人，但必须给出理由；如果无人愿意当DRI→说明事项定义不清或风险过高 | DRI指定机制 |
| DRI是否可以更换 | 如果DRI明显不胜任→可以更换，但更换本身需要另一个DRI来决定；如果DRI只是暂时困难→支持而非更换 | 问责归位 |
| 是否需要集体讨论 | 如果决策需要多维度信息→DRI应听取意见再拍板；如果信息已经充分→DRI直接决定 | DRI决策权 |
| 结果不理想时 | 如果DRI尽责但结果不佳→复盘学习而非追责；如果DRI失职导致结果差→DRI承担后果 | 问责机制 |
| 跨部门事项的DRI | 如果事项跨越多个部门→指定一个DRI而非多个；如果必须多部门协作→DRI负责协调，其他部门配合 | 避免集体负责 |

## 与其他方法论的关系

| 关联方法论 | 关系 | 接口 |
|-----------|------|------|
| Netflix知情船长 | 正交互补 | 知情船长解决"谁做决策"（决策权归属），DRI解决"谁对结果负责"（问责归属）——一个管决策，一个管问责，两者可以分离也可以合一 |
| Amazon单线程领导 | 并行类比 | Amazon强调100%专职+独立团队，Apple强调一人最终负责——Amazon用组织独立性保障执行，Apple用个人问责保障结果 |
| 华为ATI/ATB/ATC | 对立参照 | 华为每个关键决策点有正式评审（ATI/ATB/ATC），Apple用DRI简化问责——华为靠流程和集体把关，Apple靠个人判断和事后问责 |
| Google委员会制 | 对立参照 | Google用委员会集体决策，Apple用DRI个人问责——Google追求决策的全面性，Apple追求问责的清晰性 |
| Amazon Disagree and Commit | 文化协同 | DaC是DRI决策的加速器——DRI拍板后团队执行，不因内部分歧拖延 |
| 字节OKR | 并行类比 | 字节用OKR对齐方向+分布式执行，Apple用DRI明确问责+个人决策——字节靠目标体系对齐，Apple靠个人问责驱动 |

## 适用场景

### 最适合

- 问责模糊的大组织——组织越大，责任稀释越严重，DRI的收益越大
- 需要快速决策的场景——一人拍板比委员会讨论快
- 跨部门协作项目——多部门参与时最容易出现"集体负责"陷阱
- 结果导向型工作——交付物明确、结果可衡量的事项
- 危机处理——出问题时需要立即找到责任人并推动解决

### 不适合

- 安全敏感行业——航空/医疗/核能，错误代价不可逆，需要多重审批和集体决策兜底
- 需要广泛共识的战略决策——DRI适合执行问责，不适合需要多方认同的决策制定
- 合规要求极高的行业——金融/制药，监管要求保留集体决策和审批流程
- 创意探索阶段——方向未定时，个人决策可能过早锁定路径
- 文化不支持个人问责的组织——如果"出了问题大家一起扛"是默认文化，DRI制度会遭遇强烈抵触

## 实施检查清单

- [ ] 每个关键决策和交付物是否指定了唯一的DRI
- [ ] DRI是否是最适合对结果负责的人而非默认的管理者
- [ ] DRI是否拥有所负责事项的最终决定权
- [ ] 是否存在"集体负责"的责任模糊地带——如果有，立即指定DRI
- [ ] 会议议程是否每项都标注了DRI
- [ ] 项目里程碑是否每个都有DRI
- [ ] 出问题时第一反应是否是"谁是DRI"
- [ ] DRI的问责是否与权力对等——有权无责或有权无责都是问题
- [ ] 组织文化是否支持个人问责——如果不支持，需要先做文化铺垫
- [ ] 是否有DRI不胜任时的更换机制

## 诚实边界

1. **DRI与团队领导的混淆风险**：在实践中，"谁最适合对结果负责"的判断并不总是清晰的。当团队领导和专业能力足以覆盖事项时，DRI和团队领导自然合一；但当两者分离时，团队领导可能不愿意让渡决策权给DRI，造成权力冲突。

2. **个人问责的心理压力**：DRI制度将问责集中到个人，这意味着DRI承担了远超普通成员的心理压力。在结果不理想时，DRI可能成为众矢之的，即使失败的原因不完全在DRI的控制范围内。这种压力可能导致有能力的人不愿意当DRI。

3. **与Netflix知情船长的互补性被简化**：知情船长和DRI确实侧重不同——船长管决策，DRI管问责。但在实际组织中，决策权和问责权往往纠缠在一起。如果DRI不是决策者，DRI对结果负责却无法控制决策，这是权责不对等的经典困境。

4. **与Amazon单线程领导的差异需要语境**：Amazon的单线程领导强调100%专职和独立团队，Apple的DRI强调一人最终负责但不要求专职。这意味着DRI可能同时是多个事项的DRI，注意力分散的风险高于单线程领导。两种制度解决的核心问题不同：Amazon解决"没人全职投入"，Apple解决"没人最终负责"。

5. **与华为ATI/ATB/ATC的对比简化了双方**：华为的正式评审不是纯粹的"集体决策"，评审中有明确的决策权归属（IPMT主任拍板）；Apple的DRI也不是纯粹的"个人决策"，DRI在决策前通常会听取多方意见。两者的差异是流程化程度和集体参与程度，不是二元对立。

6. **与Google委员会制的对比忽略了Google的演变**：Google并非所有决策都用委员会——在产品层面，Google也有明确的DRI角色（如Product Area Lead）。公开资料对Apple DRI和Google委员会制的对比往往停留在文化层面，忽略了两者在实际执行中的趋同。

7. **知识盲区**：本文件基于公开资料整理，不包含Apple内部DRI的具体指定流程、DRI不胜任时的更换机制、DRI与职能型组织的具体耦合方式等内部实践细节。
