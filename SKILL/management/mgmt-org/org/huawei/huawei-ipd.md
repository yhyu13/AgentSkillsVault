# 华为 · IPD 集成产品开发

> 把产品开发当投资管理，用结构化流程和跨部门团队对抗研发的低效与失控。

## 核心理念

IPD解决的核心问题是：研发不再是技术部门的独角戏，而是一项需要投资决策、市场验证、跨职能协作的系统工程。它将产品开发从"技术驱动、部门割裂、事后评审"转变为"市场驱动、团队协同、过程受控"。

六根思想支柱：

1. **市场驱动**——产品立项的起点不是技术灵感，而是客户需求和商业价值
2. **投资决策**——把产品开发视为投资组合管理，每个阶段都有"止损"机制
3. **跨部门协同**——打破部门墙，研发/营销/供应链/财务全程参与
4. **重量级团队**——PDT不是协调会，是有实权的产品经营单元
5. **结构化流程**——六阶段+双控点，流程是纪律不是建议
6. **异步开发与CBB**——公共基础模块先行沉淀，产品开发在CBB上组装而非从零造轮子

## 关键模块

### 模块1：六大阶段

- 定义：产品从构想到退市的全生命周期，被切分为六个有明确输入输出的阶段
- 输入：市场需求+业务计划（来自MM流程）
- 输出：可交付的产品包+全生命周期管理方案
- 关键动作：
  - 概念阶段：明确"做什么"——需求分析、概念方案、可行性评估
  - 计划阶段：明确"怎么做"——详细方案、资源计划、风险识别
  - 开发阶段：按计划构建——编码/设计/集成、CBB复用
  - 验证阶段：确认"做对了"——系统测试、客户验证、制造验证
  - 发布阶段：推向市场——上市准备、渠道赋能、首批交付
  - 生命周期管理：持续运营——版本维护、降本优化、退市决策
- 常见误区：把阶段当走过场，尤其是计划阶段草率跳过，导致开发阶段反复返工

### 模块2：DCP投资决策点

- 定义：IPMT在阶段转换时进行的商业决策评审，决定项目继续/转向/终止
- 输入：阶段交付件+商业论证
- 输出：Go/No-Go/Redirect决策
- 关键动作：
  - CDCP（概念决策点）：项目值不值得立项？
  - PDCP（计划决策点）：方案和资源是否可行？
  - ADCP（可用性决策点）：产品是否达到上市标准？
  - LDCP（生命周期决策点）：产品是否继续/退市？
- 常见误区：DCP变成橡皮图章，IPMT不敢叫停已投入大量资源的项目（沉没成本谬误）

### 模块3：TR技术评审点

- 定义：技术维度的质量关卡，确保产品技术方案在每个里程碑达到预期水平
- 输入：技术文档+测试结果+评审检查单
- 输出：技术风险评估+改进要求
- 关键动作：
  - TR1-TR6分布在开发与验证阶段
  - 每个TR有明确的通过标准和遗留问题处理机制
  - TR不通过不影响DCP决策，但必须记录风险
- 常见误区：TR与DCP混淆——TR管技术质量，DCP管商业投资，两者独立运作

### 模块4：IPMT与PDT

- 定义：IPMT是跨产品线的投资决策委员会，PDT是端到端负责产品交付的重量级团队
- 输入：IPMT接收业务提案，PDT接收IPMT的授权与资源
- 输出：IPMT输出投资决策，PDT输出产品包
- 关键动作：
  - IPMT：组合管理、资源分配、DCP评审、PDT考核
  - PDT：跨部门组建（研发+营销+供应链+财务+质量）、端到端负责、共享KPI
  - PDT经理有资源调度权，不是协调员而是经营者
- 常见误区：PDT变成虚线汇报的协调组织，成员仍听命于原部门而非PDT经理

### 模块5：MM市场管理流程

- 定义：IPD的前端输入流程，负责从市场洞察到产品路标的全链路规划
- 输入：市场数据+竞争情报+客户需求
- 输出：产品路标+业务计划+投资优先级
- 关键动作：
  - 了解市场：五看（宏观/行业/客户/竞争/自身）
  - 细分市场：H1成熟/H2成长/H3探索三类策略
  - 组合分析：基于价值-风险矩阵排列投资优先级
  - 制定业务计划：产品路标+竞争策略+资源需求
  - 融合优化：跨产品线对齐，消除重复投资
  - 管理评估：持续监控市场变化，动态调整
- 常见误区：MM与IPD脱节——MM做完规划后束之高阁，IPD阶段不参考MM输出

### 模块6：异步开发与CBB

- 定义：将公共技术模块（CBB）与产品开发解耦，CBB先行开发并沉淀，产品在CBB上快速组装
- 输入：技术架构+公共需求
- 输出：可复用的CBB库+产品定制化模块
- 关键动作：
  - 识别公共需求，抽象为CBB
  - CBB独立开发、独立测试、独立版本管理
  - 产品开发时优先复用CBB，仅开发差异化部分
  - 建立CBB贡献与复用的激励机制
- 常见误区：CBB库变成"僵尸库"——有人贡献没人复用，因为缺乏版本管理和质量保证

## 决策启发式

| 场景 | 判断规则 | 来源 |
|------|---------|------|
| 产品立项 | 如果没有经过MM流程验证市场需求，则不应进入IPD概念阶段 | 华为IPD实践 |
| DCP评审 | 如果项目商业论证ROI低于阈值且无战略价值，则应终止而非继续投入 | 投资决策原则 |
| TR不通过 | 如果技术风险为高且无缓解方案，则TR不通过但DCP可继续（记录风险） | 双控机制设计 |
| 跨部门冲突 | 如果PDT成员双重汇报导致决策迟缓，则PDT经理应有人事考核权 | 重量级团队原则 |
| CBB复用 | 如果某模块被3个以上产品使用，则应升级为CBB并独立维护 | 异步开发原则 |
| 版本规划 | 如果市场需求变化导致原方案失效，则回到计划阶段重新评估，而非在开发阶段硬改 | 结构化流程纪律 |

## 适用场景

### 最适合

- B2B复杂产品开发（通信设备、企业软件、工业系统）
- 多产品线并行、需要组合管理的中大型企业
- 研发投入大、周期长、失败成本高的行业
- 跨部门协作瓶颈明显的组织（研发与市场脱节）

### 不适合

- 10人以下初创团队（流程成本高于收益）
- C端快消品/互联网产品（迭代速度要求远超IPD的节奏）
- 探索性创新项目（不确定性太高，无法按阶段评审）
- 单一产品线的小型企业（没有组合管理的需求）

## 实施检查清单

- [ ] IPMT是否真正有投资决策权（而非橡皮图章）？
- [ ] PDT经理是否有人事考核权和资源调度权？
- [ ] DCP是否有真实的Go/No-Go记录（有没有项目被叫停过）？
- [ ] TR与DCP是否独立运作（技术评审不替代商业决策）？
- [ ] MM流程是否在IPD之前运行（产品立项有市场验证）？
- [ ] CBB库是否有活跃的复用记录（而非僵尸库）？
- [ ] 六个阶段是否有明确的交付件清单和通过标准？
- [ ] 跨部门成员是否真正在PDT中全职投入（而非兼职协调）？

## 诚实边界

1. **流程过重**：IPD的完整实施需要大量文档、评审和协调，对小型团队是负担而非助力。华为自身也经历了从3.0到5.1的持续裁剪。
2. **文化前提**：IPD有效运作依赖"让听得见炮声的人呼唤炮火"的组织文化。如果决策权仍集中在高层，PDT就是空壳。
3. **投资纪律**：DCP的杀伤力取决于IPMT是否敢于止损。如果组织文化回避冲突、不敢叫停，DCP就退化为进度汇报会。
4. **知识盲区**：本文件基于公开资料整理，不包含华为IPD的内部实操细节、裁剪规则和行业适配方案。
5. **落地周期**：华为从1999年引入到真正见效花了5年以上，且投入数亿美元咨询费。短期照搬不可能复制效果。
