# Amazon · 逆向工作法（PR/FAQ）

> 先写新闻稿再写代码——用客户视角的"发布稿"验证产品价值，故事说不通就不动手。

## 核心理念

逆向工作法解决的核心问题是：**如何在投入工程资源之前，先验证产品对客户是否真的有价值？**

传统产品开发是"正向"的——先有技术方案，再找目标用户，最后写营销话术。这条路径的致命缺陷是：团队在写完代码之后才发现"没人想要这个东西"。逆向工作法把这个顺序倒过来——先模拟产品发布后的客户体验，如果客户不会为此兴奋，项目就不该启动。

本质是**用叙事替代预测**：不是猜测客户会喜欢什么，而是逼自己站在客户角度把产品体验讲成一个完整的故事。故事讲不通，说明产品逻辑有硬伤；故事讲通了，才值得投入资源。

## 框架结构

```
逆向工作法 = PR/FAQ 迭代验证系统
│
├── 起源层
│   └── 2004年禁止PPT → 需要替代方案 → PR/FAQ是6页纸备忘录在产品开发中的具体应用
│
├── PR层（Press Release / 新闻稿）
│   ├── 标题：产品一句话定位
│   ├── 问题：客户当前痛点是什么
│   ├── 方案：产品如何解决这个痛点
│   ├── 引用：来自"客户"的证言
│   ├── 如何开始：客户如何上手
│   └── 客户体验描述：从客户视角描述使用场景
│
├── FAQ层（Frequently Asked Questions）
│   ├── 外部FAQ：客户会问什么——价格/可用性/兼容性
│   └── 内部FAQ：团队该问什么——成本/技术可行性/竞品应对/依赖关系
│
├── 迭代层
│   ├── PR/FAQ写完→评审→质疑→重写→再评审
│   ├── 迭代多次直到"故事说得通"
│   └── 故事说得通→才写第一行代码
│
└── 验证层
    └── PR/FAQ是"事前验证"——在代码之前验证客户价值
```

## 关键模块

### 模块1：PR新闻稿

- 定义：用面向客户的新闻稿格式描述一个尚未存在的产品，模拟产品发布时客户会看到什么
- 输入：客户痛点+产品构想+市场洞察
- 输出：一篇完整的、面向外部读者的新闻稿
- 关键动作：
  - 标题：用一句话说清产品是什么、给谁用
  - 问题陈述：客户今天面临什么具体困难？不是"市场有机会"，而是"客户在受苦"
  - 方案描述：产品如何解决上述问题——从客户视角描述，不是技术视角
  - 客户引言：虚构一段"客户"的证言，描述使用后的感受
  - 如何开始：客户获取和使用产品的路径
- 常见误区：把PR写成内部方案——PR的读者是外部客户，不是内部评审者。如果PR读起来像技术文档，说明还在"正向思维"

### 模块2：FAQ常见问题

- 定义：回答产品最尖锐的质疑——包括客户会问的和团队该问的
- 输入：PR草稿+所有利益相关方的质疑
- 输出：结构化的问答文档，覆盖外部和内部两大类问题
- 关键动作：
  - 外部FAQ：客户会问什么？——多少钱？什么时候能用？和现有产品什么关系？数据怎么迁移？
  - 内部FAQ：团队该问什么？——成本结构是什么？技术上有无不可逾越的障碍？竞品如果跟进怎么办？依赖哪些内部团队？关键指标怎么定义？
  - FAQ不是粉饰太平——每个回答都必须诚实，如果某个问题回答不了，说明产品方案还不成熟
- 常见误区：FAQ只写"好回答的问题"，回避"难回答的问题"——恰恰是难回答的问题暴露了方案的致命缺陷

### 模块3：迭代验证循环

- 定义：PR/FAQ不是一次性文档，而是反复打磨直到"故事说得通"的迭代过程
- 输入：上一版PR/FAQ+评审反馈+新发现的质疑
- 输出：经过多轮验证的、故事逻辑自洽的PR/FAQ终稿
- 关键动作：
  - 每轮评审：团队集体阅读→提问质疑→识别逻辑断裂→重写
  - "故事说得通"的标准：客户痛点真实、方案直接回应痛点、客户愿意为此付费、内部能力支撑得住
  - 迭代次数不限——Prime和Kindle的PR/FAQ都经历了大量重写
  - 故事说不通→项目不启动，而不是"先做再改"
- 常见误区：把PR/FAQ当成走流程——写一版就通过，没有真正的质疑和重写。如果没有人提出尖锐问题，说明评审质量不够

### 模块4：事前验证思维

- 定义：在写代码之前验证客户价值，而不是在写完代码之后用数据验证
- 输入：产品假设+客户洞察+竞争格局
- 输出：经过事前验证的产品立项决策
- 关键动作：
  - 传统模式：假设→开发→上线→数据验证→发现没人要→沉没成本
  - 逆向模式：假设→PR/FAQ验证→故事说不通→零成本放弃 / 故事说得通→开发→上线
  - 事前验证不是预测未来，而是逼团队把隐含假设显性化——每个假设都写在FAQ里，接受质疑
- 常见误区：把事前验证等同于"想清楚再干"——PR/FAQ不是完美规划，而是快速试错，只不过试错的成本是写作时间而非工程资源

### 模块5：与6页纸备忘录的关系

- 定义：PR/FAQ是6页纸备忘录在产品开发场景下的具体形态
- 输入：6页纸的叙述体写作要求+产品开发的结构化需求
- 输出：符合6页纸标准的、面向产品决策的叙事文档
- 关键动作：
  - 2004年贝索斯禁止PPT后，6页纸成为Amazon决策沟通的标准格式
  - PR/FAQ继承了6页纸的核心：叙述体（非碎片）、完整逻辑链（非跳跃）、可独立阅读（非依赖口述）
  - PR/FAQ在6页纸基础上增加了产品开发特有的结构：PR部分面向客户叙事，FAQ部分面向内部质疑
- 常见误区：把PR/FAQ和6页纸割裂——PR/FAQ不是独立方法论，而是6页纸在产品场景的落地形态

## 决策启发式

| 场景 | 判断规则 | 来源 |
|------|---------|------|
| 是否启动一个产品项目 | 如果PR/FAQ的故事说不通→不启动；如果故事说得通→才写代码 | 逆向工作法核心 |
| PR是否合格 | 如果PR读起来像内部技术方案→重写；如果读起来像面向客户的新闻稿→通过 | PR写作标准 |
| FAQ是否充分 | 如果没有"回答不了的问题"→FAQ不够尖锐；如果有回答不了的问题且无法解决→项目不该做 | FAQ验证逻辑 |
| 迭代是否到位 | 如果PR/FAQ只写了一两版就通过→迭代不足；如果经历了多轮质疑和重写→迭代到位 | Prime/Kindle实践 |
| 选择事前验证还是事后验证 | 如果产品失败成本高（硬件/基础设施）→事前验证；如果迭代成本极低（软件功能）→事后验证也可 | 成本-风险权衡 |
| PR/FAQ与数据驱动如何配合 | 如果是全新品类→PR/FAQ先行；如果是已有产品的优化→A/B测试先行 | Amazon实践 |

## 适用场景

### 最适合

- 全新产品品类——没有历史数据参考，只能靠叙事验证客户价值
- 硬件/基础设施项目——试错成本极高，必须在写代码前想清楚
- B2C客户体验驱动型产品——客户视角的叙事最容易验证
- 跨部门协作的大型项目——PR/FAQ强制对齐各方对"产品是什么"的理解

### 不适合

- 已有产品的微调优化——A/B测试比PR/FAQ更直接有效
- 探索性极强的不确定性项目——连客户是谁都不确定，PR无从写起
- 紧急响应/热修复——没有时间迭代PR/FAQ
- 内部工具/基础设施——没有外部"客户"，PR的新闻稿格式失去意义

## 实施检查清单

- [ ] PR是否面向外部客户撰写——读起来像新闻稿而非内部方案
- [ ] PR是否从客户痛点出发——先说问题再说方案
- [ ] FAQ是否包含"回答不了的问题"——如果没有，说明质疑不够尖锐
- [ ] FAQ是否区分外部问题（客户视角）和内部问题（团队视角）
- [ ] PR/FAQ是否经历了多轮迭代——一两版就通过等于没验证
- [ ] 评审中是否有人真正提出质疑——如果一片叫好，说明评审质量不够
- [ ] "故事说得通"的标准是否明确——客户痛点真实/方案直接回应/客户愿付费/内部能力支撑
- [ ] 故事说不通时是否敢于不启动——如果每个项目都通过了PR/FAQ，说明验证是走过场

## 诚实边界

1. **叙事偏差**：PR/FAQ本质是讲故事，而故事可以被讲得很好听。一个善于写作的团队可能把一个平庸的产品讲成令人兴奋的故事，反之一个不善于叙事的团队可能低估了一个好产品。验证质量取决于叙事能力，这是一个系统性偏差。

2. **事前验证的局限**：PR/FAQ验证的是"客户价值假设"，不是"技术可行性假设"。一个故事说得通的PR/FAQ，技术上可能根本做不出来。FAQ的内部问题部分可以暴露技术风险，但无法替代真正的技术验证。

3. **B2B场景的适配困难**：PR/FAQ天然适合B2C场景——客户是个人消费者，体验可以想象。但B2B场景中，"客户"是组织，决策链长、利益相关方多，一篇新闻稿很难覆盖所有决策者的关切。

4. **与数据驱动的张力**：Amazon自身也大量使用数据驱动（推荐算法/A/B测试），PR/FAQ和数据驱动并非替代关系而是互补关系。但在实践中，"故事说得通"和"数据证明有效"之间可能产生冲突——故事很好但数据不好，或数据很好但故事讲不通。

5. **知识盲区**：本文件基于公开资料整理，不包含Amazon内部PR/FAQ的具体模板、评审流程细节和项目决策的真实案例数据。

6. **文化前提**：PR/FAQ有效运作依赖"Disagree and Commit"的文化——评审中必须有人敢于说"故事说不通"。如果组织文化回避冲突，PR/FAQ就退化为形式主义的文档流程。
