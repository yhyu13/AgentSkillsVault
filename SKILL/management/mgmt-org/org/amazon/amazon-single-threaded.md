# Amazon · 单线程领导（Single-Threaded Leadership）

> 一个人，100%专职，带一支独立团队，把一件事做到底——不兼职、不协调、不等待。

## 核心理念

单线程领导解决的核心问题是：**为什么大公司里重要项目总是推进缓慢甚至半途而废？**

答案出乎意料地简单：因为没有人100%为它负责。每个参与者都在同时做三件事，每个项目都是某人的兼职工作。贝索斯在一次项目追问中发现了这个结构性问题——他逐个询问项目相关人"你在这个项目上投入多少时间"，没有一个人回答100%。于是他定下了原则：**"The best way to fail at inventing something is to make it somebody's part-time job."**

单线程领导的解法不是加强协调，而是消除协调的需求——把跨部门依赖内部化，让一个独立团队拥有完成项目所需的所有能力。团队之外没有需要等待的人，没有需要申请的资源，没有需要对齐的日程。一条线，从头到尾，自给自足。

核心命题：**组织独立性的价值高于协调效率——与其优化跨团队沟通，不如让沟通变得不必要。**

## 关键模块

### 模块1：100%专职——兼职必败原则

- 定义：项目负责人必须将全部工作时间投入该项目，不得同时承担其他项目或管理职能
- 输入：项目立项决策
- 输出：一个全职投入的领导者
- 关键动作：
  - 贝索斯发现问题的场景：追问某项目负责人"你在这个项目上投入多少时间"，答案从5%到50%不等，没有100%
  - "The best way to fail at inventing something is to make it somebody's part-time job"——兼职是创新最可靠的失败方式
  - 100%专职不是"主要精力在这个项目"——是字面意义上的全部时间，没有例外
  - 专职意味着领导者的职业成功与这一个项目的成败完全绑定——没有退路，没有备选
- 常见误区：以为"大部分时间投入"就够了——80%和100%之间不是20%的量差，而是"有没有退路"的质差；让管理者兼任单线程领导——管理职能本身就是另一份全职工作

### 模块2：独立团队——将依赖内部化

- 定义：单线程领导带领一支拥有端到端能力的独立团队，团队内部完成所有必要工作，无需等待外部团队
- 输入：项目范围 + 所需能力清单
- 输出：一支自给自足的独立团队
- 关键动作：
  - 传统做法：项目需要设计→找设计团队，需要开发→找开发团队，需要测试→找测试团队，每个环节都是跨团队协调
  - 单线程做法：把设计、开发、测试全部放进同一个团队——不是加强协调，而是让协调变得不必要
  - 团队规模控制在"两个披萨"能喂饱的范围——通常6-10人，保持沟通效率和敏捷性
  - 团队边界清晰——职责不与其它团队重叠，避免"三个团队做同一件事"的混乱
- 常见误区：以为独立团队等于大团队——独立不是人多，而是能力全；把所有职能都塞进团队但人数膨胀到30人——这已经超出了两个披萨团队的边界

### 模块3：单线性——一条线到底

- 定义：团队只做一件事，从开始到完成，不并行多项目
- 输入：项目优先级排序
- 输出：团队100%聚焦于单一项目
- 关键动作：
  - 单线程的"单"字有两层含义：领导者只做一个项目（个人层面），团队只推进一条任务线（团队层面）
  - 多线程的代价：上下文切换消耗认知资源，每个项目都做到80%但没有一个做到100%
  - 单线性不等于线性执行——团队内部可以有并行工作，但目标只有一个
  - 项目完成后团队可以转向新项目，但在任一时刻只有一个焦点
- 常见误区：把单线性理解为"不能并行"——团队内部可以并行，但战略焦点只有一个；以为单线程意味着慢——恰恰相反，因为零上下文切换、零等待，单线程往往更快

### 模块4：边界感——不重叠、不遗漏

- 定义：每个单线程团队的职责边界清晰，与其它团队之间没有灰色地带
- 输入：组织能力地图 + 项目范围定义
- 输出：无重叠、无遗漏的团队职责划分
- 关键动作：
  - 边界感是独立性的前提——如果两个团队的职责有重叠，独立性就被破坏，协调需求重新出现
  - 边界划分遵循"不重叠、不遗漏"原则——MECE（Mutually Exclusive, Collectively Exhaustive）在团队设计中的应用
  - 边界不是永久固定的——随着项目演进，团队边界可以调整，但调整后必须重新确保无重叠
  - 边界感也意味着团队有明确的"不做"清单——不做边界之外的事，避免蔓延
- 常见误区：边界划分过于技术导向——应该从客户价值或业务结果出发划分，而非从技术栈出发；边界太细导致团队过多——每个团队都需要足够的体量才能自给自足

### 模块5：两个披萨团队——规模约束

- 定义：单线程团队的规模控制在两个披萨能喂饱的人数范围内，通常6-10人
- 输入：项目复杂度 + 所需能力
- 输出：精干而全功能的团队
- 关键动作：
  - 规模约束的核心目的：保持沟通效率——团队越大，沟通路径越多（n(n-1)/2），决策越慢
  - 两个披萨是经验法则而非硬性数字——关键是团队小到每个人都知道其他人在做什么
  - 小团队倒逼能力密度——每个成员必须独当一面，不能有"只做一小块"的螺丝钉
  - 如果项目复杂度超出两个披萨团队的承载能力，应该拆分为多个独立的单线程团队，而非扩大单个团队
- 常见误区：把两个披萨当成精确数字——6人和12人的沟通效率差异巨大，但都可能在"两个披萨"范围内；为了凑人数而缩小团队——如果5个人就能做完，不需要为了"看起来更正式"而加到8人

## 决策启发式

| 场景 | 判断规则 | 来源 |
|------|---------|------|
| 是否需要单线程领导 | 如果项目是0→1的创新型项目→必须单线程；如果是渐进式优化→可以多线程 | 兼职必败原则 |
| 领导者是否合格 | 如果此人还在兼管其他项目或职能→不合格；如果此人100%投入且对结果全权负责→合格 | 100%专职定义 |
| 团队是否独立 | 如果团队完成工作需要等待外部团队→独立性不足；如果所有必要能力都在团队内部→独立 | 独立团队定义 |
| 团队规模是否合适 | 如果团队超过10人→考虑拆分；如果团队内部有人不知道其他人在做什么→团队太大 | 两个披萨原则 |
| 跨团队依赖如何处理 | 如果依赖是偶尔的→接受；如果依赖是持续的→将对方能力内部化 | 依赖内部化原则 |
| 多个项目如何排序 | 如果资源有限→按战略优先级逐个推进，而非同时推进多个项目 | 单线性原则 |
| 项目完成后团队怎么办 | 如果有新的同等优先级项目→团队转向新项目；如果没有→团队解散，人员重新分配 | 灵活性原则 |

## 适用场景

### 最适合

- 0→1的创新型项目——没有历史路径依赖，需要全速推进
- 跨部门依赖严重的项目——将依赖内部化是最有效的解法
- 大型组织中的关键项目——大组织的协调成本最高，单线程的收益最大
- 时间窗口紧迫的项目——零等待、零协调意味着最快速度
- 技术和业务深度耦合的项目——需要业务判断和技术能力在同一团队内快速迭代

### 不适合

- 纯维护型工作——稳定运行的系统不需要全职投入，兼职响应即可
- 需要广泛共识的战略决策——单线程适合执行，不适合需要多方认同的决策制定
- 资源极度受限的小型组织——没有足够的人组建独立团队，单线程的门槛达不到
- 高度标准化的重复性工作——流程已经成熟，独立性带来的边际收益低
- 需要多专业领域深度协作的复杂系统工程——单一团队无法覆盖所有专业深度

## 实施检查清单

- [ ] 项目负责人是否100%专职——不兼其他项目、不兼管理职能
- [ ] 团队是否拥有端到端的所有必要能力——完成工作是否需要等待外部团队
- [ ] 团队规模是否在两个披萨范围内——通常不超过10人
- [ ] 团队职责边界是否清晰——与其它团队有无重叠和灰色地带
- [ ] 是否存在持续的跨团队依赖——如果有，是否可以内部化
- [ ] 领导者的职业成功是否与项目成败完全绑定——有没有退路
- [ ] 项目是否是0→1的创新型项目——渐进式优化可能不需要单线程
- [ ] 组织是否愿意为独立性付出资源代价——独立团队意味着资源冗余，这是成本

## 诚实边界

1. **资源冗余的代价**：独立团队意味着每个团队都拥有完整能力，这必然导致资源冗余——三个单线程团队可能各需要一个设计师，而共享模式下一个设计师就够了。单线程用资源换速度，但资源不是无限的。

2. **组织规模门槛**：单线程领导的前提是组织有足够的人来组建独立团队。对于50人以下的公司，每个项目都搞独立团队是不现实的——你可能根本没有足够的设计师、工程师和产品经理来分配。

3. **专业深度的两难**：独立团队需要"全功能"，但全功能不等于全专业。一个6人团队里的工程师可能不是该领域最顶尖的专家，而共享模式下的专业团队可以集中最顶尖的人才。独立性牺牲了专业深度。

4. **与华为铁三角的对比需要语境**：铁三角适合B2B长周期销售场景——客户关系、方案设计、交付承诺需要不同专业的人深度协作，内部化所有能力不现实。单线程适合产品开发场景——产品可以由一个小团队端到端交付。场景不同，组织模式不同，不是简单的优劣关系。

5. **与Netflix知情船长的互补性被简化**：知情船长和单线程领导确实解决不同问题，但在实际组织中，决策权和执行权往往纠缠在一起。单线程领导既是执行的负责人，往往也是决策的船长——两个角色的重叠可能导致权力过度集中。

6. **知识盲区**：本文件基于公开资料整理，不包含Amazon内部单线程团队的具体组建流程、人员调配机制和项目结束后的团队解散实践。
