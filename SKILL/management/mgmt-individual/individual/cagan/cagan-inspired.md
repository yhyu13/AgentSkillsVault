# 马蒂·卡根 · 产品发现+交付双轨(Inspired + Empowered)

> 产品团队≠功能工厂；发现>交付；产品需要领导力不是管理

## 核心理念

卡根要解决的根本问题是：**为什么大多数产品团队是"功能工厂"而非"技术驱动型产品团队"？为什么大多数公司做错了双轨制？**

卡根的底层逻辑是三重升级：第一层，从功能工厂到产品团队——功能工厂按路线图交付功能，产品团队按业务结果解决问题；功能工厂是"做什么"的执行者，产品团队是"解决什么问题"的所有者；第二层，从交付到发现+交付——大多数公司只关注交付（把功能做出来），卡根强调发现比交付更重要（先验证值不值得做）；发现和交付是两条并行轨道，不是先后顺序；第三层，从管理到领导力——产品需要领导力不是管理：愿景>路线图，策略>计划，赋能>管控。

核心公式：**功能工厂→产品团队（从执行到所有）→ 交付→发现+交付（从做出来到值不值得做）→ 管理→领导力（从管控到赋能）→ 双轨制=发现和交付并行不是先后 → 大多数公司做错了双轨**

卡根在惠普、Netscape、eBay等公司担任产品高管后创办SVPG(Silicon Valley Product Group)，为全球顶尖科技公司提供产品咨询。他的两本书——《Inspired》聚焦"如何打造技术驱动型产品团队"，《Empowered》聚焦"如何赋能产品团队"——构成了产品管理的完整框架。

## 关键模块

### 模块1：技术驱动型产品团队

- 定义：技术驱动型产品团队是"被赋予业务问题而非功能列表"的团队——产品经理、设计师、工程师的铁三角共同解决问题，而非各自分工交付功能
- 输入：业务问题、用户需求、技术约束
- 输出：解决业务问题的产品方案
- 关键动作：
  - 为什么产品团队≠功能工厂——功能工厂模式：利益相关者提需求→产品经理写PRD→设计师画原型→工程师写代码→测试上线；这个模式的问题是：产品经理变成需求翻译器，设计师变成原型画师，工程师变成代码工人——没有人对业务结果负责；技术驱动型产品团队模式：团队被赋予业务问题→产品经理发现值得解决的问题→设计师设计解决方案→工程师用技术实现→团队对业务结果负责
  - 产品经理/设计师/工程师铁三角——产品经理：发现值得解决的用户问题，确保产品有价值(value)和商业可行性(viability)；设计师：设计用户可用的解决方案，确保产品可用(usable)；工程师：用技术实现解决方案，确保产品可行(feasible)；铁三角缺一不可——没有产品经理的团队做不出有价值的产品，没有设计师的团队做不出好用的产品，没有工程师的团队做不出可行的产品
  - 为什么团队>个人——产品是团队协作的结果不是个人英雄主义的产物；一个人再强也无法同时做好发现、设计和工程；卡根说"伟大的产品来自伟大的团队，不是伟大的个人"
  - 产品经理的核心能力——对用户的深度理解、对数据的敏锐洞察、对技术的足够认知、对商业的清晰判断；产品经理不是"写PRD的人"而是"发现值得解决的问题的人"
- 常见误区：把产品团队理解为"敏捷团队"——敏捷是交付方法不是团队定位，功能工厂也可以用敏捷但仍然是功能工厂；认为铁三角=三个角色各自为政——铁三角是协作不是分工，三个角色必须紧密合作；认为产品经理=项目经理——产品经理对产品价值负责，项目经理对项目进度负责

### 模块2：产品发现

- 定义：产品发现是验证"产品是否值得做"的过程——验证价值(value)、可用性(usability)、可行性(feasibility)、商业可行性(viability)四个维度
- 输入：业务问题、用户洞察、技术约束、商业约束
- 输出：经验证的产品方案（值得投入交付的产品）
- 关键动作：
  - 验证值/可用性/可行性/商业可行性——价值(Value)：用户是否真的需要这个功能？他们愿意为此付费吗？可用性(Usability)：用户能理解和使用这个功能吗？可行性(Feasibility)：我们的技术能实现这个功能吗？商业可行性(Viability)：这个功能在商业上可行吗？成本、收入、合规？四个维度必须同时验证——只验证价值不验证可行性是"空中楼阁"，只验证可行性不验证价值是"没人要的产品"
  - 为什么发现>交付——发现决定"做正确的事"，交付决定"把事做正确"；做正确的事>把事做正确——做错误的事做得再好也是浪费；大多数公司花90%时间在交付、10%时间在发现，卡根建议反转比例——至少50%时间在发现
  - 6种发现技术——①用户访谈(User Interviews)：深度理解用户需求和痛点；②原型测试(Prototype Testing)：用原型验证可用性和价值；③冒烟测试(Smoke Test)：用假门测试验证需求强度；④A/B测试(A/B Testing)：用数据验证假设；⑤拼凑原型(Concierge/Prototype)：用人工方式验证复杂流程；⑥可行性冲刺(Feasibility Spike)：用技术原型验证技术可行性
  - 发现的节奏——发现不是一次性事件而是持续过程：每周至少1-2次用户接触，每2-4周验证一个产品假设，持续迭代直到找到值得投入交付的方案
- 常见误区：把发现理解为"做调研"——调研是发现的一种手段不是发现的全部，发现还包括原型测试和技术验证；认为发现=不做产品——发现是做最小实验验证假设，不是空谈；跳过发现直接交付——没有发现的交付是"功能工厂"模式

### 模块3：产品交付

- 定义：产品交付是"把经验证的产品方案实现并推向用户"的过程——持续交付、小批量、快速反馈是交付的核心原则
- 输入：经验证的产品方案（发现阶段的输出）
- 输出：上线的产品功能、用户反馈数据
- 关键动作：
  - 为什么交付是基础——没有交付，发现只是想法；交付是发现的基础——只有交付了才能获得真实用户反馈，只有真实用户反馈才能验证发现是否正确；卡根说"发现决定方向，交付验证方向"
  - 持续交付——持续交付(Continuous Delivery)是产品交付的核心能力：每次代码提交都可以安全部署、自动化测试覆盖关键路径、一键部署到生产环境；持续交付让团队从"每月发布一次"变成"每天发布多次"，大幅缩短反馈环
  - 小批量——小批量交付是精益思想在产品开发中的应用：每次交付最小可用功能、快速获得用户反馈、根据反馈调整方向；大批量交付的问题：开发周期长、反馈延迟、风险累积、调整困难
  - 为什么交付质量决定发现速度——交付质量高=发布速度快=反馈速度快=发现速度快；交付质量低=发布速度慢=反馈速度慢=发现速度慢；卡根说"交付能力是发现能力的瓶颈——如果你的团队需要3个月才能发布一个功能，你的发现速度就被3个月的反馈环限制了"
- 常见误区：认为交付=写代码——交付包括设计、编码、测试、部署、监控的全流程；认为持续交付=没有质量保证——持续交付依赖自动化测试和渐进式发布，不是降低质量标准；认为小批量=碎片化交付——小批量是每次交付最小完整功能，不是交付半成品

### 模块4：产品领导力

- 定义：产品领导力是"通过愿景和策略赋能产品团队"——不是管理团队做什么，而是领导团队解决什么问题
- 输入：公司战略、市场洞察、团队能力
- 输出：产品愿景、产品策略、赋能的团队
- 关键动作：
  - 为什么产品需要领导力不是管理——管理是"告诉团队做什么"，领导力是"告诉团队为什么做"；管理是"管控过程"，领导力是"赋能结果"；功能工厂需要管理，产品团队需要领导力；卡根说"如果你需要告诉产品团队做什么，你就没有产品领导力"
  - 产品愿景——产品愿景是"我们5-10年后要创造什么"的清晰图景：愿景不是功能列表而是用户价值的北极星；愿景让团队在遇到困难时知道方向，在遇到选择时知道取舍；卡根说"没有愿景的产品团队是迷失的团队"
  - 产品策略——产品策略是"如何从现在到愿景"的路径规划：策略不是路线图而是优先级框架——先解决什么问题、服务什么用户、进入什么市场；策略比路线图更重要——路线图是"什么时候做什么功能"，策略是"为什么先做这个"
  - 为什么愿景>路线图——路线图是功能列表按时间排列——Q1做A功能，Q2做B功能；愿景是用户价值的长远图景——5年后用户的生活因为我们的产品变得怎样；路线图容易过时（市场变化），愿景相对稳定（用户价值不变）；卡根说"路线图是管理工具，愿景是领导力工具"
- 常见误区：把产品领导力理解为"产品经理的领导力"——产品领导力是产品负责人/VP/CEO的职责，不是产品经理的职责；认为愿景=口号——愿景必须足够具体到能指导决策，口号太抽象无法指导取舍；认为策略=路线图——策略是优先级框架，路线图是时间计划

### 模块5：双轨制实施

- 定义：双轨制是产品发现和产品交付并行运行的机制——发现轨道验证假设，交付轨道实现方案，两条轨道节奏不同但相互驱动
- 输入：业务问题、团队产能、技术约束
- 输出：双轨制的运行节奏和协调机制
- 关键动作：
  - 为什么大多数公司做错了双轨——错误1：发现和交付先后顺序——先发现再交付，发现完成后才进入交付；正确做法：发现和交付并行——团队同时进行发现和交付；错误2：发现变成"研究部门"——发现团队和交付团队分离，发现变成纯研究不产出产品；正确做法：同一个团队同时做发现和交付；错误3：发现没有交付验证——发现产出的方案不经过交付验证就进入路线图；正确做法：发现必须用原型和测试验证，交付必须用真实用户数据验证
  - 发现和交付的节奏——发现节奏：每周1-2次用户接触，每2-4周验证一个假设，持续进行；交付节奏：每1-2周交付一个功能增量，持续发布，持续获得反馈；两条节奏不同但必须协调——发现验证的方案进入交付队列，交付获得的反馈驱动新的发现
  - 如何避免发现变成"研究"——发现的目的是"验证产品是否值得做"不是"产出研究报告"；发现必须有明确的假设和验证标准——"我们假设X类用户有Y问题，我们用Z方法验证"；发现的结果是"做/不做/修改"的决策不是PPT报告
  - 双轨制的团队配置——同一个产品团队同时做发现和交付：产品经理主导发现（验证价值/商业可行性），设计师参与发现（验证可用性），工程师参与发现（验证可行性）；交付阶段三人紧密协作；关键：不要把发现和交付分配给不同的人或团队
- 常见误区：认为双轨制=两个团队——双轨制是两条轨道不是两个团队，同一个团队同时做发现和交付；认为发现可以脱离交付——发现必须与交付紧密耦合，脱离交付的发现是"研究"不是"产品发现"；认为双轨制=双倍工作量——发现减少了无效交付的工作量，总体工作量反而减少

## 决策启发式

| 场景 | 判断规则 | 来源 |
|------|---------|------|
| 团队是功能工厂还是产品团队 | 如果团队被赋予功能列表→功能工厂；如果被赋予业务问题→产品团队 | 《Inspired》2017 |
| 发现vs交付时间分配 | 如果花在发现上的时间<30%→比例错误，至少50% | 《Inspired》2017 |
| 产品发现是否有效 | 如果发现没有验证4个维度（价值/可用性/可行性/商业可行性）→发现不完整 | 《Inspired》2017 |
| 选择哪种发现技术 | 如果验证需求强度→冒烟测试；如果验证可用性→原型测试；如果验证技术可行性→可行性冲刺 | 《Inspired》2017 |
| 产品领导力是否有效 | 如果需要告诉团队做什么→没有产品领导力；如果团队知道为什么做→有产品领导力 | 《Empowered》2020 |
| 愿景vs路线图 | 如果只有路线图没有愿景→团队迷失；如果有愿景有策略→团队有方向 | 《Empowered》2020 |
| 双轨制是否正确 | 如果发现和交付是先后顺序→做错了；如果是并行→做对了 | 《Inspired》2017 |
| 发现是否变成"研究" | 如果发现产出的是PPT报告→变成了研究；如果产出的是做/不做决策→是产品发现 | 《Inspired》2017 |
| 交付质量是否足够 | 如果发布周期>2周→交付质量不足，需要提升持续交付能力 | 《Inspired》2017 |
| 产品经理角色 | 如果产品经理在写PRD→角色错误；如果在发现值得解决的问题→角色正确 | 《Inspired》2017 |

| 字节A/B测试 | 下游-A/B测试是产品发现的技术之一 | 字节A/B测试是卡根产品发现中"6种发现技术"之一——用数据验证假设的工程化实践；字节把A/B测试做到极致——海量流量+实时数据+自动化决策；卡根提供"为什么要实验"的理论，字节提供"如何大规模实验"的技术 |

## 适用场景

### 最适合

- 科技公司产品团队，需要从功能工厂转型为技术驱动型产品团队
- 产品经理需要明确角色定位（发现者而非PRD写手）
- 组织需要建立双轨制（发现+交付并行）
- 产品领导力缺失，团队缺乏愿景和策略
- 交付能力强但发现能力弱的组织

### 不适合

- 外包型公司（按需求交付，不需要产品发现）
- 强合规行业（产品变更需要审批，双轨制节奏受限）
- 传统制造业（产品开发周期长，不适合快速发现迭代）
- 产品经理没有技术理解力的团队（铁三角无法协作）
- 没有基本敏捷交付能力的组织（先建立交付能力再建立发现能力）

## 实施检查清单

- [ ] 产品团队是被赋予业务问题还是功能列表
- [ ] 产品经理/设计师/工程师是否形成铁三角协作
- [ ] 发现时间是否占团队时间的至少30%（目标50%）
- [ ] 产品发现是否验证了4个维度（价值/可用性/可行性/商业可行性）
- [ ] 是否使用了多种发现技术（而非只用一种）
- [ ] 发现和交付是否并行而非先后
- [ ] 发现是否产出做/不做决策（而非PPT报告）
- [ ] 是否有清晰的产品愿景和策略（而非只有路线图）
- [ ] 交付能力是否足够支撑快速反馈（发布周期<2周）
- [ ] 产品领导力是否赋能团队（而非管控团队）

## 诚实边界

1. **铁三角的理想化假设**：卡根假设产品经理、设计师、工程师可以平等协作，但现实中三个角色之间存在权力不对等——工程师通常有更强的技术话语权，产品经理的"发现"可能被工程师的"不可行"否决。铁三角的平等协作需要组织文化的支撑。

2. **"发现>交付"的语境依赖**：卡根说"发现>交付"，但这依赖于组织已经有基本的交付能力。如果组织连交付都做不好（发布周期>1个月），先提升交付能力比建立发现能力更紧迫。发现>交付的前提是交付不是瓶颈。

3. **6种发现技术的选择困难**：卡根列出了6种发现技术但没有给出清晰的选择框架——什么场景用哪种技术？不同技术的适用条件和局限性是什么？实践者需要自己摸索，选择错误的发现技术可能浪费大量时间。

4. **产品愿景的落地困难**：卡根强调"愿景>路线图"，但大多数产品经理的日常工作被短期需求填满，没有时间思考5-10年的愿景。愿景需要高层领导的支持和保护，但卡根对如何获得这种支持的指导不足。

5. **双轨制的团队负荷**：同一个团队同时做发现和交付意味着团队成员需要同时处理两种不同节奏的工作——发现的节奏是不确定的（可能2周验证一个假设，也可能2个月），交付的节奏是相对确定的（每1-2周交付一个增量）。两种节奏的叠加可能导致团队过载。

6. **硅谷偏见**：卡根的框架基于硅谷顶尖科技公司的实践——这些公司有顶尖人才密度、充足的资源、快速的迭代环境。在非硅谷环境中，人才密度和资源限制使得"技术驱动型产品团队"的理想难以实现。

7. **产品经理的能力门槛**：卡根对产品经理的期望极高——深度理解用户、敏锐洞察数据、足够认知技术、清晰判断商业。现实中大多数产品经理达不到这个标准，卡根对"如何培养这样的产品经理"的指导不够具体。
