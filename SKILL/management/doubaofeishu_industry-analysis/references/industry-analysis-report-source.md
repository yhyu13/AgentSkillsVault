# doubao\-industry\-analysis（行业分析报告）

**Skill ID：**doubao\-industry\-analysis（行业分析报告）

**蒸馏发起方：**行业深度洞察专家

**蒸馏日期：**2026\-11\-10

**核心定位：**针对某一行业/赛道的中长期基本面与产业研究，输出数据可溯源、判断有主线、结构完整的深度研究报告。默认交付可交互网页，用户明确要求时交付飞书云文档。

# 一、质量标准（最高优先级）

一份合格的行业深度报告必须做到五件事，按优先级排序：

1. **数据真实可溯源（底线）**。每个数字都要能追溯到清晰来源，每个关键判断都要说清依据来自一手披露、具名机构、行业数据还是本研究测算。绝不用印象、常识或模糊出处补数字。

2. **判断贯穿一条主线**。报告要有一个可验证、可推翻的核心判断，五大板块各自认领一个子命题去印证或限定它，而不是"什么都讲一点的资料汇编"。

3. **信息详实、有量化**。讲清行业真实经营图景：定义与边界、规模与增速、产业链与利润池、竞争格局与集中度、政策与驱动、盈利质量与现金流、关键风险与落地路径。

4. **事实支撑判断，而非替代判断**。分析性正文围绕判断展开，读者应看到判断如何由事实推出，而不是仅仅看到事实清单。

5. **克制专业**。语气像懂行的研究员在解释：直接、克制、重因果、少口号。区分确定事实、机构估算、媒体观点与作者推断。

# 二、核心方法论

## 2\.1 先有判断，再写正文

检索取证结束、动笔之前，先落一张**判断主线底稿**（七格表 \+ 三情景 \+ 各板块子命题）。证据推翻判断时，先改这张表，再动正文。

## 2\.2 五大板块写透

固定结构，每个板块开头用一句"亮明判断"的主题句，结尾用「回扣主线」小节收回到核心判断：

1. 行业定义与规模

2. 行业结构与竞争格局

3. 核心驱动与制约

4. 趋势研判与结构性机会

5. 商业化路径与盈利质量

外加：执行摘要、风险提示、结语、参考文献。

## 2\.3 三级数据分级守住真实性

每条数据先归入一/二/三级可信度，据此决定能否当展示数值、措辞要多克制：

|级别|定义|使用规则|
|---|---|---|
|一级|一手披露 / 官方统计 / 监管数据|可直接陈述，作为核心数据|
|二级|具名机构研报 / 行业协会 / 权威媒体|须显名归因，可作展示数据|
|三级|自媒体 / 社交内容 / 聚合页|仅作线索，不入展示|

## 2\.4 全表格化呈现

所有原本用图承载的并列信息（规模趋势、产业链全景、各环节毛利率、市场份额、三情景对比等）一律用结构化表格呈现，不出折线图、柱状图、饼图等配图。

# 三、工作流程

## 第 1 步 · 定锚与策略

- 用系统时间解算基准年与预测窗口（当前年 \+5）

- 确认任务类型、记录用户焦点、判定行业结构类型

- 承认训练数据可能过期：规模/政策/融资/技术以联网检索结果为准

## 第 2 步 · 检索取证与三级分级

- 取数只走两条通道：公开搜索（事实/政策/事件）\+ 金融数据（规模/增速/份额/财务）

- 以覆盖度而非轮数停机：核心维度各 ≥2 条证据，累计 ≥18 条

- 边查边记**来源台账**：取数通道、来源级别、数据基期、源值（原文数字＋单位＋口径）

- 两条通道都拿不到的，作为数据缺口如实记录，绝不编造

## 第 3 步 · 定判断主线（写正文前必做）

判断主线底稿包含：

- **一句话主线**：可验证、可推翻的核心判断

- **七格表**：决策问题 / 市场共识 / 非共识判断 / 核心数据 3\-5 个 / 因果链 / 利润池迁移 / 验证证伪信号 ≥5 个

- **三情景速览**：基准/乐观/悲观，先想好结果

- **各板块子命题**：每个板块认领什么子命题去印证主线

## 第 4 步 · 分批写入正文

- 正文按 6 批写入独立 Markdown 分片：执行摘要 → 定义规模 → 结构竞争 → 驱动制约 → 趋势机会 → 商业化风险参考文献

- 每批写完立即做单批校验：论证完整、与主线一致、标题层级正确

- 批 3 写完后额外做阶段校验，检查前 3 片结构与引用连续性

- 数字引用按正文首次出现顺序递增编号、同一来源全文复用、句末标注

## 第 5 步 · 交付前自检

最关键四项自检：

1. 判断主线已贯穿且无内部标签痕迹

2. 各批内容完整且核心数据前后一致

3. 每个市场/财务数字取数通道与出处级别达标、估算带相称限定语、缺口如实标注

4. 正文每个数字已句末标引用、并对照台账源值完成准确性核验

## 第 6 步 · 收尾与交付

- 拼接 6 个分片为整篇报告

- 运行整篇校验（引用编号顺序、数据准确性最终核验）

- 默认交付：可交互网页报告

- 用户明确要求飞书云文档时：导入飞书在线文档 \+ 交付抽查

# 五、交付标准

一份合格的行业深度报告应具备三个特征：

- **信息充分**：真实的规模、产业链、利润池、竞争格局、政策、盈利质量与风险事实，每处尽量带具体数字与一步测算。

- **判断清晰**：一条贯穿全文的核心判断、各板块认领的子命题、明确的"什么能验证 / 什么能推翻"，而非"行业空间大、长期看好"这种正确的废话。

- **证据可溯、数据可核**：正文每个数据点有句末数字引用、与台账源值核对一致、文末参考文献可点击且与正文勾稽、估算与二三级来源带相称限定语、数据缺口如实标注。

# 飞书文档写作方法论（Feishu Doc Writing）

**Skill ID：**feishu\-doc\-writing（飞书文档写作方法论）

**蒸馏发起方：**俞航的智能伙伴

**版本：**v1\.0\.0

**蒸馏日期：**2026\-11\-10

## 用途

用于在飞书云文档中产出高质量的技术文档、分析报告、进展总结、方案设计等结构化写作场景。核心能力是「结论先行 \+ 证据导向 \+ 结构清晰」，让读者在最短时间内获取关键信息，同时保留完整的论证链条和数据支撑。

不适用场景：营销文案、公文写作、文学创作、纯表格数据录入。

## 核心原则

### 1\. 结论先行（Inverted Pyramid）

每篇文档、每章、每段的第一句必须是结论或核心判断，不铺垫、不绕弯、不写"综上所述"式的结尾总结。

- 文档开篇用 callout 或 grid 放执行摘要，一句话讲完核心结论 \+ 关键数字

- 每个章节标题直接写判断或状态，不写中性描述（写「X 方案不可行」而非「X 方案分析」）

- 段落首句即结论，后面补证据和推理，读者扫首句就能掌握 80% 信息

### 2\. 证据导向（Evidence\-Based）

每个判断必须有数据或事实支撑，数字可追溯、来源可定位。

- 每个数字标注出处：哪个接口、哪份日志、什么时间、什么口径

- 引用外部材料用行内链接 `[[n]](url)`，不单独设"参考文献"章节

- 没有证据的判断标注「待核实」或「假设」，不写成既定事实

- 定性结论优先用定量数据支撑，其次用事实描述，最次用专家判断

### 3\. 结构化表达（Structured）

信息按层级组织，读者可以在任意深度停止阅读都能获得完整的当前层级信息。

- 文档分 3–8 章，每章有明确的单一主题

- 章内用「判断 → 证据 → 细节」三层结构，逐层展开

- 能用列表就不用段落，能用表格就不用列表

- 关键信息用加粗标出来，但每段不超过 3 处加粗（密集加粗 = 没有重点）

### 4\. 克制的组件使用

飞书文档组件丰富，但克制使用才能突出重点。

- **callout**：只用于开篇摘要、重要提醒、风险提示，不滥用

- **grid**：用于并列展示 2–3 个核心指标或对比项，里面不放表格

- **table**：≤7 列，行列含义清晰；表头必须有单位说明

- **mermaid 图**：只在确实有流程/结构/关系需要可视化时用，一幅图只讲一件事

- **图片**：必须有图注说明图的内容和结论，不放"裸图"

## 文档类型与结构模板

### 分析报告类

适用场景：bug 分析、性能分析、竞品分析、方案评估

1. **执行摘要**（callout）：核心结论 \+ 关键数字 \+ 建议动作（1 段）

2. **背景与问题定义**：为什么要做这件事、问题是什么、影响范围（≤2 段）

3. **分析方法**：用了什么方法、数据来源、假设前提

4. **核心发现**：按重要性排序，每条一个子标题，先结论后证据

5. **横向对比**（如有）：多方案/多模型对比表

6. **结论与建议**：明确给出推荐方案和理由

7. **附录**：原始数据、详细日志、补充图表

### 技术方案类

适用场景：架构设计、技术选型、实施方案

1. **背景与目标**：为什么做、做成什么样算完（完成标准可验证）

2. **方案总览**：一张架构图 \+ 一句话概括

3. **核心设计**：分模块详述，每个模块「是什么 \+ 为什么这么设计 \+ 备选方案为什么不选」

4. **实施计划**：分阶段表格（阶段、交付物、时间、风险）

5. **风险与应对**：已知风险和 mitigation

6. **附录**：详细设计、接口定义、数据字典

### 进展总结类

适用场景：周报、项目进展、阶段复盘

1. **本期核心结论**：3–5 条要点，每条一句话

2. **已完成事项**：按重要性排序，带数据

3. **进行中事项**：当前状态、卡点、预计完成时间

4. **下一步计划**：下期重点、优先级排序

5. **风险与求助**：需要协调的资源或决策

## 写作流程

### 第一步：取证（先拿素材，再动笔）

- 已有具体 URL → fetch 读全文

- 目标在某个站点/账号内部 → 浏览器实地查看

- 泛主题检索 → web\_search / drive \+search

- 关键素材全部落盘验证，不靠记忆

### 第二步：搭骨架（先定结构，再填内容）

1. 确定文档类型（分析报告/技术方案/进展总结）

2. 列出 3–8 个章节标题，每个标题是一个判断或结论

3. 每章定 2–5 个要点，每个要点标注证据来源

4. 确定需要的飞书组件（表格/图/callout/grid）

### 第三步：写正文（结论先行，证据跟上）

- 从最重要的章节开始写，不一定按顺序

- 每段第一句写结论，后面补证据和推理

- 数字和引用当场标注来源，不最后补

- 写完一章就自查：结论是否明确、证据是否充分、结构是否清晰

### 第四步：配图与排版

- 需要的图（mermaid/截图/示意图）在对应位置插入

- 表格数据核对一遍，确保和正文数字一致

- callout/grid 等组件只放在真正需要突出的地方

- 检查层级：标题层级是否正确、列表缩进是否一致

### 第五步：终审

1. **结论先行检查**：每章首句、每段首句是否是结论

2. **证据完整性检查**：每个判断是否有支撑、数字是否有出处

3. **结构一致性检查**：章节逻辑是否顺畅、层级是否混乱

4. **组件克制检查**：有没有滥用 callout、加粗、表格

5. **时效性检查**：数据是否是最新的、有没有过时的信息

## 飞书文档操作最佳实践

### 新建文档

- 优先用 `docs +create` \+ Markdown 格式批量导入内容

- 标题简洁明确，包含核心关键词和日期（如「X 性能分析报告 2026\-11\-10」）

- 创建后立即确认 URL 和访问权限

### 更新已有文档

- 先读当前版本作为基线，只改真正需要变动的部分

- 优先用局部更新（`str_replace` / `block_insert_after` / `block_replace`）

- 整篇 overwrite 会丢失评论和图片，仅在确需整篇换稿时使用

- 更新后回读改动范围确认落地

### 图片处理

- 图片必须先上传为飞书素材 token，不能直接写 URL

- 每张图必须有图注，说明图的内容和核心结论

- 图片宽度统一，高度按比例

- 需要精确位置的图片，用 `media-insert` \+ `block_move_after` 组合

### 评论协作

- 文档评论用 bot 身份发布，不冒充用户

- 评论只写要问/要说的那一点，不复述过程

- 局部评论先定位 block\_id，不用文本片段定位

## 常见坑与避坑指南

### 内容类

- **AI 腔过重**：去掉「综上所述、值得注意的是、全方位、多层次」这类连接词和修饰词

- **数据无出处**：每个数字必须能追溯到来源，答不出来就留空

- **结论模糊**：「有所提升、效果不错」这种话不算结论，要写具体提升了多少

- **逻辑跳跃**：因果关系用「因为、所以、因此、但」显式带出来，不靠读者猜

### 格式类

- **表格列太多**：超过 7 列就拆成多张表或转成列表

- **加粗泛滥**：每段 1–3 处就够了，全加粗等于没加粗

- **标题层级混乱**：H1 只有一个（文档标题），H2 是章节，H3 是子章节

- **列表不平行**：同一级列表的语法结构要一致（都是动词开头、或都是名词短语）

### 操作类

- **直接覆盖整篇**：会丢失评论、图片 token，优先局部更新

- **图片用 URL**：飞书文档的 img src 只认素材 token，不认 URL

- **路径写绝对路径**：lark\-cli 的本地文件参数一律写相对路径

## 适用 / 不适用

- **适用**：技术分析报告、方案设计文档、项目进展总结、bug 排查笔记、数据对比评估

- **不适用**：营销文案、正式公文、文学创作、纯数据录入、即时聊天消息
