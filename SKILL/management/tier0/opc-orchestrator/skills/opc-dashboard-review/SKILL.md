# 经营复盘

## 目标

帮助用户判断当前最真实的瓶颈是什么，并确认下一周期应该优先解决哪个问题。

## 核心原则

- 默认读写当前工作目录下的 `opc-doc/`
- 教学模式下先解释复盘不是流水账，而是找瓶颈
- 默认一次只问一个问题；如果几个问题都很轻、彼此紧密相关，可以合并成 2 到 3 个
- 默认给 3 个瓶颈假设或优先重点，并附加 `4. 我有自己的方案`
- 用户确认后再写入正式结果
- 不直接给推荐结论，只做方案分析

## 本步骤必须完成什么

1. 当前经营状态摘要
2. 主要瓶颈识别
3. 下周期优先重点确认

## 优先确认顺序

1. 最近最卡的地方
2. 最可能的瓶颈类型
3. 下一周期优先修正哪一点

## 完成标准

- 已形成 3 个瓶颈假设或优先重点
- 用户已确认当前最真实的瓶颈

## 本步需要解释什么

教学模式下先解释：

- 复盘看的是需求、转化、资产和风险
- 目标不是证明自己努力了，而是找出最值得修正的一点
- 这一步会决定下一周期的唯一重点

## 触发条件

**本技能不是建盘期的线性下一步，而是运营循环中的周期性工具。**

触发时机（满足其一即可）：
- 运营一段时间后感到卡顿，不知道问题出在哪
- 想做一次有结构的回顾，而不是凭感觉继续做
- 转化、留存或成交出现明显下滑
- 用户自主选择做一次复盘

**前置条件检查**：如果用户刚完成建盘期还没开始执行，不进入本技能——复盘需要有实际运营数据，哪怕是轻量的。

## 输入

优先读取：

- `opc-doc/outputs/**`（所有建盘期产物，用于对照）
- `opc-doc/reviews/dashboard.json`（历史复盘记录，如果存在）
- `opc-doc/outputs/09-dashboard-review/`（本周期前几次复盘，如果有）

如果 `opc-doc/` 不存在或数据不足，先看当前对话中是否已有足够经营信息。

- 如果用户完全没有运营过，不做假复盘，提醒先去执行再来复盘

## 执行步骤

1. 解释本步目标
2. 默认一次只问一个问题；如果几个问题都很轻、彼此紧密相关，可以合并成 2 到 3 个，例如：
   - 你最近最卡的一步是什么？
   - 你是没人来、没人买，还是做完不复用？
3. 每轮回答后，给简短反馈
4. 生成 3 个瓶颈判断，例如：
   - 需求验证不足
   - 转化路径不顺
   - 资产沉淀太弱
5. 说明每个判断的适用情况、依据和代价
6. 默认增加 `4. 我有自己的方案`
7. 让用户确认、组合、修改，或直接提出自己的版本
8. 用户确认后，再写入正式复盘结果

## 输出

对话层必须包含：

1. 本步解释
2. 当前经营状态摘要
3. 3 个瓶颈判断 + `4. 我有自己的方案`
4. 每个判断的适用情况、依据和代价
5. 请用户确认或修改

## 落盘检查点（每次触发后必须完成）

用户明确确认本周期核心瓶颈和下一重点后，**立即**使用 Write 工具写入文件。在对话中描述结论不等于落盘。

**本技能支持多次触发。每次落盘使用带日期的文件名，不覆盖历史记录。**

**写入文件（使用当天日期，格式 YYYYMMDD）：**

- `opc-doc/outputs/09-dashboard-review/review-[YYYYMMDD].md`（经营状态摘要 + 瓶颈判断 + 下周期唯一优先重点）
- `opc-doc/reviews/dashboard.json`（结构化复盘数据，**追加写入**，保留历史，不覆盖）

**更新状态文件：**

- `opc-doc/state/current-stage.json`（写入：`{"stage": "09-dashboard-review", "status": "completed", "next_stage": "execution-or-回退阶段", "summary": "一句话核心瓶颈和下一重点"}`）
- `opc-doc/state/decisions.json`（追加下周期唯一优先重点，注明日期）

**落盘完成后，在对话中告知用户：**
> "✅ 本次复盘已保存。根据复盘结论：[简短说明下一步是继续执行、回退某阶段，还是触发资产沉淀]"

## 何时调用其他 skills

- 如果复盘发现前置阶段缺口，明确建议回退到对应 skill
- 不要在没有依据时让用户重复整个流程

## 异常处理

- 如果数据不完整，只做轻量定性复盘，不装作有完整结论
- 不要同时给多个下一步重点，保持单一优先级

## 产出物模板与初始化脚本

本 skill 自带 `templates/` 与 `scripts/`，**不依赖其它 skill 的文件**也能独立运行：
模板给出产出物的完整骨架，脚本负责建目录与写骨架文件（已存在的文件不会被覆盖，可重复执行）。

```bash
# 建到当前目录下的 opc-doc/
python scripts/init_stage.py

# 或指定位置
python scripts/init_stage.py D:/work/opc-doc
```

初始化只是把骨架摆好，**内容必须由对话确认后填写**。落盘完成才允许进入下一阶段。

## 质量自检（落盘前逐条过）

| 检查项 | 通过标准 |
|---|---|
| 数据对照 | 每项指标都有本期与上期对比，没有孤立数字 |
| 瓶颈唯一 | 最终只锁定一个主瓶颈，其余列为候补并说明排除理由 |
| 证据双向 | 每个候选瓶颈都写了支持与反对的证据 |
| 重点唯一 | 下周期只留一件事，且给了完成判据 |
| 有止损判断 | 明确回答止损条件是否已触发 |
| 不重做分析 | 没有回头重跑 01-07 的分析 |

一句话判据：**读完这份复盘，用户能不能立刻说出"下周我只做这一件事"，并且知道为什么不是别的。**

## 常见失败模式与纠偏

| 失败模式 | 表现 | 纠偏动作 |
|---|---|---|
| 罗列数据 | 列了 20 个指标，没有判读 | 每个指标后面补一句"这说明什么" |
| 瓶颈过多 | 同时认定 3 个瓶颈 | 只留证据最强的一个，其余进候补 |
| 归因情绪化 | "因为我不够努力" | 改成可观测的事实与环节 |
| 重点不可执行 | "加强运营" | 改成一件有完成判据的具体事 |
| 回避止损 | 数据明显不行仍说继续观察 | 对照止损规则明确给出结论 |

```text
瓶颈判断的排除顺序：
先看触达量够不够 → 再看承接转化 → 再看成交动作 → 最后才怀疑定位
前面环节没排除之前，不要下"定位错了"的结论。
```

## 阶段衔接契约

| 方向 | 内容 |
|---|---|
| 接收 | `opc-doc/outputs/**` 全部建盘期产物、`opc-doc/reviews/dashboard.json` 历史复盘 |
| 交付 | `review-<YYYYMMDD>.md`、`dashboard.json`（追加写入） |
| 下游 | 下周期执行；或按结论回退到某个具体阶段重做 |
| 不接收 | 没有实际运营数据就做复盘——纯推演的复盘没有信息量 |

复盘唯一的目的，是**把注意力从"很多事都要做"收敛到"下一步只做哪一件"**。
所以产出里最重要的不是数据表，而是最后那一条"下周期唯一重点"。如果这条写不出来，
说明瓶颈判断还没收敛，继续排除，不要往下走。

回退是合法结论：如果证据指向定位问题，就明确写"建议回退到 02 阶段重做"，而不是在本阶段硬修。

## 落盘自检

复盘文件按日期累积，写入前先确认没有覆盖历史：

```bash
ls -lt opc-doc/outputs/09-dashboard-review/ | head -5
head -30 "opc-doc/outputs/09-dashboard-review/review-$(date +%Y%m%d).md"
python -c "import json;d=json.load(open('opc-doc/reviews/dashboard.json'));print(len(d['reviews']))"
```

判据：本次 `review-<今天>.md` 存在；`dashboard.json` 里记录条数比上次多 1（追加成功，不是覆盖）；
`current-stage.json` 的 `summary` 能一句话说清"核心瓶颈 + 下一重点"。

`dashboard.json` 是唯一需要**追加写入**的状态文件：先读取现有内容，push 本次记录，再整体写回。
直接覆盖会让历史趋势断掉，而趋势正是判断瓶颈是否真的改善的唯一依据。


### 复盘频率

建议以周为单位做轻复盘、以月为单位做重复盘。周复盘只回答一个问题：本周唯一重点推进了吗；
月复盘才动瓶颈判断和止损结论。频率过高会让人反复改方向，频率过低则问题积压到无法收拾。

回退不是失败信号。只要证据充分，把结论写成"建议回退到某阶段重做"比在本阶段硬修更有价值；
真正浪费时间的，是在瓶颈判断还没收敛时就开始做新动作，让下一个周期继续跑偏。

复盘结论要能一句话说完，说不完就说明还没收敛。
写不出这一句时，回到瓶颈判断那张表，继续排除候选项，而不是先写下周期计划。
