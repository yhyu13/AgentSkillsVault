# 节级结构模板 (Structural Patterns)

iTech ZCode 一文的整体节序,可拆为 6 种节级结构,各自有固定模板。写新文时按题材选择 4-6 个节组装。

---

## 全文章序参考

```
1. 戏剧化开场 (1 段)                ← 指纹 1
2. 提纲 (6-7 条短标题,起结构作用)
3. 争议展开 (1-2 节,带 N 层递进)   ← 指纹 2 + 4 + 5
4. 官方/对手回应 (1 节)             ← 指纹 7 (立场标)
5. 工具/对象全解析 (3-5 节)         ← 指纹 6 (冒号双行标题)
6. 关键附属物/披露文档专章 (1 节)   ← 指纹 10 (诚实声明)
7. 选型判断 / 实务建议 (1 节)       ← 指纹 3 (公平论反转) + 7 (实务立场标)
8. 收尾三段                          ← 指纹 8
9. 参考链接 (1 段)
```

总字数 2500-4000 字,5-8 个指纹命中。

---

## 结构 1 · 戏剧化开场

**适用**:几乎所有争议/事件长文。

**模板**:
```markdown
<TITLE>

*<一句话钩子 + 服务承诺>*    ← 斜体副标题,8-20 字

<正文第 1 段,2-3 句>
- 第一句:用"瓜/这事/这场 X" 把题材人文化
- 第二句:给一个精确时间/数字锚点(例:"9 月 18 日,一个叫 X 的开发者发了...")
- 第三句:点出读者最关心的悬念(例:"... 客户端本身都解不开")

<正文第 2 段,2-3 句>
- 一句话总结事件影响
- 预告下面要讲的内容(用"这篇文章把... 一次讲清楚" 句式)

## 本文提纲

1. <争议始末:... >
2. <官方回应:... >
3. <工具全貌:... >
4. <关键披露:... >
5. <选型判断:... >
```

**禁忌**:
- 不要开篇"在这个 AI 飞速发展的时代..."
- 不要开篇"今天我们来聊聊..."
- 不要开篇"作为一名 XX,从我自己的观察来看..."
- 不要用引言/题图/视频

## 结构 2 · 争议展开(带 N 层递进)

**适用**:任何"我有证据,我把证据链交代清楚"的争议段。

**模板**:
```markdown
## <争议主题:一个精确的锐评>     ← 指纹 6 双行标题

先把事实链条理清楚,这件事有几层。

**第 N 层,<层面>。** <核心陈述句,带具体行为>
<2-3 个细节点,用项目符号列出>
- <细节 1,带数字>
- <细节 2,带数字>          ← 指纹 4 精确数字堆
- <细节 3,带数字>

<可选第 N+1 层,社区复测 / 独立验证>

<关键转折段>                 ← 指纹 3 公平论反转
平心而论,"<承认合理面>"。
问题不在 X,而在 <N 个具体条款>,这 N 点叠加,
性质就从 "<原属性>" 变成了 "<新属性>"。
```

**示例触发**:智谱 ZCode 偷传、某 SDK 隐私争议、某模型 benchmark 作弊、某工具定价突变。

---

## 结构 3 · 官方/对手回应

**适用**:任何"事件主体方有公开回应"的题材。

**模板**:
```markdown
## <回应方>:<回应关键词列表,3-4 项>

<日期>:<具体的回应行动 / 时间线>
<回应要点 1>
<回应要点 2>
<回应要点 3>

随后发生的事是:**<日期> <具体动作>。<可选细节>。
<短句补一句意义>。

开源/回应本身的意义,不只是"动作公开"。
更重要的是 <这次真正有价值的部分 — 引出下一节>。
```

**要点**:
- 用冒号双行标题把回应方和回应动作压缩进标题
- 时间锚定必须精确到日
- "随后发生的事" 用来引出下一节,不留硬切

---

## 结构 4 · 工具/对象全解析

**适用**:争议平息后给工具本身写 deep-dive / 给模型写全解析。

**模板**:
```markdown
## <工具定位:一句精确的"X 是什么">

<一句话定位,带类比>
<三形态表格(可选)>

| 形态 | 入口 | 说明 |
|------|------|------|
| Desktop | X | ... |
| Web | X | ... |
| CLI | X | ... |

<核心卖点 1,2-3 句>
<核心卖点 2,2-3 句>

### <功能模块 1:<锐评>>    ← 二级三级都用冒号双行
<3-5 句讲清是什么 / 怎么用 / 为什么特别>

### <功能模块 2:<锐评>>
<同上结构>

...
```

**要点**:
- 每个功能模块用 `### N · <模块名:<锐评>>` 标题
- 每个模块讲清"是什么 + 怎么用 + 为什么特别(差异化)"
- 不堆技术参数,堆使用场景

---

## 结构 5 · 关键附属物/披露文档专章

**适用**:争议工具开源后,单独讲那份"罕见透明披露"。

**模板**:
```markdown
## <文档名>:<"罕见/值得单独讲"的锐评>

这是我个人认为这次 <事件> 里最有价值的部分,值得单独讲。

<文档位置,1 句话>

<文档覆盖范围,1 句话 — 用"按业务场景列了一张大表,覆盖..." 句式>

<几个要点值得注意:>
- <要点 1,承认不足的具体细节>          ← 指纹 4 精确数字 / 指纹 10 诚实声明
- <要点 2,承认不足的具体细节>
- <要点 3,诚实声明 — "用户自配的 X 可能...">

<总结句>这份 <文档> 的价值在于:**它把"黑盒"变成了"可审计的白盒"**。
无论你信不信 X,你现在至少能基于 <源> 去核对,而不是靠猜。
这也正是 <事件意义> 的真正意义 — 不是 X 本身,而是 X 让
你第一次能真正审查这个工具做了什么。
```

**触发**:这类结构在事件型长文中出彩率最高,几乎必用。

## 结构 6 · 选型判断 / 实务建议

**适用**:任何"读者要带走行动建议"的结尾。

**模板**:
```markdown
## <该不该用 / 怎么办:选型判断>      ← 指纹 6 双行标题

几层实在的判断。

**<争议怎么看>?** <立场表态 — 指纹 7>
<事实回顾,1 段>
<但也要看到 — 指纹 7>: <积极面,1 段>
<关键在于,关键转折>

**<功能上值不值得用>?** <立场表态>
<如果读者画像是 A — 1 段>
<这个赛道里,X 和 Y 是同类竞品>

**<安全上 / 行动上怎么做>?** <实务立场标 — "给几条务实的建议">
- <建议 1:具体行动,带场景>
- <建议 2:具体行动,带场景>
- <建议 3:具体行动,带场景>
```

**要点**:
- 三个小问题用 `**` 加粗 + `?` 收尾
- 每问下先用立场标,再展开
- 实务建议条数 3-5 条,每条带场景

---

## 结构 7 · 收尾三段

**适用**:全文结尾。

**模板**:
```markdown
## <可选:单独小节 / 直接接上节末段>

<金句段>     ← 指纹 8
说到底,<题材> 给整个 <行业> 上了一课:**<中心论点金句>**。
<1 句支撑论证>。

<反问段>
<1 句反问读者 / 邀请互动>。

<实务小段 — 可选>
<若前文已经给实务,这里只重复一句最关键的>。
```

**关键**:
- 金句必须加粗,**且必须包含反直觉判断**(对比/反差/打破常识)
- 反问必须具体,不能"你怎么看"

---

## 模板组合示例(给 LLM 的"按需装配"指令)

写一篇 3000 字的"X 工具被曝数据争议 + 开源复盘"长文时:

```
必选结构: 1 (开场) + 2 (争议展开) + 3 (官方回应) + 6 (选型判断) + 7 (收尾)
按需结构: 4 (工具全解析 — 仅当争议工具本身有较多功能值得讲) + 5 (披露文档专章 — 仅当有 README/NOTICE/治理文档可单独成节)
建议字数: 1 (200) + 2 (800) + 3 (300) + 4 (1200,可选) + 5 (500,可选) + 6 (500) + 7 (200) ≈ 2500-3700 字
```
