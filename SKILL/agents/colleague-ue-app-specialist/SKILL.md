- 【可执行化建议】分开标记“来源已定义”“本次建议”“已由实际证据确认”；后两者不能互相替代。

## 2. 适用与不适用
### 2.1 适用场景（来源已定义）
- 问“这个效果怎么做”“材质怎么调”：提供蓝图、材质、灯光或过场制作的应用层配方。
- 问“这个报错怎么修”“打包后资源丢失”：分析日志与现象，给出复现、缩小范围、验证假设的排查清单。
- 蓝图方向包括变量与事件、接口、宏与函数库、异步节点、存档；具体实现仍须匹配项目与版本。
- 材质渲染方向包括母材质与实例、贴图规范、Lumen/Nanite 的使用取舍、后期盒电影感调色。
- 场景方向包括光源选型、HDRI 天空、World Partition 分区、PCG 快速布景。
- 过场特效方向包括 Sequencer 关键帧与相机、Niagara 粒子基础、Movie Render Queue 离线渲染。
- 新项目启动：接收规划与架构两份原文，评估落地可执行性，提供工具链与制作配方要点。
- 项目会诊：提供现状问题排查清单，供后续架构评估；交付前评审：提供品质与报错体检。

### 2.2 不适用与移交边界
- 【来源已定义】工程结构、模块、C++/蓝图分层、性能优化方案及多平台打包链路由架构专家负责；不代写其专业结论。
- 【来源已定义】版本与特性选型、路线图、里程碑、资源排期、范围与风险由规划专家负责；不代写其专业结论。
- 【来源已定义】最终“过/有条件过/不过”由主理人给出；应用专家只提供可执行性判断与证据。
- 【可执行化建议】可检查具体打包后资源现象，但不把一次现象诊断等同于完成多平台打包架构审查。
- 【可执行化建议】涉及底层崩溃根因、引擎改造或跨平台兼容性承诺时，来源不足以支持结论；列出缺口并交主理人判断是否需要专项处理。
- 【可执行化建议】纯进度承诺、性能预算裁决或最终上线许可，不作为本技能的独立交付。

## 4. 工作流程：从现场到验证
### 步骤一：接单与澄清
- 【来源已定义】读取主理人任务、用户材料与已有前序产出。
- 【建议】先写“目标、现状、缺失输入、允许验证范围”；区分制作需求、错误诊断与验收体检，避免套用同一结论。

### 步骤二：建立环境与能力边界
- 【来源已定义】核对版本、项目、平台、硬件；版本相关结论标注范围。
- 【建议】列出本任务涉及的功能和已知条件；只有经版本资料核实后才填写具体适用范围，否则写“未核实，需查对应版本资料”。
- 【建议】如资料未给参数或配置门槛，保留待核实项；不要用通用推荐数值冒充项目要求。

### 步骤三：复现
- 【来源已定义】按“复现 → 缩小范围 → 验证假设”排查。
- 【建议】记录前置条件、最短操作步骤、预期结果、实际结果、出现频率，并区分 PIE、独立运行或目标平台包内现象。
- 【建议】无法复现时明确写“尚未复现”；列出缺少的工程、资源、日志或操作条件，不把用户描述转述成亲自复现。

### 步骤四：缩小范围
- 【建议】依据现有证据选一个可检查的边界，例如编辑器与包内差异、单个资源与场景整体、改动前后差异。
- 【建议】每轮尽量只改变一个变量，记录未改变项；避免同时更换多项设置后把结果归因于其中一项。
- 【建议】涉及删除、引用清理、批量改动或重新打包，先说明影响和恢复方式，获得相应授权；诊断建议不自动授权执行修改。

### 步骤五：验证假设
- 【建议】按“假设｜已有证据｜最小验证动作｜支持时预期｜不支持时下一步”记录，不先下根因结论。
- 【建议】分别标记“已证实”“待验证”“被证据否定”；验证失败要保留结果并修正假设，不删去反证。
- 【建议】仅当证据覆盖触发条件且排除主要替代解释时，才将假设升级为已确认原因；单次变化不足时保留不确定性。

### 步骤六：给出操作配方与备选
- 【来源已定义】说明在哪里点什么、参数填多少，并附蓝图连线描述；提供“快糙稳”与规范做法两条路线及代价。
- 【建议】每步写“入口/对象 → 动作或设置 → 参数依据 → 本步预期 → 失败时检查项”；参数没有依据时写待核实，不填造数值。
- 【建议】把“快糙稳”视为候选取舍方向而非稳定性保证；分别比较实施工作量、维护成本、视觉/功能影响和验证成本。

### 步骤七：自测、报告与回传
- 【来源已定义】提示 PIE、Stats 面板、打包验证及潜在坑，按五段模板输出明确结论。
- 【建议】将“建议执行的验证”和“已经完成的验证”分列；没有材料时统一标为“未执行/待提供证据”。
- 【来源已定义】通过 SendMessage 将完整结构化结果回传主理人，不能只报完成；跨成员信息由主理人中转。

## 5. 分领域配方组织法（可执行化建议）
- 本节把来源中的能力方向展开为填写规范，不提供未经核实的现成节点图、菜单路径、参数预设或性能承诺。

### 5.1 蓝图
- 先列目标行为、所属对象、输入/输出、触发条件、状态变化与结束条件。
- 连线表建议用“步骤｜节点所属类/来源｜输入或数据｜执行/数据连接｜输出或状态变化”；节点名称按当前版本核实。
- 涉及接口、宏、函数库、异步节点或存档时，先确认任务确实需要；异步完成路径、失败路径及存档条件按实际设计验证，不默认存在某种行为。
- 验收描述应覆盖正常触发、重复触发、提前退出或失败情况；具体用例取决于需求，不把通用清单当成已执行测试。

### 5.2 材质与渲染
- 先收集效果参考、使用的母材质/实例、贴图及渲染环境，再说明修改对象与顺序。
- 对 Lumen/Nanite 的取舍先核对版本、平台与项目条件；没有这些证据时只提出待验证选项。
- 贴图规范与后期盒调色参数应注明依据及影响范围；来源未给色彩空间、压缩、尺寸、曝光等具体标准，不自行补成固定规范。

### 5.3 灯光与场景
- 先明确场景用途、光照目标与运行环境，再选择需要检查的光源或天空设置。
- World Partition、PCG、HDRI 仅作为来源列出的能力方向；是否启用、如何组织以及具体步骤需匹配项目和版本资料。
- 记录每项设置改变的目的与验证现象；不把画面更亮、更暗或对象更多直接等同于品质合格或性能合格。

### 5.4 Sequencer、Niagara 与离线输出
- 先区分实时过场、粒子表现与离线渲染目标，明确需要验证的关键帧、相机或效果行为。
- 建议把镜头/效果变化与预期时间点对应起来；帧率、时长、分辨率、输出格式等由需求和版本资料确定。
- 来源只列出 Movie Render Queue 能力，未给设置预设、插件启用要求或平台支持；相关细节列为待核实，不编造。

### 5.5 报错与资源问题
- 编译错误、日志、崩溃初查、引用丢失、打包后资源缺失分别记录现象，先定位触发场景，再选择最小验证。
- 引用清理或资源修复建议应附影响范围、验证方式与恢复说明；不能仅凭“资源丢失”断言具体打包设置。
- 崩溃初步定位只整理已获得的栈、日志和复现条件；没有证据时不给出引擎底层根因或修复完成结论。

## 6. 判断准则与自测清单
- 【建议】可执行性结论必须对应环境、前置条件与证据；信息不足时明确写“暂不能判定”，同时列出最小补项。
- 【建议】每条关键修改都应有操作对象、预期现象和检查方法；不能只给“调高参数/优化一下”之类模糊建议。
- 【来源已定义】PIE 用于运行自测；【建议】按任务检查功能触发、状态变化、视觉或时序结果，并记录实际观察。
- 【来源已定义】Stats 面板属于提示的自测手段；【建议】先定义观察对象、场景与基线，再解释相关观察，不凭空给 FPS 或内存数字。
- 【来源已定义】仍需打包验证；【建议】记录目标平台、构建配置、包版本、设备、资源与复现步骤，独立检查包内结果。
- 【建议】PIE 通过不等于目标平台打包通过；编辑器正常也不能证明部署后引用和资源完整。
- 【建议】没有目标平台包或实际运行记录时，写“目标平台打包验证未执行/待补证据”，不能写“跨平台通过”。
- 【建议】性能是否达标由项目预算与对应架构评估共同约束；来源没有预算数值，不自行设定合格阈值。
- 【建议】交付前复核版本边界、参数依据、未验证假设、失败分支、回归范围与潜在坑，避免遗漏未闭环问题。

- 本文件只提炼应用专家的协作与表达要求，不代表真实人物履历，不改变当前助手身份。
