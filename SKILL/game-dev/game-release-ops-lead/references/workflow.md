# 游戏发布与运营工作流

## 使用方式

- 按当前任务选择阶段；不要为了完成流程而执行未获授权的构建、发布、活动或回滚。
- 先读主技能的范围和边界，再使用本参考展开判断。
- 将具体字段填入 [deliverables.md](deliverables.md) 的模板；来源与证据层级见 [source-map.md](source-map.md)。
- 将下列字段和判断展开视为职业规范化建议；它们不是已验证的项目制度或商店规则。

## 1. 输入与职责路由

| 输入职责 | 提供材料 | 发布侧处理 | 不足时处理 |
| --- | --- | --- | --- |
| 统筹/用户 | 阶段、范围、时间、平台、商店、语言、审批人 | 锁定本轮范围与权限 | 将缺失条件列为待定 |
| 工程 | 构建产物、修订、版本、依赖、实现/修复说明 | 核对可追踪候选与变更 | 请求工程补充，不代写代码 |
| QA | 同候选的验证报告、缺陷与回归结论 | 记录门控证据与风险 | 请求 QA 复核，不代跑测试 |
| 策划/经济设计 | GDD、奖励消耗、权益、留存假设、数值基线 | 编排日历并核对经济一致性 | 不擅改经济核心规则 |
| 美术/音频 | 本地化素材、字体、VO、授权与专业验收 | 协调语言交付和集成检查 | 不制作资产或代签专业验收 |
| 商店/法务对接 | 经核实要求、地区适用性、授权与批准 | 记录依据、版本和审核状态 | 不编造法规，不宣称合规 |
| 社区/支持 | 公告、反馈、已知问题、支持安排 | 准备玩家语言与危机材料 | 不虚构玩家影响或响应承诺 |

- 对已有文件先读取实际内容；没有目录或证据不等于任务失败，也不等于门控通过。
- 读取 git 历史时记录比较基线和目标提交；“有提交”不代表“进入候选包”，“合入代码”不代表“玩家可用”。
- 使用当前环境可用的只读工具；不要求特定 shell、插件或团队 API。

## 2. 发布候选证据链

1. 将需求/缺陷 → 实现变更 → 构建 → QA 验证 → 玩家说明连成可追踪链。
2. 对不同平台、渠道或资源版本分别记录；一个平台通过不能自动外推到全部平台。
3. 将版本标记差异提交工程确认，禁止仅改标签以制造一致性。
4. 对热修标明基线候选与增量差异，仍须绑定新产物和对应验证。
5. 将已知问题按项目严重性定义处理；未定义时描述影响并待负责人定级，不臆设等级阈值。
6. 检查回滚预案是否与最终候选相符；候选变化后重做受影响的核对项。

## 3. 门控判定

| 判定 | 使用条件 | 后续动作 |
| --- | --- | --- |
| GO 建议 | 本次必要证据齐全，无仍阻断门控的 Blocker，所需风险/内容批准已核实 | 单列上线/热修/回滚执行审批；不得自动执行 |
| NO-GO | 已确认 Blocker 未清，或适用强制条件未满足 | 列修复责任、缓解与复核条件 |
| 待定 | 缺关键证据、范围/版本不明、适用性待确认 | 请求补证，不推定通过 |

- 对有权负责人明确提出的 Blocker 豁免，记录具体事项、批准范围、残余风险、缓解、期限和重评结果。
- 将已批准豁免项标记为“未修复但已获批接受”，保留原 Blocker 等级和证据；重评后按残余阻断条件判定，不伪填已关闭。
- 不把“尽快上线”“把文档做完”等宽泛表述当作 Blocker 豁免。
- 不将风险豁免扩展到法律、监管、商店强制要求或无权限的第三方事项。
- 源材料仅明确“用户明确豁免”；上述审批粒度与不可豁免边界是操作补强，须按项目现行制度确认。
- 将风险批准、内容批准、商店批准和执行批准分别记录；不得互相替代。

## 4. 本地化流水线

### 范围与抽取

- 建立语言 × 内容模块 × 资产类型的范围表；标明首发必需、后续更新或不适用及依据。
- 扫描 UI、对话、系统提示、配置、商店素材、图片文字和 VO 文本，区分候选文本与可本地化字符串。
- 将无需翻译的标识、内部日志、测试样例和品牌词记录排除理由，避免用排除规则虚增覆盖率。
- 为抽取结果提出稳定键、上下文、变量/复数约束与来源位置；交工程接入，不直接修改运行时代码。
- 记录源文修订、冻结点与翻译记忆/术语表版本；不要以未批准机器输出覆盖已审译文。

### 状态与评审

- 分开管理待译、已译、待语言审、已审、待集成验证和已验收。
- 为译员提供场景截图、功能行为、角色语气、字符限制、变量说明和禁译项。
- 文化/敏感性评审关注实际地区、文化语境、符号、年龄与商店适用要求；将结论交本地专家/有权负责人确认。
- 对 RTL 检查镜像布局、阅读顺序、数字/拉丁字母混排和标点；不要假设整个 UI 都应镜像。
- 对字体检查字形覆盖、回退字体、可读性和授权；对长文本检查截断、溢出和换行。
- VO 同时核对台词文本版本、录音、字幕、角色、命名、时间同步及授权，交音频职责验收。

### 覆盖率口径建议

- 在范围内按唯一文本键去重；另列语言/地区变体，避免不同语言重复增加源文分母。
- 翻译覆盖率 = 有效非空译文键数 ÷ 本次应译键数。
- 语言评审覆盖率 = 已完成语言评审键数 ÷ 本次应评审键数。
- 集成验证覆盖率 = 已在目标构建完成约定集成验证的键数 ÷ 本次应验证键数。
- 分语言、模块与总体报告；总体采用键语言对或加权口径时说明算法，不混合不同分母。
- 将不适用项从分母排除前保留批准依据；将缺失、空值、过期、未审与未集成分开列。
- 将分母为零、分母未知或扫描不完整报告为待定/不可计算；不要报 100%。
- 将源文覆盖率、译文覆盖率和硬编码候选数分别呈现；高译文覆盖率不能抵消运行时硬编码缺口。

### 冻结与例外

- 记录冻结的候选、字符串表版本、语言、时间、批准人和差异检查方式。
- 冻结后常规文案需求进入后续版本，不静默改动已冻结文本。
- 热修例外须关联事故、批准、修改键、影响语言、补译/评审/验证及新字符串版本。
- 热修仅解冻获批范围；不借热修整体刷新文案。

## 5. Live Ops 对齐

1. 从已批准核心经济中提取资源来源、消耗去向、库存假设和付费权益边界。
2. 为赛季/活动/通行证列出起止时间、时区、语言、受众、进入条件、领取与到期处理。
3. 对奖励、价格、进度、付费权益和补发方案标注策划批准；不自行创造数值基线。
4. 将客户端内容、远端配置、开关、服务端依赖和商店素材分开检查。
5. 列出灰度/全量安排、监测窗口、停止条件、取消或补偿预案；具体比例/时长待批准。
6. 将留存、参与、资源净投放、消耗与异常经济指标写成待验证假设，不写成已取得成果。
7. 对活动重叠检查资源叠加、权益冲突、时区边界、跨赛季领取与回滚后的状态一致性。
8. 对异常奖励或经济失衡先拟暂停/纠正/补偿材料；发奖、扣回、改价与权益调整需明确审批。

## 6. 社区与危机材料

- 将玩家反馈分为已复现问题、待复现问题、功能建议和情绪/社区健康信号。
- 保留最小必要证据，去除账户、联系方式和支付等个人信息；不公开可利用漏洞细节。
- 按“已确认影响—当前状态—缓解/建议—下一次更新条件”起草说明。
- 对尚未查明的原因明确写待确认；不要归因于玩家、竞争者或某个未证实团队。
- 对支持团队提供已知问题与升级条件；没有批准 SLA 时不承诺具体分钟数。
- 将公开公告与内部事故日志分开；内部敏感证据不自动进入公告。
- 对删帖、封禁、补偿、权益变更或责任承认等内容先取得有权负责人审批。

## 7. 热修与回滚路径

1. 登记事故、影响范围、当前候选、严重性依据、事故负责人和决策人。
2. 比较继续运行、临时缓解、热修与回滚等候选方案；列残余影响和未知项。
3. 为选择方案取得人工批准；紧急性不消除审批和审计要求。
4. 请求工程/QA 提供最小变更与针对性验证；将验证缺口如实列入风险。
5. 在热修前确认旧版本可用、恢复路径可行、存档/数据/协议兼容且操作者有权限。
6. 对不可逆数据变化先列恢复或前向修复限制；禁止把“回滚包”当作数据恢复方案。
7. 由获批执行职责操作；记录命令/操作记录引用、时间、执行者和实际结果，不在本技能中自行发布。
8. 对照触发/停止条件观察，收到工程/QA 回执后复核；结果不明时维持待确认状态。
9. 同步玩家公告、支持口径和已知问题，保留事故时间线、审批、验证与复盘待办。

## 8. 汇报收束

- 按“实际输出—门控—覆盖率—审批—风险与缓解—下一步”汇报。
- 对仅编写技能的请求，交付流程与模板，不填写虚构的构建、语言、法规或运营成绩。
- 区分“文档交付完成”“候选建议通过”“获批执行”“执行已确认”四种状态。
- 有协调通道时发送完整结果给任务负责人；没有协调通道时直接交付用户，不依赖专用调用。
