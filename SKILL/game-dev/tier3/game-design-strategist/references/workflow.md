# 工作流程与阶段门

## 依据与使用方式

将本文视为基于角色方法的**新增规范化模板**，不是原插件原文，也不代表任何真实项目的已验证流程。原文明确概念方法、系统依赖排序、GDD 八节、跨文档评审、缺失材料先问和用户决策权；参见 [来源映射](source-map.md)。

按当前任务进入相应阶段，不为简单评审重复整个项目。先确认输出授权；未得到授权时只在对话中给出草案和问题。将“就绪”限定为设计材料状态，不将其等同工程可运行或测试通过。

## 1. 接单与材料基线

1. 确认任务类别、阶段、目标、范围、平台、Output Path 与写入许可。
2. 读取可用概念、系统索引、相关 GDD、美术/可访问性要求和架构/控制材料，记录版本与缺失项。
3. 将信息分为已确认事实、设计假设、待审批选项和资料不足项，避免把新建议混入基线。
4. 只问会改变方案的关键缺项；将不影响当前交付的未知项登记后续负责人。

| 阶段门 | 必须能回答 | 缺项处理 |
|---|---|---|
| 范围清楚 | 此次交付什么、不交付什么？ | 请求缩小范围或确认目标 |
| 事实可追溯 | 哪些材料支持本方案？ | 指向具体文档与行号；没有则标未知 |
| 可写且可接收 | 写哪里、谁决策、谁接手？ | 先给草案，不擅自覆盖或派发 |

## 2. 概念与范围门

按“2–3 条支柱 → MDA → 玩家心理映射 → MVP/目标/愿景”推进。将动词优先法用在核心行为上，再说明这些行为为什么形成可持续循环。

- 为支柱提出可观察问题，而不是只写抽象形容词。
- 将自我决定论作为自主、胜任、关联的检查透镜，不替用户规定唯一动机。
- 将 Bartle 用作动机偏好讨论工具，允许混合偏好，不把标签当人格或真实玩家统计。
- 为核心循环列出进入、行动、结果、反馈、再次行动；指出循环中断与退出条件。
- 为 MVP 写清验证问题及不可再删的依赖，将扩展功能放到目标/愿景层。

**通过条件**：支柱与核心循环有对应关系，范围有明确取舍，待审批项已交用户拍板。体验效果尚未验证时保留“假设”状态。

## 3. 系统与 GDD 门

先拆解系统并排依赖，再逐节澄清与编写。

| 系统字段 | 填写要求 |
|---|---|
| 标识与目标 | 用唯一系统标识，说明支持哪条支柱 |
| 输入与输出 | 写数据/动作及生产者、消费者，不写未确认 API |
| 状态与规则 | 列进入、退出、失败、恢复和共享定义 |
| 前置依赖 | 引用系统版本或待确认项，不伪造就绪状态 |
| 工作顺序 | 标就绪、待澄清或阻塞，并写解除条件 |
| 责任边界 | 写需工程、美术、音频、质量保障确认的内容 |

对循环依赖先拆共享定义或列方案，不能靠文档排列顺序掩盖相互等待。对跨系统反馈链追踪到输入来源，避免同一资源或条件由多个权威位置定义。

逐系统依次确认八节：概述、机制、数据、公式、边缘情况、UI 接口、依赖、验收标准。缺资料时允许起草带明确未知项的结构，但不得宣称该 GDD 已实现就绪。

**通过条件**：八节完整，变量与单位一致，至少三类相关边缘情况可判定，阻塞项可见，待用户确认项已列出。

## 4. 专项设计门

按任务选择以下检查，不要求每个系统都附带整套关卡、经济或叙事。

| 专项 | 展开顺序 | 通过条件 |
|---|---|---|
| 关卡 | 目标 → 布局 → 遭遇 → 节奏 → 失败/重试 → 奖励 | 路径、状态与规则闭合，学习及节奏假设可观察 |
| 经济 | 来源 → 消耗 → 转化 → 储存/回收 → 进度 | 资源口径一致，可达性与收益风险可比较，参数有依据或明确待调 |
| 叙事 | 体验 → 世界规则 → 故事弧 → 角色/阵营 → 对话/条目 | 世界事实、角色认知和假设分离，分支与玩法状态不冲突 |
| UX | 流程 → 信息优先级 → 屏幕状态 → 输入/焦点 → 可访问性 | 每屏入口出口、错误恢复和交接规格清楚，不越界制作资产 |

用设计推演发现风险，将实测、样本与统计判断交质量保障职责。没有验证数据时，不将收益比较写成“已证明平衡”。

## 5. 一致性与红线评审门

1. 建立实体/变量索引，逐项比较跨 GDD 的名称、数值、单位、状态和引用版本。
2. 按玩家行动、状态、资源、信息四条链检查规则是否相互矛盾。
3. 分别检查主导策略、经济失衡、认知过载和支柱漂移；每条发现说明具体触发场景。
4. 将“文本已冲突”与“可能存在风险”分开；为后者列缺少的证据及建议验证方法。
5. 为每个问题给出位置、影响、候选修复、决策人和复核条件，避免泛泛评价。
6. 对架构/引擎存疑项经统筹职责与工程确认；对视觉、音频和测试证据请求相应职责确认。

**通过条件**：影响本次范围的已确认冲突已修复或得到用户对保留问题的明确决策；未验证风险保留状态，不能包装成通过。

## 6. 交付、审批与变更

- 使用 [交付骨架与验收](deliverables.md) 组织文件，先列摘要，再列决策、风险和下一步。
- 将“文档完整”“设计评审通过”“实现验收通过”分开报告；本职责只陈述可证实的状态。
- 通过当前宿主的沟通通道回传，不依赖原团队 Agent ID、固定工具或插件安装目录。
- 在用户批准前保留候选状态；批准后记录影响范围、修改位置、旧新规则及待同步 GDD。
- 更新后复查引用、变量、单位、依赖与验收标准；不要只改一处造成新冲突。
