# 阶段工作流

用于阶段诊断、依赖排序和门控组织。本文件保留原规范的阶段方法，并将执行状态记录规范化。
原文证据与本次整理范围见 [来源映射](source-map.md)。

## 1. 编号与进入原则

- 原始编号为 Phase 0-8，共九个流程节点。
- 实际游戏开发七阶段为 Phase 1-7：概念、系统设计、技术搭建、预制作、制作、打磨、发布。
- Phase 0 是进入开发前的诊断，Phase 8 是汇编交付；不要称其为九个开发阶段。
- 从现有项目所处阶段进入；不要强迫用户从头重跑。

## 2. 诊断记录

先检查已有 `design/gdd/`、`docs/architecture/`、`production/epics/`、`src/`、`tests/`。
记录已找到的产物、内容缺口、评审状态和下一步依赖；没有读到的内容不能记为已验证。

向用户确认：

1. 引擎选型。
2. 目标平台。
3. 评审强度 `full / lean / solo`。
4. 本次任务从哪个阶段进入，以及哪些已有决策继续沿用。

三种强度只有名称证据，具体参与职责、评审数量和通过规则均待项目约定。
不要将 full 默认解释为所有阶段全量重审，也不要将 solo 解释为免评审。

## 3. 各阶段交接表

### Phase 0：阶段诊断

- 承接：统筹职责，串行。
- 输入：用户目标、当前项目产物和已确认约束。
- 输出：当前阶段判断、缺口、引擎/平台/评审强度确认记录。
- 完成条件：确认进入位置；不把文件存在视为质量门通过。

### Phase 1：概念孵化

- 策划与叙事职责使用 MDA、动词优先法、玩家心理学。
- 策划产物：概念文档，含支柱、MDA 分析、范围分层与视觉锚点。
- 美术与视觉职责产物：围绕视觉锚点的美术圣经，采用视觉身份九节。
- 原文安排为可并行，但美术仍依赖视觉锚点。
- 执行时先交接已确认锚点；可先做不依赖锚点的探索，不能跳过输入依赖。
- 九节的具体目录由美术职责与项目约定，本技能不补造。

### Phase 2：系统设计

- 前置：Phase 1 已确认的概念与相关输入。
- 承接：策划与叙事职责，串行推进。
- 顺序：系统拆解与依赖排序 → 逐系统 GDD → 跨 GDD 一致性与设计理论评审。
- 产物：系统清单与依赖顺序、每系统八节 GDD、专业评审结论。
- 八节的具体目录由策划职责与项目约定，统筹只核对交接完整性。

### Phase 3：技术搭建

- 工程与引擎职责：主架构、至少三条基础层 ADR、架构评审、控制清单。
- 美术与视觉职责：可访问性分级与特性矩阵。
- 分级名称：`Basic / Standard / Comprehensive`。
- 原文安排为可并行；具体分级判定、控制清单内容及架构细则由专业职责确定。
- 统筹收取两类专业结论，不自行批准技术方案或定义可访问性达标标准。

### Phase 4：预制作

- 策划职责：UX 规格。
- 美术职责：资产规格。
- 工程职责：Epic/Story 拆分、测试框架脚手架。
- 对无阻塞依赖的三项工作可并行分派。
- 统筹汇编：首个冲刺计划。
- 可选：组织垂直切片验证，由专业职责判断核心循环是否好玩；不把可选项默认为已承诺范围。

### Phase 5：制作

按每个冲刺保持下列顺序：

1. 工程实现就绪 Story。
2. QA 制定 QA 计划并执行烟雾测试。
3. 策划做设计评审与范围检查。
4. 统筹收尾并回顾。

- 收取实际实现、测试证据与范围判断，不将计划中的测试算作执行结果。
- 对未就绪 Story 明确其依赖；不要仅凭编号推定实现就绪。
- 每冲刺的回顾由统筹汇总，具体排期与验收规则待项目约定。

### Phase 6：打磨

可并行的专业工作：

| 能力域 | 原规范工作 |
| --- | --- |
| 质量保障 | 至少三轮 Playtest |
| 工程与引擎 | 性能剖析与优化 |
| 美术与视觉 | 资产审计 |
| 音频与声效 | 音频打磨 |

- 保留至少三轮 Playtest 的数量要求。
- 每轮样本、环境、观察方法与通过规则待 QA 和项目补充，不自行编造。
- 统筹核对轮次、证据与未决问题；不能以计划轮数代替真实执行。

### Phase 7：发布

按顺序处理：

1. 发布与运营职责输出发布清单、补丁说明、上线清单、本地化覆盖。
2. QA 完成最终建议性质量门（advisory），提交三态判定、证据、风险与残余问题，不自动批准发布。
3. 统筹汇总 QA 质量建议与发布材料，分别记录 QA advisory 质量结论、用户或经授权发布负责人的人工放行签字（确认放行及风险接受），以及针对本次具体发布执行的明确审批（确认部署指令）。

- 区分材料准备、QA advisory 质量结论、人工放行签字、具体发布执行审批与实际发布；各项不能互相替代。
- QA 质量结论不构成自动放行授权；人工放行及风险接受签字不等于实际部署指令，未取得针对本次发布的明确执行审批，不执行发布。
- 版本号、变更日志、构建、回滚、热修等专项工作交给发布运营职责。

### Phase 8：汇编交付

- 收齐当前阶段应有的专业交接。
- 核对跨职责一致性、产物路径、版本及未决事项。
- 汇编概念文档、GDD、架构、UX 规格、冲刺计划、测试报告、发布清单等已有材料。
- 向用户交付实际路径及“已知风险与缓解”。
- 将缺失产物或未执行验证明确标出，不用“已汇编”掩盖证据缺口。

## 4. 阶段切换检查

1. 核对上一阶段必需产物与依赖是否已交付。
2. 由对应专业职责给出评审结论，记录 `PASS / CONCERNS / FAIL`。
3. 对 `CONCERNS / FAIL` 先安排解决；若用户明确豁免，记录范围与决定。
4. 核对下一阶段输入与承接能力，再推进。
5. 附已知风险、缓解、责任归属和待补证据。

- 保留三态原始含义，不擅自添加数值阈值或严重度分级。
- 门控细则尚未约定时，将其作为待澄清项交给用户和专业职责。
- 豁免不能把失败结果改成通过，也不能替代高影响动作的独立审批。

## 5. 可移植执行

- 将“并行”视为依赖关系允许的调度安排，不视为必须存在的运行工具。
- 有实际多角色能力时，分别分派并收取交接。
- 无此能力时，交给具备相应能力的执行者或请用户安排；必要时顺序推进。
- 缺少专业承接时报告阻塞，不声称专业工作已完成。
- 使用当前环境的职责交接协议；不要调用或假定固定插件的成员名称与消息接口。
