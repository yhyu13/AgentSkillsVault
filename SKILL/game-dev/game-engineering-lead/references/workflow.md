# 工程工作流程

将本流程用于真实技术任务，按任务类型选择路径；模板中的字段是待填写项，不是完成证明。

## 1. 接单检查

- [ ] 记录任务阶段、范围、Story/需求路径、输出路径与授权动作。
- [ ] 核对 GDD 与系统索引、架构/ADR、引擎版本参考及项目配置。
- [ ] 确认目标平台、设备、联网形态和运行环境；未提供的项标“待确认”。
- [ ] 查看现有代码与测试入口，优先复用；不默认仓库是 npm 或特定引擎。
- [ ] 列出阻塞输入、可继续的只读工作和需要用户决策的事项。

遇到缺失文件时只读取项目实际存在的资料，不要求扫描无关目录，不把模板路径视为必须存在的文件。

## 2. 需求到架构

1. 从 GDD 提取行为、约束、平台需求与可观察结果，建立需求 ID 清单。
2. 将需求映射到基础/核心/玩法层，为每个模块写明职责、输入、输出和允许依赖。
3. 将跨系统契约、生命周期和高风险边界列为架构评审重点。
4. 在基础层至少落实三条 ADR；选题可为引擎/平台、资源生命周期、数据与存档基础。
5. 为每项决定比较备选，写出代价、后果、回退条件和验证方法。
6. 输出一页控制清单，把原则变成路径内的具体行为规则。

不要把“使用某引擎”“保持可维护”等结论当成完整 ADR；至少说明项目为何需要该决定，以及替代方案为什么不合适。

## 3. 架构评审与实现就绪

- [ ] 核对每个已纳入范围的 GDD 需求 ID 都有模块或待决项承接。
- [ ] 核对循环依赖、权威状态归属、跨线程边界和生命周期责任。
- [ ] 核对 ADR 与引擎版本、目标平台和已确认的路径编码规则一致。
- [ ] 核对 Story 有 GDD、ADR、验收标准、证据路径与依赖顺序。
- [ ] 核对工程具备可测试接口，QA 具备可执行的验收计划入口。
- [ ] 将评审发现区分为阻塞、需关注、建议；没有验证时不给出无条件通过结论。

## 4. Story 的验证驱动路径

1. 读取 Story 与关联 GDD/ADR，确认技术子域、改动范围及不做什么。
2. 与 QA 确认验收条件可观察，先写最小技术验证及其预期失败结果。
3. 运行验证并核对失败原因，排除环境错误或无效断言造成的假失败。
4. 实施最小必要修改，再运行同一技术验证，保留实际输出与证据。
5. 按影响面运行已有技术检查、相关集成验证或构建检查；记录未运行原因。
6. 更新追溯表，向 QA 提供版本、环境、技术结果和已知限制。
7. 由 QA 执行独立验收并给出结论；工程修复被确认的技术缺陷后重复验证。

对纯方案任务，将第 2—7 步写为待执行计划，不创建伪测试结果；对纯评审任务，只报告证据能支持的发现。

## 5. 性能诊断路径

先记录预算，再建立基线；预算未定就提出测量方案，不虚构通过阈值。

| 阶段 | 要保留的信息 |
|---|---|
| 定预算 | 指标、单位、目标设备、场景、画质、帧率、CPU/GPU/内存预算；联网时补带宽 |
| 建基线 | 构建标识、工具版本、采样窗口、重复次数、场景输入、原始结果 |
| 找瓶颈 | 数据指向的耗时/分配/带宽热点、证据位置、待排除解释 |
| 做优化 | 变更假设、改动范围、正确性检查、可能的副作用 |
| 复测 | 同条件前后对比、是否满足预算、残余风险与进一步优化建议 |

不要混用开发编辑器和发行构建的采样结果；不要将平均帧率当作卡顿或长帧的唯一指标。具体指标和工具以项目可用证据为准。

## 6. 安全评审路径

- [ ] 确认资产与行为：玩家输入、网络消息、存档、遥测和构建产物。
- [ ] 确认信任边界：客户端、服务端、持久化存储、日志接收端与工具链。
- [ ] 按项目检查输入范围/权限、权威状态、重放或篡改风险、存档完整性和机密性需求。
- [ ] 将反作弊与网络权威措施关联具体风险，不承诺绝对防作弊。
- [ ] 将密钥、账号、令牌及敏感日志列入审查，不把秘密写入交付模板。
- [ ] 对加密、认证和部署方案记录所依赖的项目规范与证据缺口。

不要将“有服务端代码”直接等同于“服务端权威”；验证关键状态由谁决定。单机项目无服务端时，将网络条目记为不适用或待明确，而非擅自增加服务端。

## 7. CI 与遥测路径

将流水线组织为“环境准备 → 适用的静态/技术检查 → 构建 → 约定测试 → 产物归档”，按项目现有工具裁剪。
记录失败出口、权限最小化和产物版本；没有授权时只写配置方案，不实际发布或上传。

为遥测逐项确认业务问题、事件名、触发条件、必要字段、版本、接收方和验证方式。
A/B 设计另记假设、分组、指标、观察窗口与停止条件；不要仅凭事件数量认定实验有效。

## 8. 交接与停止条件

交接时提供：产物路径、关键决定、变更范围、技术证据、QA 状态、风险/缺口、待审批动作、下一步。

- 在资料不足时继续只读分析，并将依赖该资料的实现或结论挂起。
- 在目标已存在或授权不明确时停止写入并确认，避免覆盖他人成果。
- 在提交、删除、安装、上线等高影响动作前取得明确许可，不从一般编辑授权推导这些权限。
- 在团队模式下通过当前环境的正常交接渠道回报统筹，跨职责事项经统筹协调；单人模式直接向用户交付。

本技能的职责边界和模板细化属于职业方法规范化，不代表真实团队冲突、真实历史项目或引擎验证结论。
