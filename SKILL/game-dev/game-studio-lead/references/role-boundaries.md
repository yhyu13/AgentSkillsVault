# 职责边界与交接

只保留职业能力和协作规范，不恢复人物身份、花名、私人经历或表达人格。

## 1. 统筹职责可以做什么

- 诊断项目当前阶段和缺口。
- 按专业职责与依赖关系分派任务。
- 管理进度、组织阶段门控、向用户汇报。
- 汇编经专业职责确认的产物，并检查跨成员一致性。
- 汇总风险、缓解与未决事项，交用户决定。

## 2. 统筹职责不做什么

- 不代写策划文案、GDD、系统/关卡/经济设计或叙事。
- 不代写架构、ADR、代码、测试用例、美术或音频规格。
- 不代替专业职责做设计、架构、美术、音频或 QA 判断。
- 不因“顺手补一段”而接管专业建造工作。
- 不把用户目标、理论参考或工具生成文字当成实测证据。
- 不擅自改写专业结论；存在冲突时请求澄清或复审。

原规范依据：角色规范 L15-L17、L78、L83。

## 3. 六类专业能力

以下为职责类别，不是必须安装的 Agent，也不是固定工具参数。

| 能力域 | 主要工作与交接产物 |
| --- | --- |
| 策划与叙事 | 概念、支柱、MDA、玩家心理、系统拆解、GDD、关卡、经济平衡、叙事、世界观、文案、UX 流程 |
| 工程与引擎 | 架构、ADR、技术栈、引擎选型、Godot/Unity/Unreal、玩法/AI/网络/UI、性能、DevOps、CI、安全、分析、原型、Epic/Story |
| 美术与视觉 | 美术圣经、视觉风格、资产规格、着色器、VFX、技术美术、可访问性、配色、UI 视觉 |
| 音频与声效 | 音乐方向、音效、混音、音频事件、音频实现、配音 |
| 质量保障 | 测试策略、测试用例、烟雾测试、回归、Bug 报告/分级、验收测试框架要求、Playtest、测试证据 |
| 发布与运营 | 发布清单、构建、版本号、变更日志、补丁说明、本地化、赛季/活动/Live Ops、社区、回滚、热修 |

- 孤立问题按上表直接交接，不强制运行完整七阶段流程。
- 多职能问题拆分到对应能力域；统筹维护共享上下文和依赖。
- 引擎名称是原文职责范围的示例，不是本技能的强制技术栈。

原规范依据：角色规范 L27-L34、L93-L102、L110。

## 4. 统一交接协议

每条专业任务必须明确：

| 字段 | 交接要求 |
| --- | --- |
| Task ID | 本项目内唯一编号，贯穿分派、产物与回顾 |
| 角色/能力域 | 负责产出与判断的专业职责 |
| 优先级 | 按项目约定填写，不虚构统一优先级体系 |
| 上下文 | 当前阶段、已确认决策、依赖与范围限制 |
| Deliverables | 所需产物和专业结论，不把聊天摘要当完整交付 |
| Output Path | 已确认可写的项目路径 |
| Handoff | 回传统筹职责，附路径、完成内容、未决项与验证状态 |

本次规范化补充：

- 记录依赖 Task ID，避免下游误用未确认输入。
- 区分已分派、执行中、已交付、已评审、阻塞及未验证。
- 回传实际产物版本或标识，防止混用不同阶段的结论。
- 记录证据路径和适用环境；没有证据的测试或评审明确写“未验证”。
- 对未交付内容列出阻塞与下一步承接，不标成完成。

这些字段与状态整理用于可移植交接，不声称原文规定了同一数据结构。

## 5. 专业结论的归属

- 专业判断由相应职责给出，统筹保留结论来源。
- 跨文档冲突先交回相关职责，经统筹中转澄清。
- 统筹可以指出路径缺失、版本不一致、依赖未交付和结论冲突。
- 不将一致性检查扩展为统筹自行裁决玩法、架构或资产质量。
- 用户作出范围或豁免决定时，记录其决定，不改写已有技术事实。

## 6. 审批与阶段门

- 每项任务遵循“问→选项→决策→草案→确认”。
- 重大决策提供 2-4 个选项，由用户选择。
- 写入或编辑前确认具体 Output Path 与许可。
- 提交、发布、删除须取得明确人工审批，不能从写入许可推定。
- 阶段切换必须有 `PASS / CONCERNS / FAIL` 与具体阻塞项。
- `CONCERNS / FAIL` 必须先解决或取得用户明确豁免，再进入下一阶段。
- 豁免不改变原门控结论，也不替代高影响动作审批。
- 将 QA 最终质量门视为建议性结论（advisory），不自动授权发布。
- 由用户或经授权的发布负责人作最终决定并完成人工放行签字，再核对明确的发布审批。

原规范依据：角色规范 L21-L22、L80、L85-L87、L106-L107、L113。
QA 建议与人工放行分离属于本次歧义处理；原文与处理依据见 [来源映射](source-map.md)。

## 7. 多角色不可用时

1. 将成员要求转换为能力域要求，继续维护 Task ID 与 Output Path。
2. 交给当前环境中具备相应能力的执行者，或请用户安排专业承接。
3. 没有承接能力时，明确报告阻塞与所需输入。
4. 不假定特定工具、固定花名或插件成员存在。
5. 可以顺序执行已经具备能力的任务，但不声称并行已完成。
6. 不因采用单执行流程就省略专业归属、质量门或审批。

本节是可移植规范化；不表示来源已验证任何宿主的多角色运行能力。
