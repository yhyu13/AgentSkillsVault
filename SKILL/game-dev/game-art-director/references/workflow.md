# 工作流程与协作细则

本文件把来源职责展开为可执行步骤；证据状态、ID 对应和审计记录属于本次规范化，不是来源逐字模板。来源编号见 [source-map.md](source-map.md)，骨架见 [deliverables.md](deliverables.md)。运行时只读取技能内参考，不需要原插件或提炼工具。

## 1. 接收与读取

1. 从任务中确认阶段、范围、Output Path、目标平台和约束；缺项先列出，不默认为已有项目决策。
2. 确认可读取的资料与用户写入授权。对既有文件先读后改；不修改来源材料、其他职责产出或未经授权的目录。
3. 按项目路径定位概念、GDD 系统、关卡/角色、既有美术圣经、实体清单、主资产清单、可访问性需求与技术偏好。
4. 为每项输入记录实际文件位置及相关段落；不要将示例路径视为文件已存在。
5. 缺 GDD/概念时向统筹或策划索取，暂停依赖这些输入的推导；不要编造视觉需求以完成文档。
6. 缺目标平台、渲染能力或预算时向工程确认；可继续不依赖这些信息的草案，但不得批准其技术兼容性。
7. 已有美术圣经与本次概念冲突时先报告冲突与受影响实体，请用户或统筹确认，不静默覆盖旧规范。

## 2. 选择交付路线

| 任务 | 最低产出 | 先决输入 | 主要协作 |
|---|---|---|---|
| 美术方向 | 视觉锚点、风格参照需求、配色/构图候选、待拍板项 | 概念/GDD、现有视觉身份 | 统筹、策划、用户 |
| 美术圣经 | 九节规范与资产/UX引用 | 已确认或有明确缺口的视觉方向 | 策划、工程、用户 |
| 资产规格 | 实体清单、逐资产规格、AI提示词、主清单更新计划 | 概念、关卡/角色、美术圣经、技术约束 | 策划、工程 |
| 技术美术 | 效果/工具需求、贴图/LOD/预算对齐表、管线待确认项 | 平台、渲染管线、项目预算 | 工程 |
| 资产审计 | 命名/格式/尺寸/管线检查及引用审计表 | 实际资产范围、主清单、规范与引用范围 | 工程 |
| 可访问性 | 分级选择、特性矩阵、UX引用与缺口 | 项目目标、UX需求、现有实现证据 | 策划、工程、用户 |

表中路线是本次职责化展开；可按任务只执行相关部分，不要求每次制作全部交付物。

## 3. 提炼视觉身份

1. 从概念摘取影响视觉的目标，逐条记录设计来源；不增加来源没有的审美偏好。
2. 整理用户提供的风格参照与其选择依据；没有图板时登记参照缺口，不把文字骨架称作完成的美术资产。
3. 按配色、构图、角色、环境、UI、动画梳理一致性要求，分别连接对应设计输入。
4. 对未确定方向提出选项与取舍；说明影响哪些实体和预算，而非替用户拍板。
5. 从项目技术偏好提取命名、格式、尺寸及性能预算，逐项记录单位和适用范围。
6. 将已确认与候选内容分开写入美术圣经；对偏离规范的现有资产标注差异，不为追求数量放弃一致性。

## 4. 建立实体到资产的对应

1. 遍历设计中的角色、环境与 UI 视觉需求，登记实体 ID、来源位置、用途和类别。
2. 为实体建立规格引用；需要多个资产时逐项登记，不凭固定数量生成素材。
3. 在规格中落实用途、风格、尺寸、格式、动画需求、AI 提示词，并引用美术圣经相应章节。
4. 对命名和预算不明项先确认，再写可生产规格；未决内容保留占位，不填行业通用值替代项目决定。
5. 编写 AI 提示词时仅使用有依据的角色/环境/UI要求；涉及未确定风格、尺寸或动画的提示词标“草稿，待确认”。
6. 将主清单中的实际文件与规格连接；只有规格没有文件时属于计划项，不报告为已交付素材。
7. 记录美术圣经偏离、设计缺口和管线冲突，并交相关职责负责人处理。

## 5. 技术美术交接

对着色器、后处理、粒子 VFX、贴图/LOD 优化和管线工具分别记录：

- 要解决的需求、使用场景、关联资产及美术圣经位置。
- 目标平台、渲染管线及其来源；缺来源即标待确认。
- 预期表现、输入/输出约束、工具使用方，避免直接编写引擎实现逻辑。
- 相关资源预算、单位和测量范围；原文未给任何通用性能阈值。
- 需要工程确认的兼容性、实现方式和测试方法。
- 已有证据与待执行检查；未运行的引擎验证不能写成已完成。

若需求超出渲染能力，先保留原目标、约束与可选调整，交统筹/工程核对，再请求用户选择。不得自行保证性能收益或修改玩法数值来掩盖美术冲突。

## 6. 只读资产审计

1. 记录资产根目录、清单版本、检索范围和项目规则来源；原文默认 `assets/`，不强迫真实项目使用此路径。
2. 用现有文件列表建立实际文件集合，记录数量；不把规格计划项混入实际资产数量。
3. 对照项目规则检查命名、文件格式、尺寸预算及管线要求；无检查依据或工具时记录未检查，不猜通过。
4. 用项目清单、配置、设计引用及工程指定范围建立引用集合，并记录每处引用位置。
5. 对实际文件与引用目标逐项对应，形成以下候选，不直接作删除或破坏性修复：

| 检查情况 | 登记结果 | 必要复核 |
|---|---|---|
| 实际文件存在，已检索范围内未发现入链 | 孤立候选 | 让工程确认动态加载、生成路径、外部引用及检索遗漏 |
| 存在引用，目标路径在本次范围内无法确认存在 | 缺失引用候选 | 核对路径解析、构建期生成、打包映射及实际文件状态 |
| 有文件且有明确引用 | 已建立对应 | 继续检查命名/格式/预算，不把有引用等同全部合格 |
| 规范或检查范围缺失 | 待确认 | 记录所缺证据及责任人，不报告通过 |

6. 记录检索方法、覆盖与未覆盖范围；静态搜索未命中不能证明运行时从不加载。
7. 仅在有相应运行或工程验证证据时补充动态加载结论，保留证据位置。
8. 回报偏差和处置建议；只读审计不删除资产、不改引用、不擅自重命名文件。

## 7. 可访问性与 UX 闭环

1. 保留 Basic/Standard/Comprehensive/Exemplary 的完整枚举；明确主流程只列前三级，第四级准入标准证据不足。
2. 依据项目需求与用户确认选定等级；未定时在矩阵与交接中列为待确认，不虚构等级差异。
3. 映射色盲模式、重映射、字幕、文本缩放和输入需求；每项关联需求来源与 UX 位置。
4. 使用“支持/待实现/已验证”三态；支持要有现有实现证据，待实现要解释未实现或待确认原因。
5. 只有实际检查留存环境、方法、结果和证据后才写已验证；文档完整不能代替功能验证。
6. 将同一等级和矩阵位置交 UX 职责负责人引用；发现等级或特性变更时同步关联资产规格与工程缺口。

## 8. 回报与完成条件

交接至少包含实际输出路径、产出摘要、关键视觉决策、资产清单状态、待用户审批项、引擎/管线风险和下一步建议。

- 明确哪些内容已写入、哪些仅是草案、哪些未执行。
- 列出未解决的来源缺口、用户决定与工程依赖；有阻塞时如实标记，不声称全部完成。
- 团队协作时交统筹和相关职责负责人；独立运行时向请求方提交同等内容的文字交接。
- 不创建子团队、不自动安装、不更改源文件；实际制作、生成素材、执行引擎测试均需独立任务范围与相应授权。
