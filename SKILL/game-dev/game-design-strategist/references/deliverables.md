# 可复用交付骨架与验收清单

## 使用规则与来源性质

将本文全部字段布局、表格、状态值和判定步骤作为**新增规范化模板**使用。原角色明确要求概念、依赖排序、GDD 八节、公式单位、至少三类边缘情况和具体冲突定位；未提供这些可直接填写的完整表格。依据见 [来源映射](source-map.md)。

- 只取本次任务所需骨架；用项目事实替换花括号占位内容。
- 对缺少事实的字段写“待确认：{问题}／{决策职责}”，不要编造游戏名称、实体、数值、阈值或实测成果。
- 将状态统一记为“草案／待评审／已确认／已废弃”，并分别记录设计就绪和实现验收状态。
- 将清单结果记为“满足／不满足／待确认／不适用（理由与影响）”；没有证据时不得填“满足”。
- 将以下示例结构视为文档模板，不是要求为每个系统产出全部专项文档。

## 可判定验收清单

将每项关联到输出位置或证据，不因模板存在就判为满足。

| 检查项 | 满足条件 | 不满足或待确认信号 |
|---|---|---|
| 输入与授权 | 阶段、范围、输出与写入许可已确认，缺失材料已登记 | 无范围、擅自覆盖、把缺失路径当已读 |
| 概念完整性 | 2–3 条支柱、MDA、心理映射、核心循环及三层范围齐全 | 只有功能清单、没有取舍或体验对应 |
| 假设与事实分离 | 新设定、数值、效果假设和用户批准事实有不同标记 | 未批准建议被写成既定结论 |
| 系统索引 | 每个待设计系统有标识、权威 GDD、依赖及状态 | 无权威位置、依赖失踪、循环未处理 |
| GDD 八节 | 八节均有内容；不适用项有理由和影响 | 空章节、以标题代替规则、静默省略 |
| 数据一致性 | 实体/变量有唯一权威位置、类型、单位、范围和来源 | 同名异义、单位不一致、默认值无依据 |
| 公式完整性 | 符号、变量、单位、适用域、计算顺序和边界明确 | 未定义变量、量纲不通、无依据参数 |
| 边缘情况 | 至少三类相关场景，均有触发、处理、反馈、验证方法 | 仅列场景名、少于三类且无批准裁剪 |
| 关卡闭合 | 进入、路径、遭遇、结束、失败、奖励、重试闭合 | 无法退出、失败无恢复、规则与系统冲突 |
| 经济口径 | 来源消耗闭合；概率口径/空池/保底明确；曲线有依据 | 概率权重混用、奖励循环失控、参数无出处 |
| 叙事一致性 | 世界事实、角色认知、分支条件与玩法状态对应 | 世界事实冲突、重玩/失败分支状态不明 |
| UX 完整性 | 相关屏幕目标、状态、输入、焦点、返回及可访问性齐全 | 只有画面描述，没有失败/取消路径 |
| 红线评审 | 四类风险均被检查；发现附具体位置和修复或证据缺口 | 未检查、泛泛评价、宣称“绝对平衡” |
| 可实现性 | 架构/引擎限制已引用，未确认项交工程且状态明确 | 越界承诺功能、性能或工期 |
| 验收可判定 | 每条有前置、操作、预期、判定方法和待测状态 | “足够好玩”“体验流畅”等不可判定措辞 |
| 审批与交接 | 决策记录、风险、接收职责、输入版本、下一步齐全 | 未审批即定稿、接收方缺上下文、伪造测试通过 |
