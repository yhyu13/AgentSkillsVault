# 游戏 QA 工作流

> 按阶段使用以下操作，不把本参考文档当成某个项目已经执行的测试报告。
> 所有具体阈值、覆盖矩阵字段和状态细化均为规范化操作建议，不是原文逐字规定。

## 1. 接收与资料定位

1. 明确本次交付是测试策略、测试设计、证据评审、执行报告还是 Playtest 计划。
2. 记录任务范围、阶段、版本、环境、允许操作与输出路径。
3. 确认写入/编辑许可与测试运行范围；对可能污染存档、生产数据或外部服务的测试先提出隔离方案。
4. 只读取项目相关资料；缺少 GDD/Story 标准时，向需求或设计负责人提出具体澄清问题。
5. 若项目无法访问，交付模板并标 NOT_RUN；不要创建虚假的构建、日志或测试结果。

### 输入清单

| 输入 | 核查重点 | 缺失时处理 |
| --- | --- | --- |
| GDD 与关键路径 | 玩家目标、核心循环、明确验收条件 | 向设计/统筹索取，不自行决定目标数值 |
| Epic/Story | 状态、范围、验收条目、依赖 | 将对应项列为待澄清，不沿用未核实的“完成” |
| 测试与回归套件 | 实际断言、可运行性、版本、跳过/隔离记录 | 记覆盖缺口；不得凭测试数量判通过 |
| 已开 Bug | 复现、影响、修复版本、复测证据 | 建待跟踪项，不能把“已修”当“已验证” |
| Playtest 记录 | 真实参与者、构建、任务、观察与授权 | 只写模板/计划，不补造反馈 |

## 2. 建立追溯矩阵

- 为每条验收标准分配稳定 ID，并保留原文件位置或经授权可访问的链接。
- 将逻辑、集成、视觉、UI 方法映射到 Story；同一用例可覆盖多条标准，但必须分别列证据。
- 为自动测试写输入、状态和断言；为人工检查写可观察条件、素材基准和判定尺度。
- 列出适用的边界值、空/极值输入、失败/恢复路径、状态转换以及版本/配置差异。
- 将关键路径的入口、成功路径和失败恢复纳入最小烟雾集合。
- 把缺失标准、证据、负责人和执行条件作为显式待办，不留隐含假设。

### 追溯行格式

| 字段 | 填写方式 |
| --- | --- |
| 需求来源 | GDD/Story ID 与具体位置 |
| 验收条目 | 原文条件或经确认的释义；标清两者 |
| 关键路径与风险 | 受影响的玩家动作、系统状态和后果 |
| 方法与用例 | 自动/手动/烟雾/Playtest 及用例 ID |
| 断言或判定 | 可核验条件，不写“正常”“没问题” |
| 执行记录 | NOT_RUN/PASS/FAIL/BLOCKED、版本、时间、日志位置 |
| 证据结论 | ADEQUATE/INCOMPLETE/MISSING 与具体缺口 |
| 跟踪 | Bug/任务、负责人、下一步 |

## 3. 分配 QA 四层

### 自动层

- 选择项目已有测试入口，核实退出码与报告文件，不臆造脚本或框架。
- 按层级设计断言：逻辑关注规则与边界；集成关注状态和依赖交互；视觉关注约定素材基准；UI 关注操作与反馈。
- 将随机输入、网络、计时、执行顺序和环境差异列为潜在不稳定来源。
- 向工程交接框架需求、目录/命名约定、运行入口、报告格式与隔离要求；由工程实施基础设施。
- 在已授权环境运行适用自动套件及项目已有 lint/typecheck，保留命令、退出码和原始输出。
- 区分断言失败、编译错误、缺少依赖、权限/环境故障；没有完成有效执行时不判 PASS。

### 手动层

- 优先覆盖主观体验、视觉/UI、真实设备行为及难以稳定自动化的操作路径。
- 写明前置存档/配置、输入设备、操作顺序和可重复预期。
- 为每条用例保留实际结果与证据；无法复现时记录条件与次数，不补全未知步骤。
- 若项目标准不足，描述现象并申请澄清，不凭个人偏好发明验收线。

### 烟雾层

- 在计划中列最小核心路径、运行环境、命令、人工确认点和阻塞规则。
- 对每个检查记录预期/实际；先完成适用自动检查，再验证核心交互。
- 必需项通过且有对应证据时给 PASS；失败、未运行或不可核验时给 FAIL 并解释。
- 将烟雾结论绑定精确构建与配置；不要用历史 PASS 代替当前版本验证。

### Playtest 层

- 在打磨阶段计划至少三轮真实测试，分别说明目的、参与者选择、任务和构建。
- 围绕新玩家体验、中盘系统、难度曲线采集证据；根据当轮目标调整重点。
- 先记录事实，再记录玩家解释与 QA 分析；不要将推测写成玩家原话。
- 每轮形成问题列表、归属、修复/设计动作与下一轮或专项复测安排。
- 在总结中列出计划轮数、真实完成轮数、未解决项和签收人；没有参与者与记录不得写“完成三轮”。

## 4. Bug 与回归闭环

1. 记录环境、前置、最小复现步骤、预期与实际。
2. 标明严重度、影响范围、频率/观察次数和证据可信度。
3. 另列优先级、排期依据、负责人和待决事项。
4. 修复交接时提供原 Bug、相关 Story、复现数据与期望回归断言。
5. 收集修复前失败和修复后同条件复测的证据；未执行则保留 NOT_RUN。
6. 将受影响功能、邻近路径与关键循环纳入回归；不要只重跑原复现一次便宣称无回归。
7. 将关闭依据写清：哪些用例、哪些构建、哪些证据；保留残余风险与人工豁免。

## 5. flaky 隔离与复入

- 先核对版本、环境和测试输入是否可比，排除构建变化造成的差异；真实竞态缺陷仍需独立跟踪，不能以环境修复代替产品修复。
- 收集通过/失败次数、日志、种子、运行顺序、时间和资源状态；不要无依据断言根因。
- 必须隔离已识别的不稳定测试，防止污染主 CI 判定；使用项目支持的隔离/独立跟踪机制。
- 明确隔离不是删除覆盖：保留 Story、断言、Bug、负责人、影响与临时替代验证。
- 将修复交工程；修复后在同条件重复运行并核验根因对应断言，再按批准条件复入。
- 若项目未规定复入次数/观察期，提出建议并请求确认；不要声称来源要求固定次数。

## 6. 证据评审与门控

- 逐 Story 对照原始验收标准，不以笼统“覆盖率良好”替代具体断言评审。
- 核对测试存在、有效执行、断言满足、证据完整四件事；缺任一环节分别说明。
- ADEQUATE 要求覆盖和证据均充分；INCOMPLETE 表示部分满足；MISSING 表示无可核验对应证据。
- 分别汇报烟雾 PASS/FAIL、证据评级与整体 PASS/CONCERNS/FAIL，禁止混用状态。
- 将所有 Blocker、未运行必需项、失败和不稳定信号写入阻塞清单。
- 将所有 CONCERNS 写入风险/待审批清单，提出处置方案，不默认豁免。
- 保持 advisory 边界：用户最终决定是否放行，QA 原始判定不能被审批结论覆盖。

## 7. 输出与职责交接

- 将文档写入已许可的 `production/qa/`、`tests/` 或 `production/playtests/`，以项目实际约定为准。
- 回传实际路径、范围、质量门、Bug/缺口、待审批项和下一步；没有执行时明确 NOT_RUN。
- 工程负责产品代码、测试基础设施、测试实现修复与 flaky 根因处理。
- 设计负责需求解释、体验目标和数值方案；QA 提供测试设计与平衡数据分析。
- 统筹负责跨职责澄清与审批组织；最终放行和发布签字由用户决定。
- 不要求固定专家名称、专用消息工具、团队或来源插件存在；使用当前环境的正常职责交接方式。
