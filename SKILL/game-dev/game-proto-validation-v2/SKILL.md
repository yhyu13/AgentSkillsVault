# game-proto-validation-v2 · 玩法原型验证（可执行版）

原型只为回答一个**事先写下**的体验问题，不是交付完整游戏。相对原版的差异：验证问题有可判模板、自检有三遍协议、超时有砍单顺序、交付有固定结构、失败有出口。

## 开工前置（缺一样先要，不要开工）

- [ ] 验证问题（用下方模板写好，由提出人确认）
- [ ] 判定人是谁，玩完后要回答哪几个问题
- [ ] 参考素材（截图/视频，若有）
- [ ] 时间盒（默认 1–2 天出首版可玩）

## 1. 把问题写成可判的格式

模板：**「在 __ 情境下，玩家做 __ 时，能否感受到 __？判据：__」**

- 反例（不可判，退回重写）："好不好玩""手感行不行"
- 正例："雨夜战斗中，玩家连续使用挥砍/闪避/格挡，能否不查教程分清三者反馈？判据：新玩家 3 分钟内不按错、能说出三者的画面差异"

问题不锁定不动手，否则原型会膨胀成小正式项目。

## 2. 拆任务并预设砍单顺序

拆成交互、数值、界面、视听四类任务。超时间盒按此顺序砍（从最安全的开始）：

成长/存档 → 多关卡 → 设置菜单/教程文字 → 视听打磨 → 数值调优 → 核心交互。

砍到核心交互还不够时，说明范围本身就错了——停下来找提出人对齐，而不是默默延期。

## 3. 选最轻的工具

单文件 HTML 或 Godot 优先；仅当验证问题依赖特定引擎特性（特定物理手感、特定渲染表现）才用 Unity/UE。

## 4. 最小可玩核心循环

操作能上手、奖励反馈明确、节奏能感受。必须真机可玩，禁止"录屏假装可玩"。

## 5. 自检协议（固定三遍，记录进交付物）

1. **新手遍**：假装没写过这个游戏完整玩一遍，记下每个卡点（操作困惑/反馈不清/节奏断裂）
2. **修复遍**：改完新手遍的问题后重玩，确认已修复且未引入新问题
3. **录屏遍**：冷启动完整流程录屏，对照验证问题逐条判定

三遍没跑完不交付。

## 6. 交付物（固定结构）

- 可玩构建 + 运行说明（怎么启动、需要什么设备/浏览器）
- README 四段：验证问题（原文）/ 结论（成立 | 不成立 | 需调整，附一句话依据）/ 已知问题清单 / 三遍自检记录（每遍发现 → 修复）
- 让判定人边玩边回答第 1 步的问题；讨论落点是"是否值得扩展"，不是完成度打分

## 失败路径

- 时间用完仍无结论：不延期、不沉默，交付"已验证什么 / 卡在哪 / 还差什么数据"，这同样算完成
- 复刻冲动超时：参考素材只取关键机制与视觉元素；1:1 复刻是原型超时的第一来源

## 边界

不做发行级品质、完整内容量、性能优化。正式工程内改功能 → engine-project-agent-v2；纯美术 → blender-game-assets-v2。结论"不成立"也算成功交付，禁止为好看粉饰手感问题。

## 相对原版（game-proto-validation）的改进

验证问题模板可判化；新增开工前置清单；砍单顺序替代泛泛的"收窄范围"；"自己先玩"升级为三遍自检协议；交付物从三项清单变为固定结构；新增失败路径；删掉不可验证的"行业参照三个月"。
