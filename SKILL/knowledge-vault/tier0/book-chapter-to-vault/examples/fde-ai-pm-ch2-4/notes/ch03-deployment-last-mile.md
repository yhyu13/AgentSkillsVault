## 🧠 核心概念（6 段）

### 概念 1 · 部署 = FDE 的分水岭

> **原文金句**：「写代码的 FDE 和能部署的 FDE，是两个物种。」+ 「能把代码从你笔记本"搬"到客户环境、让它稳定跑起来——这门手艺决定你是普通程序员还是 FDE。」

**我的理解**：客户不在意你写得多优雅，只在意"在我这能不能跑"。部署能力的差距 = 客单价差距。

**怎么用**：把"部署清单"作为 FDE 简历的硬技能高亮区——Docker / IaC / CI/CD / 监控四件套。

**复述题**：客户机房里 4 年前的服务器 + CentOS 6 + 祖传 MySQL 5.5，第一步该做什么？

---

### 概念 2 · 客户环境的 4 种难度

> **原文金句**（环境难度表）：
> - ① 公有云（AWS/阿里云）★★☆ — 最理想
> - ② 客户私有云（客户 K8s）★★★ — 权限受限
> - ③ 物理机房 ★★★★ — 要肉身到现场
> - ④ 断网环境（涉密/军工）★★★★★ — 全离线包

**我的理解**：FDE 的部署能力 = 见过多少种"烂环境"。见过断网部署过 1 次，你这辈子都不会慌。

**怎么用**：去现场前**强制**确认——
- 公有云 → VPC/权限/白名单
- 私有云 → K8s 版本/网络策略/镜像仓库
- 物理机房 → 谁开门/账号密码/有无 sudo
- 断网 → 离线包/备用笔记本

**复述题**：客户说"环境准备好了"，你信吗？你的 Plan B 是什么？

---

### 概念 3 · 部署三板斧：Docker + IaC + 上线清单

> **原文金句**：
> - **第一板斧**：容器化（Docker 是你的保命符）—— 不管什么环境，先打包成 Docker 镜像
> - **第二板斧**：基础设施即代码（IaC）—— 别手敲配置，用代码声明你要什么
> - **第三板斧**：上线检查清单 —— 没有清单的部署 = 俄罗斯轮盘

**我的理解**：三板斧 = FDE 的部署"心法三件套"。Docker 解环境不一致，IaC 解复制粘贴，清单解人脑不可靠。

**怎么用**：
- **Docker 模板**：用 `python:3.11-slim`，加 `HEALTHCHECK`，日志输出到 stdout
- **IaC 选型**：80% 场景用 Docker Compose，15% 用 Terraform，5% 才上 K8s
- **清单**：8 个部署前问题 + 6 个部署后验证（见下方"反模式"表）

**复述题**：为什么"FDE 最常用的是 Docker Compose"而不是 K8s？

---

### 概念 4 · 数据集成 = 90% 部署时间

> **原文金句**：「90% 的部署时间花在数据上，不是代码上。」+ 「因为客户的数据永远比你想象的乱。」

**我的理解**：代码搬家 1 天，数据搬家 1 周。这是 FDE 的常识，也是客户的盲区。

**怎么用**：数据集成三步法——
1. **抓样本**：先拿 100 条脱敏数据，不要一上来全量
2. **建映射**：写 `FIELD_MAP = {"源字段": "目标字段"}`，把客户奇葩的拼音字段名/缩写翻译成规范名
3. **渐进接入**：宁可先跑 1 天的数据，也别跑 3 年的

**复述题**：客户给了一张 2 亿行的订单表，第一步做什么？

---

### 概念 5 · CI/CD = 让部署变成一条命令

> **原文金句**：「如果你还在手动部署……赶紧停。手动部署是 FDE 最大的敌人。」

**我的理解**：CI/CD 的本质不是工具（GitHub Actions / GitLab CI / Jenkins），而是**让部署可回滚、可重复、可追溯**。

**怎么用**：最小可行 CI/CD 三件套——
- 触发：push 到 main
- 构建：docker build + tag
- 部署：scp + ssh 一行命令

**FDE 的 CI/CD 原则**：
- 每个环境一个配置（不要"通用配置"）
- 部署=一次命令（不能需要 10 步手动操作）
- 回滚更快（部署可以慢，回滚必须快）
- 部署要有通知（钉钉/微信群自动告知）

**复述题**：客户说"我们想要一键部署"，你会推荐他上 K8s 还是先上 Docker Compose？为什么？

---

### 概念 6 · 监控与告警 = 没有监控=在裸奔

> **原文金句**：「部署完不等于结束。客户的系统出问题，FDE 是第一个要被 @ 的人。」+ 「没有监控=在裸奔。」

**我的理解**：监控的本质 = 让你比客户先知道系统挂了。这是 FDE 责任心的体现。

**怎么用**：监控三件套 = Prometheus + Grafana + 告警（钉钉/微信/邮件）。必须监控的 5 个指标：

| 指标 | 为什么 | 阈值 |
|------|--------|------|
| CPU 使用率 | 代码写得烂会吃满 | >80% 告警 |
| 内存使用 | 内存泄漏很常见 | >85% 告警 |
| 磁盘 | 日志把磁盘写满 | >85% 告警 |
| P99 延迟 | 用户是不是在等 | >3s 告警 |
| 错误率 (5xx) | 代码是不是在抛异常 | >1% 告警 |

**复述题**：客户凌晨 2 点收到告警说服务挂了，你 8 点起床看到手机有 6 条告警。你的部署架构出了什么问题？

## 🚫 反模式 / 常见坑

| 坑 | 表现 | 危害 | 破解 |
|----|------|------|------|
| **手动部署** | ssh 上去 git pull + 重启 | 每次 30 分钟，迟早出错 | CI/CD 流水线 |
| **没有 Dockerfile** | 直接 rsync 代码 | 客户机 Python 版本不一致就挂 | 强制 Docker 化 |
| **没做健康检查** | 部署完不知道活没活着 | 客户发现挂了比你早 | `HEALTHCHECK` + `/health` 接口 |
| **日志没输出到 stdout** | 写文件日志 | Docker 里看不到 | `logging` 走 stdout |
| **数据一上来就全量** | 上来就迁 3 年数据 | 一个错误就崩 | 先 100 条样本 → 1 天 → 1 周 → 全量 |
| **没有告警** | 部署完走人 | 客户半夜 @ 你 | CPU/内存/磁盘/P99/错误率 5 个必备 |
| **没做回滚** | 新版本炸了不知道怎么回 | 客户生产停 1 小时 | 镜像 tag + 老版本保留 |
| **配置写死在代码里** | 端口/数据库连接硬编码 | 换环境要改代码 | 环境变量 + 12-Factor |

## 📋 部署前 8 问（上线清单）

> **背诵这条清单。8 个全答对才允许点"部署"。**

- [ ] 配置是不是写死在代码里了？ → 用环境变量
- [ ] 数据库迁移有没有准备好？ → 不要现场改库
- [ ] 有没有健康检查接口？ → 部署后怎么知道活着
- [ ] 日志有没有输出到 stdout？ → 不然看不到
- [ ] 如果挂了，怎么知道？ → 告警配好
- [ ] 回滚方案有没有？ → tag 切回老版本
- [ ] 依赖的第三方服务地址写对了吗？ → 不然连不上
- [ ] 端口冲突了吗？资源够吗？ → 客户的服务器上可能已有 Nginx
