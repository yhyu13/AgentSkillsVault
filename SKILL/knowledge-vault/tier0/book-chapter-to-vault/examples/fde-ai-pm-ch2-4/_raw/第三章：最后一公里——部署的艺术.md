第三章：最后一公里——部署的艺术
本章用时：约3小时阅读 + 一个周末实战项目 目标：学完你能独立把一个原型部署到客户环境，并确保它持续可用
3.1 这啥玩意儿？—— 为什么部署是FDE的"分水岭"
有个FDE圈里的老话：
写代码的FDE和能部署的FDE，是两个物种。
为什么？因为在客户环境部署跟在自己笔记本上跑，完全是两码事：
维度	你本地	客户环境
系统版本	你说了算	客户有祖传CentOS 6
网络	科学上网	内网、无外网、只有微信能发文件
数据	test.csv	300张表、字段名全是中文拼音缩写
性能	你的MacBook	客户给了一台4年前的服务器
权限	root	"我们IT说不能开端口"
安全	无所谓	数据安全合规，"不能上云"
能把代码从你笔记本"搬"到客户环境、让它稳定跑起来——这门手艺决定了你是普通程序员还是FDE。

实战建议
如果你去的是	一定要提前确认
公有云	VPC配置、权限策略、白名单
私有云	K8s版本、网络策略、镜像仓库在哪
物理机房	谁给你开门、服务器的账号密码、有没有sudo
断网环境	把所有依赖打成离线包、带一台备用笔记本
警告：永远不要相信客户说的"环境已经准备好了"。FDE第一课：假设你到现场发现啥都没有，带好Plan B。
3.3 部署三板斧——FDE的通用部署法
第一板斧：容器化（Docker是你的保命符）
不管什么环境，先把你的应用打包成 Docker 镜像。
为什么要用Docker？
环境不一致？Docker一打包，跑哪都一样
依赖复杂？全在Dockerfile里，不会漏
要回滚？换一个tag就行
一个模板级的Dockerfile：
FROM python:3.11-slim
WORKDIR /app
## 先装依赖（利用Docker缓存）
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
## 再复制代码
COPY . .
## 健康检查
HEALTHCHECK --interval=30s --timeout=10s \
CMD curl -f http://localhost:8000/health || exit 1
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
⚠️ 常见坑：
镜像太大→ 用 python:3.11-slim 不用 python:3.11
时区问题→ 加 ENV TZ=Asia/Shanghai
日志丢失→ 确保日志输出到stdout/stderr
第二板斧：基础设施即代码（IaC）
别手敲配置，用代码声明你要什么。
工具	适用场景	一句话说明
Docker Compose	单机、小项目	最简单，一个yaml文件搞定
Terraform	云资源（AWS/阿里云）	"我要一台ECS+一个RDS"→ 代码写好自动创建
Ansible	已有服务器，要批量配置	100台服务器装同一个软件包
K8s YAML	K8s环境	声明Pod/Service/ConfigMap
FDE最常用的是：Docker Compose（80%场景）+ Terraform（15%场景）+ K8s（5%场景）。
不到万不得已别上K8s——K8s本身就是一个需要运维的东西。
第三板斧：上线检查清单
这是很多FDE新人最常栽跟头的地方。有一个检查清单，部署成功率翻倍。
✅ 部署前检查
□ 配置是不是写死在代码里了？
→ 应该用环境变量，不同环境用不同配置
□ 数据库迁移有没有准备好？
→ 不要在部署现场手动改数据库
□ 有没有健康检查接口？
→ 部署后怎么知道它活没活着？
□ 日志有没有输出到stdout？
→ 不然你没法看日志
□ 如果挂了，怎么知道？
→ 配置好告警（邮件/钉钉/微信）
□ 回滚方案有没有？
→ 新版本炸了，怎么切回旧版本？
□ 依赖的第三方服务（数据库/缓存）地址写对了吗？
→ 不然部署后发现连不上
□ 端口冲突了吗？
→ 客户的服务器上可能已经跑了Nginx/GitLab
□ 资源够吗？
→ CPU/内存/磁盘，看看会不会OOM
✅ 部署后验证
□ 健康检查通过
□ 核心功能走一遍（不要只点一下，要模拟真实用户）
□ 检查日志有没有异常
□ 检查资源使用（CPU/内存）
□ 通知客户"可以用了"，并告诉对方有问题怎么找你
□ 给自己设一个明天早上的闹钟，再确认一次
3.4 数据集成——FDE最脏最累的活
FDE有一句话：
90%的部署时间花在数据上，不是代码上。
因为客户的数据永远比你想象的乱。
常见的数据坑
问题	表现	解法
编码问题	中文全是乱码	确定源文件编码，统一UTF-8
字段不一致	"手机号" vs "phone" vs "mobile_phone"	建一个字段映射表
数据缺失	30%的订单没有客户ID	跟业务方确认是否有默认值
数据量大	一张表2亿行	加索引、分批处理、考虑OLAP引擎
数据敏感	不能用真实数据测试	数据脱敏后做开发测试
数据集成三步法
第一步：抓样本 先拿100条真实数据（脱敏后的）分析结构，不要一上来就全量迁移。
第二步：建映射
## 字段映射表示例
FIELD_MAP = {
"source_field": "target_field",
"客户名称": "customer_name",
"手机号码": "phone",
"order_amt": "order_amount",
}
第三步：渐进接入 宁可先跑一天的数据，也别一上来跑三年的。
原则：先让系统"能跑"，再让系统"跑全"。
3.5 CI/CD——让你的交付自动化
如果你还在手动部署……赶紧停。手动部署是FDE最大的敌人。
最小可行CI/CD
用 GitHub Actions 实现一个最简单的流程：
## .github/workflows/deploy.yml
name: Deploy
on:
push:
branches: [main]
jobs:
deploy:
runs-on: ubuntu-latest
steps:
- uses: actions/checkout@v3
- name: Build Docker image
run: docker build -t myapp:${{ github.sha }} .
- name: Deploy to server
run: |
scp docker-compose.yml user@server:/app/
ssh user@server "docker compose up -d"
这只是一个起点。 当你面对多个客户环境时，你可能需要：
每个环境一个分支/配置
GitHub Environments + Secrets
分阶段部署（先uat后prod）
FDE的CI/CD原则
原则	说明
每个环境一个配置	不要用"通用配置"，每个客户单独一份
部署=一次命令	不能需要10步手动操作
回滚更快	部署可以慢一点，但回滚必须快
部署要有通知	钉钉/微信群自动告知部署结果
3.6 监控与告警——线上出问题你第一个知道
部署完不等于结束。客户的系统出问题，FDE是第一个要被@的人。
监控三件套
┌───────────────────────────────────────────┐
│          Prometheus + Grafana               │
│    ↑ 收集指标           ↑ 可视化看板          │
├───────────────────────────────────────────┤
│         告警通知（钉钉/微信/邮件）              │
│    ↑ 出问题了第一时间通知你                      │
└───────────────────────────────────────────┘
必须监控的东西
指标	为什么重要	阈值建议
CPU使用率	代码写得烂会吃满	>80%告警
内存使用	内存泄漏很常见	>85%告警
磁盘	日志把磁盘写满	>85%告警
请求延迟(P99)	用户是不是在等	>3秒告警
错误率(5xx)	代码是不是在抛异常	>1%告警
关键业务流程	核心功能是否能跑通	合成监控
一个最简单的健康检查脚本
## health_check.py
import requests
import json
def check_service():
try:
r = requests.get("http://localhost:8000/health", timeout=5)
if r.status_code != 200:
send_alert(f"Health check failed: {r.status_code}")
return False
return True
except Exception as e:
send_alert(f"Service unreachable: {e}")
return False
check_service()
把这脚本加到cron里，每5分钟跑一次。没有监控=在裸奔。

练习：把一个原型部署到"客户环境"
这个练习建议用一天时间来完整走一遍。
场景：你已经完成了上一章（第2章）的库存管理系统原型。现在要把它部署到"客户环境"：
客户环境要求：
一台云服务器（用免费的AWS EC2/阿里云ECS就行）
一个域名（可以没有，用IP也行）
客户说"不要用80端口，用8080"
数据不能用SQLite，要换PostgreSQL
要求有基本的监控（至少知道系统活没活着）
你的任务清单：
□ 写Dockerfile + docker-compose.yml
□ 把SQLite换成PostgreSQL
□ 配置环境变量（DATABASE_URL、PORT等）
□ 部署到云服务器
□ 配置反向代理（Nginx）
□ 配置健康检查
□ 配置日志轮转（防止写满磁盘）
□ 验证：浏览器能访问+接口能返回数据+日志有输出
□ 写一份"客户操作手册"（教客户怎么启动/停止/查看日志）
□ 写一份"出问题了怎么办"的故障处理文档
自检清单
完成部署后，问自己：
如果我现在手机收到告警说服务挂了，我需要多长时间能定位问题？
<5分钟 ✅ 优秀
5-15分钟 ⚠️ 需要加日志/监控
15分钟 ❌ 架构需要重新设计
如果客户说"跑了一周了，我要升级版本"，我怎么做？
一条命令搞定 ✅ 优秀
要手敲10步 ❌ 需要CI/CD
如果明天客户跟我说"帮我再加一个环境"，我要多久？
1小时内 ✅ 你已经掌握IaC了
半天以上 ❌ 你的配置太耦合了
📝 第3章总结
部署是FDE的"分水岭"技能。能做部署的FDE和不能做部署的FDE，薪资上限差50%以上。
记住三句话：
Docker是你的保命符——不知道客户环境是啥？先打包成Docker镜像
没有检查清单不上线——部署前10问，一个没答对就别点确认
没有监控=在裸奔——你能接受客户发现系统挂了但你还不知道吗？
