# 第四章：与客户并肩作战

第四章：与客户并肩作战
本章用时：约2小时阅读 + 1小时模拟演练 目标：学完你能在第一次见客户时不慌、在客户说"这不行"时知道怎么接、在项目结束时光荣撤退
4.1 这啥玩意儿？—— 为什么技术好不等于客户说"好"
很多技术出身的人有个致命错觉：
我代码写得好，客户自然会满意。
错。大错特错。
FDE圈有一个残酷的真相：
客户评价你，90%看体验，10%看技术。
什么意思？客户不懂你代码写得牛不牛，他只感受到：
你回消息快不快
你听不听得懂他说话
你承诺的事做没做到
你遇到问题时是甩锅还是扛事
所以FDE必须学会一件事：把"技术实力"翻译成"客户感受"。
4.2 商业语言包装——让老板觉得你懂他
技术出身的FDE最容易犯的错：用技术语言跟客户沟通。
你张口就是"大模型微调、RAG检索增强、向量数据库选型"，客户的表情就像你在说外星语。
三个关键词就够了
FDE跟老板级客户沟通，所有技术方案都往这三个词上靠：
关键词	老板听到的是	背后的技术
降本	省钱！	自动化替代人工、流程优化、减少错误
增收	赚钱！	数据驱动决策、客户体验提升、交叉销售
风控	不出事！	异常检测、合规检查、实时告警
实战对比：
场景	❌ 技术人说法	✅ FDE说法
客户说"报表太慢"	"我打算用ClickHouse做列存优化，OLAP查询能快10倍"	"我用一个方案能把报表从1小时缩到3分钟，帮你团队每天省出2小时做更有价值的事（降本）"
客户说"想搞AI"	"我们用LangChain搭RAG，Embedding模型用bge-large-zh"	"我们做一个知识库系统，新员工培训时间从2周缩短到3天（降本），同时客户咨询响应速度提升80%（增收）"
金句：老板买的是"省钱"和"赚钱"，不是"大模型"和"RAG"。包装不对，方案再好也白费。
跟非技术客户沟通的三要三不要
✅ 要：用比喻
"AI就像一个读完全部文档的实习生，你问啥它都能从文档里找答案"
❌ 不要：用术语
"这是一个基于Transformer架构的多模态大模型"
✅ 要：先给结论
"这个方案能帮你的团队每天省2小时"
❌ 不要：先讲原理
"我们先来分析一下技术选型，有以下几种方案……"
✅ 要：给选项
"方案A：1周出效果（¥X），方案B：3个月做完美（¥Y）"
❌ 不要：只给一个方案
"我建议我们就做方案A"
4.3 FDE不接SOW——在模糊中定义问题
4.4 第一次见客户——开场决定结局
黄金30分钟
第一次见客户，前30分钟基本决定了你在这个项目里是"自己人"还是"那个外包的"。
✅ 正确的打开方式：
1️⃣ 到场先聊业务，别聊技术（10min）
"张总，你们现在的流程是怎么跑的？"
"每天处理多少单？哪一步最花时间？"
让客户先说，你听着，别急着给方案。
2️⃣ 展示你的"懂行"（10min）
"我刚看了你们的数据，发现订单创建时间和审核时间
平均差4个小时——这是一个常见的瓶颈，我们有类似案例。"
3️⃣ 约定合作方式（10min）
"接下来我们按这个方式配合：每天下午5点对一次进度、
有问题随时群里@我、我会拉一个共享文档记录所有决策。"
❌ 错误的打开方式（真实反面教材）：
FDE（兴奋地）："张总，你们的供应链问题我们用AI迁移学习
加上图神经网络，构建一个多目标优化模型……"
客户（懵逼地）："哦……好……"
（内心OS：这人说的啥？他到底能不能搞定？）
先做人，后做事；先听懂，后动手。
第一次沟通的万能开场白
去客户现场前，背下这段话：
"张总你好，我是冒爸团队的XX工程师。今天我们就是来听你说问题的。你不用理解任何技术细节，你只需要告诉我你们的现状、痛点、期望，我来负责翻译成能落地的方案。今天结束时，我会给你一个清晰的判断——哪些问题马上能解决，哪些需要一些时间，哪些现在还不适合做。你看行不行？"
这段话为啥好用？因为它传递了三个信号：
我站在你这边（不是来推销的）
我负责翻译（你不用学技术）
我会给你判断（不是画饼的）
4.5 管理期望——FDE最重要的非技术能力
期望管理的核心公式
客户满意度 = 实际体验 - 期望值
你的工作不是只提高实际体验，更要管理好客户的期望。
四个关键场景
场景1：客户说"这个很简单，一天搞定吧？"
错误回应：
"好，我试试" → 搞不定就毁了信任
"你懂个屁，这哪有一天" → 关系就僵了
正确回应：
"张总，你说的这个功能，如果只是实现大概需要2-3天。但我建议我们分两步走——先做个最小版本给你看效果，你觉得方向对了我们再加东西。明天下午我发一个简单的Demo给你，先看看是不是你想要的那个意思，行不？"
套路拆解：
肯定客户的直觉（"你说得对"）
给出真实时间（"不是一天，是2-3天"）
化大为小（"先做个最小版本"）
马上给结果（"明天下午发Demo"）
场景2：客户的需求一直在变
这不是客户的问题，是你的问题。 因为你没有帮客户锁住范围。
解法：需求锁定三连
第1步：每次确认需求时说
"好的，我记下了。那我先做A、B、C三件事，
你确认是这个优先级对吧？做完这三件我让你验收。"
第2步：客户加需求时说
"好的，这个需求我记下来了。现在我们在做A、B、C，
你这个新需求D，你希望：
① 替换掉某个已有功能（砍掉C来做D）
② 放在A完成后做（顺延时间）
③ 作为一个独立项目来做（另起一个项目）
你看哪个方案合适？"
不是不能加需求，是得让客户知道"加需求=减别的东西"。
场景3：进度延期了
错误做法：拖到最后一天才说"没做完"。 正确做法：提前预警，提前预警，提前预警。
FDE的黄金法则：
如果有任何因素可能导致延期，在你知道的当天就告诉客户。
一个好的预警模板：
张总，有个情况跟你同步一下：
我们原计划周五交付订单审核功能，但今天排查时发现
客户数据的时间戳格式不统一（有的用UTC、有的用北京时间），
需要额外2天做数据清洗。
影响：
✅ 周五还是能交付，但只能跑最近30天的数据
❌ 全量数据（3年）需要下周三
我的建议：
周五先上线30天版本，你确认方向对不对，
我们再花一个周末搞定全量。
你看行不行？
关键点：
先说问题（时间戳不统一）
再说影响（只能跑30天）
最后给方案（两步走）
让客户做选择题，不是问答题
场景4：客户说"这个做得不好"
听到这句话，第一反应不要防御。大多数时候客户说的"不好"其实不是你的代码有问题，而是沟通出了问题。
处理流程：
第1步：接住情绪（不要解释）
"明白，你觉得哪块不满意？能给我举个具体的例子吗？"
第2步：找根因
"如果重新做，你理想的版本长啥样？"
第3步：给补救方案
"我知道了。我今天晚上回去改一版，明天上午给你看新的。
改的方向是：XXXXXXXX。这个方向对吗？"
第4步：复盘
"对了张总，以后为了避免类似情况，我们是在开始前
先给你看一个原型再动手，还是你有什么更好的建议？"
记住：客户的"不好"通常不是针对你，而是针对"结果跟预期不一样"。把预期对齐了，满意度就回来了。
4.6 现场诊断——黄金一小时
FDE到了客户现场，最常见场景之一就是：系统出问题了，客户很急，等着你修。
这时候你有"黄金一小时"——客户愿意全神贯注配合你解决问题的窗口期。
黄金一小时工作流
┌─ 第1个10分钟：复现问题 ──────────────────────────┐
│   "你刚才做了什么操作？" → 原样操作一遍               │
│   "有截图或者录屏吗？" → 减少"我以为"                 │
├─ 第2个10分钟：收集信息 ──────────────────────────┐
│   看日志 → 查监控 → 看数据库                        │
│   问自己：什么时候开始？跟什么有关？谁操作过？          │
├─ 第3个10分钟：定位根因 ──────────────────────────┐
│   画一张图：A→B→C，哪个节点出问题了？                 │
├─ 第4个10分钟：出修复方案 ──────────────────────────┐
│   "问题在XXX，原因是XXX，方案是XXX，需要XX时间"       │
├─ 第5个10分钟：修复+验证 ──────────────────────────┐
│   修好了 → 让客户验证 → 写进故障报告                  │
├─ 第6个10分钟：善后 ──────────────────────────────┐
│   告诉客户"为什么发生" + "怎么避免再发生"            │
└────────────────────────────────────────────────────┘
现场排查常用命令速查
## 看日志（前100行最新的）
tail -100 /var/log/myapp/app.log
## 看资源
top -bn1 | head -20
df -h
## 看端口
netstat -tlnp
## 看有没有OOM
dmesg | grep -i oom
## 看Docker日志
docker logs --tail 100 myapp
## 数据库慢查询
SELECT * FROM pg_stat_activity WHERE state != 'idle';
把这些命令记在小本子上或者手机备忘录里。到了现场直接开干，不用Google搜索浪费时间。
4.7 文档与知识转移——让客户学会运营
FDE的最高境界不是"我在客户才放心"，而是**"我走了客户一切正常"**。
必须交付的三份文档
文档	写给谁看	核心内容
系统操作手册	客户的运营同学	怎么登录、怎么用、一天怎么巡检
故障排查手册	客户的运维同学	常见问题+排查步骤+该找谁
维护说明	接手的FDE	架构图、配置项、注意事项、遗留问题

撤退检查清单
□ 三份文档都交付了（操作手册+故障手册+维护说明）

最后一个印象，比第一个印象更持久。把撤退做成"光荣毕业"，而不是"终于解脱"。
🔬 动手练一练
练习1：模拟第一次客户见面
找一个朋友（或者AI）扮演客户，你演FDE。场景如下：
你是一家餐饮连锁企业的FDE，第一次见运营总监王总。 王总说："我们想用AI预测每天的食材用量，减少浪费。 现在是人工估的，经常不是多了就是少了。"
你的任务：按照4.2节的开场白，走一遍15分钟的对话。
自检清单：
我有没有在前10分钟让客户多说、自己少说？
我有没有用大白话翻译技术方案？
我有没有在结束时给客户一个"接下来怎么办"的明确路径？
客户走的时候，他的表情是"放心了"还是"更困惑了"？
练习2：场景模拟——客户说"需求变了"
你正在做一个报表系统，做了一半，客户说：
"那个，我昨天想了想，觉得报表的统计维度不对。 不应该按门店统计，应该按区域统计。 另外再加一个月度环比对比。"
你按4.3节的方法回应。写下你的回应，然后问自己：
我有没有让客户做选择题，而不是问答题？
我有没有保护原始交付时间，或者让客户明确接受延期？
练习3：写一份"一分钟诊断报告"
假设你接到客户消息：
"系统好像挂了，打不开页面。"
按4.4节的方法，写一个"一分钟诊断报告"模板，包含：
你要问客户的3个问题
你要检查的3个地方
你给客户的一个初步判断
📝 第4章总结
技术搞定的是"事"，沟通搞定的是"人"。FDE真正的天花板不在代码能力，而在你能不能管理好跟客户的关系。
记住四句话：
第一次见面：先听20分钟再说话 — 让客户觉得你懂他
需求总变：不是客户的问题，是你没锁定范围 — 让客户做选择题
客户说"不好"：先接情绪，再找根因，再给方案 — 不防御
撤退要体面：文档+复盘+留好联系方式 — 好聚好散
