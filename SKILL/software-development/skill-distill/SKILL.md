# skill-distill · 会后沉淀流水线

## 何时调

- 一段活儿刚做完、PR 已合、准备收工或汇报时；
- 用户说"沉淀 / 存成 skill / 记下来 / 以后别再踩"；
- 路上踩了坑、发现反直觉的事实、验证命令跑通了，值得留给下一个会话；
- 定期（每个版本节点）体检已有 skill 是否过时、重复、膨胀。

**不调的情况**：只想把进度记一笔 → 那是 `journey.md`，不是 skill。
**分不清时问一句**：这条是"这次做了什么"（journey），还是"下次该怎么判断和怎么做"（skill）？后者才沉淀。

## 一、判定：什么值得沉淀（过四道闸）

四道全过才写 skill；任何一道不过就走 journey 或干脆不写。

| 闸 | 判断 | 不过怎么办 |
|---|---|---|
| **① 可复用** | 下次遇到同类任务，这段话能直接省掉一次踩坑？ | 只记进度 → journey |
| **② 有判断** | 里面含"该选 A 还是 B、什么时候该停"这类决策，而不只是"我敲了这些命令" | 命令清单 → 直接进文档，别占 skill |
| **③ 有证据** | 能指回具体文件/命令/错误码/真源，不是"我觉得" | 先把证据补齐再沉淀 |
| **④ 有边界** | 说清了什么时候**不**适用 | 补一节"不调的情况" |

**反模式（不要沉淀）**：

- ❌ 把 README / AGENTS.md / 代码原样抄一遍 → skill 是指针 + 判断，不是副本；
- ❌ 单次事故流水账（"今天 ffmpeg 报错了"）→ 除非它揭示了一个会复发的机制；
- ❌ 通用编程常识（"git push 前先 commit"）→ 不属于这个仓库；
- ❌ 把 skill 写成日志 → 时间线归 `journey.md`。

## 二、粒度：一个 skill 装一件事

- **命名**用小写连字符、动词或领域词：`v04-delivery`、`skill-distill`、`dev-server`。
- **一个 skill ≈ 一条链路**（上线、招募、群运营、支付、单测策略）。
  超过 ~150 行就该问：是不是该拆两个？
- **frontmatter 三件套**：`name` / `description` / （可选）`argument-hint`。
  `description` 必须写成**召回条件**（"什么时候该用这个"），不是内容摘要——
  harness 靠它决定要不要召回，写成摘要就永远召不回来。

```yaml
---
name: <kebab-case>
description: <一句话说清「什么时候调」+ 覆盖哪条链路>。<本仓库特有的触发场景枚举>。
---
```

## 三、放置与归属（先找对家，别新开）

动手新建前，先扫一遍 `.claude/skills/`：

```bash
ls .claude/skills/ && head -6 .claude/skills/*/SKILL.md
```

| 沉淀的内容 | 去处 |
|---|---|
| 已有 skill 的新踩坑 | **追加进那个 skill 的对应小节**，别新开 |
| 已有 skill 的纪律失效了 | 就地改写，并把失效原因写进去 |
| 一条新链路 | 新建 `.claude/skills/<name>/SKILL.md` |
| 纯命令清单 / 配置表 | 普通文档（`docs/`），在 skill 里留指针 |

> 本仓库既有：`dev-server`（本机后端起停）、`v04-delivery`（上线/招募/群运营/支付四组）、
> `speckit-*`（spec-kit 流程，由上游模板维护，别改）。新沉淀前先对这三个查重。

## 四、写法：一份 skill 的骨架

```markdown
# <名字> · <一句话它替你做什么>

## 何时调
- 用户说"…"
- 你改完 X 要复测
- 接手 issue #N 的 …

## 零、先记住本仓库的物理事实      ← 反复踩的放最前
## 一、<主链路步骤>                ← 命令串、决策点
## 二、<旁支/边界>                 ← 什么时候**不**这么做
## 三、验收的最小门槛
## 四、红线（来自 AGENTS.md，不可协商）
```

**每条经验写成三段式**：`结论是什么` → `为什么（带证据：文件/命令/错误码）` → `怎么防再犯（可断言的那一步）`。
只写结论的经验过不了闸 ③，也留不住。

## 五、防重复与防膨胀（沉淀最容易出的问题）

- **合并不新建**：新沉淀先看能不能塞进已有 skill；塞不下才新建。
- **一条坑只在一个 skill 里**。出现在两处就会有一处过时，然后两处都不可信。
- **定期体检**（每版本节点，或发现 skill 说的命令跑不通时）：
  - 逐条**实跑** skill 里的关键命令，跑不通的当场改或删；
  - 删掉已经被 AGENTS.md / 宪法覆盖的复述；
  - 涨过 ~200 行就拆。
- **过时比缺失更糟**：宁可删一条，不要留一条错的。

## 六、流程（沉淀本身也要守交付纪律）

沉淀是**纯文档改动**：不需要新开 issue，但要**走分支 + PR + GitHub 上合并**，
禁止直推 main、禁止本地 merge。

```bash
git checkout -q -B skill-<name> origin/main      # 先同步上游
# …写 .claude/skills/<name>/SKILL.md…
git add -A && git commit -q -F - && git push -q origin skill-<name>
gh pr create --title "skill：<名字> · <一句话>" --body "Refs #<相关 issue>"
sleep 45 && gh pr checks <PR> && gh pr merge <PR> --squash
git fetch -q origin && git checkout -q -B skill-<name> origin/main
```

PR 正文要写清**沉淀了哪几条、每条来自什么证据**，让 review 的人不用重读全部 transcript。

## 七、自检清单（提交前逐条打勾）

- [ ] 四道闸全过（或能说清为什么这条仍值得留）
- [ ] 已扫 `.claude/skills/`，没有重复归属
- [ ] `description` 写的是**何时调**，不是内容摘要
- [ ] 每条经验带证据（文件路径 / 命令 / 错误码）
- [ ] 至少一节写了"什么时候**不**调 / 不这么做"
- [ ] 没有复述 AGENTS.md 已有内容（最多留一句指针）
- [ ] ≤150 行；超了考虑拆
- [ ] PR 已合，且 `Refs #<issue>`

## 八、红线（来自 AGENTS.md）

- ❌ 把密钥写进 skill / 文档 / 任何入库文件；
- ❌ 把 `journey.md` 的历史 Entry 搬进 skill，或改写历史 Entry；
- ❌ 沉淀"进度"冒充"方法"；
- ❌ 未验证的命令写进 skill（会被下一个人当真的执行）；
- ✅ 沉淀的是**判断与边界**，不是日志与副本。
