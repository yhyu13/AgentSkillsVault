# 让 Skill 自己被选中

一份 Skill 要同时满足三件事：不用点名也会被选中，同类任务产出稳定，人以后还能改。只把步骤写进文件，三件里一件都没有完成。

这套方法从 BV1BqnJ63E4h 的一次讲解蒸馏。讲者的估计、自述和转述都留在 [references/claims.md](references/claims.md)，不要写成普遍事实。

## 先决定做不做

三条信号沾一条就值得做：

- 同一类任务反复出现，流程几乎相同。
- 做法来自使用者的工作，模型的通识里没有。
- 做错的代价高，返工或误发比多写一份文件贵。

三条都没有，就写成一次对话，不做成 Skill。

## 先选调用方式

描述可以不给模型看。Matt Pocock 在 BV1opMh6TEgL 里把只由人用名字调用的 Skill 设成禁用模型调用。模型可调用的每条描述，每次请求都占一段上下文；一百条就是一百段。模型即使看见匹配描述，也可能不调用。他因此宁可把记忆负担放在人身上，也不为触发时机做评测。

这和 Perplexity 的负例评测相反。模型可调用的 Skill 仍要跑正例和相邻负例。人调用的 Skill 不把描述放进自动清单，也不因为没被自动选中算失败。

## 描述是触发器

宿主启动时只读名字和描述。正文写得再好，描述没碰到使用者的话，也不会被选中。

描述同时写两句：这份 Skill 做什么；使用者会说哪些话。再用一句挡住过宽的邻居，例如“不用于只要下载视频”。用第三人称，用使用者的原话，不用内部编号。

改完描述，用两个请求试：一个该选中，一个不该选中。不该选中的也被选中，就把边界写进描述，不要靠正文补救。

## 评测先于正文

Perplexity 的六步把顺序说成：先写评测，再写描述，然后才写正文，接着用目录放复杂度，迭代时看相邻 Skill，最后带着行为证据发布。来源是 BV1rb5y6wEJV 对《Designing, Refining, and Maintaining Agent Skills at Perplexity》的转述，不是原文逐句。

评测至少有三类：真实会说的请求、已经失败过的请求、看起来相近但不该选中的请求。第三类是负例。Skill 的主要风险不只是不加载，而是把无关内容塞进上下文。

正文只保留模型自己做不出的判断：什么重要、什么是错的、哪条边界不能过、哪里容易误判。模型本来就会的“先理解、再执行、最后总结”，不写进去。命令序列能收成意图时，就写目标和失败时怎么解释，不写死每条命令。

描述改一个词，就要把正例和相邻负例再跑一次。它改的是分类边界，不是文案。

## 正文写判断

先不给方法，让模型做一次同类任务。卡住的地方才写进去。模型已经会判断的，不写成规则。

信任不靠把步骤写得更细。Lauren Tan 在 BV1hEaN67EkV 里把验证放在前面：Agent 要能按用户真正使用的方式运行和检查。它自信下结论却没读受影响的代码，这次信任就断。改 Skill 后重跑评测；被测代理知道自己在被评时，行为会变。PR 数量是讲者自述，不写成质量证据。

正文保留三样：

- 为什么做：替谁省下哪一次判断。
- 心态：结果是给谁看的。
- 原则：遇到变化时先看什么。

只有对错有客观标准的动作才写成窄步骤。取数、排序、校验和格式转换放进 `scripts/`，脚本返回结果，不把脚本正文塞进主文件。超过一次任务才需要的例子、口径和长清单放进 `references/`。

主文件保持能通读。讲者转述的官方建议是超过五百行就拆；两百行以内是讲者自己的倾向，不是硬上限。

## 验收不由作者打分

容错低时，把检查清单交给一个没有参与编写的上下文。清单写可观察的通过和失败。作者不替自己的结果解释为什么算通过。

## 两种时候回来改

- 模型升级后，跑一次旧 Skill。只为弥补旧模型弱点而加的句子，删掉。
- 一次真实任务跑完，可以请 Agent 列出错误和原因。它提出的修改先由人核对，再写入文件。

维护只做三件：删重复、把新内容放回原来的骨架、把长例子移进参考资料。不要把复盘结果插到每一节。

## 触发试验

改完描述就做两次，不要等正文写完。

选中与否，只看宿主这次实际注入了哪一份 Skill。把两个请求分别交给一个新会话，看它有没有读到本文件。宿主没有显示注入记录时，就问它这次读了哪一份，并以那次回答为准。不要把检查脚本的退出码当成选中。

该选中的请求要包含描述里的原话，例如“为什么这个 Skill 不触发”。不该选中的请求要靠近边界，例如“帮我执行周报 Skill，把这周的提交整理出来”。第二个请求是在用一份已有 Skill，不是在写 Skill。

```text
选中：这份 Skill 不触发，描述该怎么改？
不选中：用现有的周报 Skill 整理这周的提交。
```

两次都选中，说明边界没写进描述。两次都不选中，说明使用者的原话不在描述里。只改被证明缺失的那一句，不要把正文目录补进描述。

## 一次只补一个缺口

试跑失败时，先把现象分成四类，再决定改哪里：

| 现象 | 改哪里 | 不要改哪里 |
|---|---|---|
| 该用时没有被选中 | 描述里的原话 | 正文步骤 |
| 不该用时也被选中 | 描述里的边界 | 删除正文 |
| 选中了，但结果不稳定 | 原则和验收清单 | 把每一步写死 |
| 取数或格式每次不同 | `scripts/` | 主文件里的口头说明 |

一次只改一个格子，再用同两个请求复查。同时改描述和正文，就看不出是哪一处生效。

## 失败时停住

遇到这些情况，停止扩展 Skill：

- 只有一次对话，三条信号都对不上。把它留在对话里。
- 原片、用户或模型没有给出的数字。缺的数字标成未知，不补成顺句。
- 复盘建议要把同一句话写进多个章节。一句只留一个位置。
- 检查脚本通过，但该选中的请求仍没选中。脚本通过不算完成。

```bash
python scripts/check_skill.py .
```

退出码 0 只表示名字、描述边界、分层和链接在。退出码 1 会指出缺的是哪一项。
