# pstack 信任阶梯

pstack 解决的是“产量上去之后，人还敢不敢相信结果”。核心不是多装 skill，而是把人从逐句盯梢，移到看证据、再移到事后抽查。

来源是 Lauren Tan（poteto）在 cursor/plugins 的 pstack，以及 BV12D4E6NEMn 对它的拆解。仓库会变；下面的名称和顺序以 2026-08-14 读取的 README（插件版本 0.15.36）为准。数量变化时重新读仓库，不要沿用旧数。

## 先判断停在哪一阶

每次只推进一阶。上一阶的过关标准没达到，不增加并行数，也不开放自动合并。

| 阶 | 人在做什么 | 过关标准 |
|---|---|---|
| 1 全程紧盯 | 每做一段就看，人在中间传递结果 | 能说出最近反复出现的三种错误 |
| 2 自己验收 | 看交件附带的证据，不再亲手重做整遍 | 不打开原始文件，也能判断对错 |
| 3 自己接单 | 模糊请求先被查清、重现、变成任务 | 人只看结果和例外 |
| 4 自动合并 | 独立验收通过后系统合并，人事后抽查 | 连续多次过夜都不需要收拾残局 |

## 改错误的顺序

同一类错误第二次出现，就停止追加“下次注意”。按能实际拦住它的最高层修复：

1. 结构上只留一种正确做法，让后续照抄也抄不错。
2. 用类型、lint、CI 或等价的自动检查拦截。
3. 用测试守住已经发生过的行为。
4. 最后才把提醒写进说明文件。说明文件没被遵守时，人不会知道。

`/correct` 官方顺序就是 architecture，然后 types、lint、CI，然后 tests，docs last。不要把某种语言的具体禁令扩大成所有项目的规则。

## 交件前要证明的三件事

没有这三项，速度只是把审查债往后推。

- **做得成**：用真实操作证明行为。项目还没有验收技能时，用 `/create-verification-skill` 生成；已经有但和产品不一致时，用 `/maintain-verification-skill` 修正，不要反复生成。
- **波及多大**：看起来很小的改动也要查。`/blast-radius` 要用实际运行证明它为什么安全，不能只凭“改动很小”跳过。
- **不是同一盲点**：同一份改动交给不同模型拆，只用能复现的发现，这是 `/interrogate`。它不检查审查者身份。写作者不能给自己的结果签通过，这是阶梯记录里的 `author` 与 `reviewer` 规则，不是这条命令的适用条件。`/swarm` 是把不同切片分给多个工作者再汇总，不能拿它代替独立拆台。

交叉审查会增加 token。预算不够时，先减少并行，不要取消独立审查。

## 什么时候用哪套

下表是 BV12D4E6NEMn 讲者的选择建议，不是 pstack README 的路由。进了 pstack，仍由 `/poteto-mode` 选 playbook。

| 现状 | 讲者建议 | 原因 |
|---|---|---|
| 目标还在人的脑子里，从零做 | 先用 Matt Pocock 的 grill-me，再写成 to-spec | 测试猜不到只有人知道的意图 |
| 已有大量历史，修缺陷、重构、改性能 | 用 pstack | 先查现状和历史，再做验收 |
| 方向刚定、准备落地 | 先问清，再交给 pstack 验证 | 讲者转述两者可以互补 |

README 的路由不同：需要严格性的工作从 `/poteto-mode` 进入；新行为走 feature playbook，不把写计划书当默认。能自己从代码或小实验查清的问题，不停下来问人；不可逆动作才等。

不要把下列命令连成固定流水线：

- `/how`、`/why` 在需要理解现状或历史时用。
- `/sharpen` 只有人明确要求改写提示时用；它交回提示，不执行任务。
- `/architect` 在改动跨出函数边界、需要先定调用和类型时用。
- `/tdd` 在修缺陷且本地测试便宜时用：先写失败测试。新功能不要因此被强加一套失败测试。

Claude Code 会给命令加插件前缀，`/poteto-mode` 实际是 `/pstack:poteto-mode`。

## 过夜的边界

睡前只接受能判断“过”或“不过”的完成条件，并写明卡住多久必须停下、留下原因。

这里要分清两层：

- 讲者给新手的第五步：只许保存和开 PR。合并、发布、删除数据、对外发送留到人回来。连续多个早上都不用收拾残局，才进入自动合并。
- README 里它们是不同 playbook，不要并成一条。`autopilot-stack` 验好后留给人合并。`shipping` 是独立验收后落地一整条已验证的栈。`autopilot-full` 是每张独立 PR 验过后合并。只有用户明确要求其中一种时才用它；白天的普通交付不要改跑会合并的 playbook。

自动进单也先汇成清单。多个表面问题常是同一个根因，先归并再派工，不要看到一条就修一条。

## 不能当成事实的说法

- “一个月 2,500 张 PR”“一天八十几张”“某天早上 20 张”“600 多张用来打地基”，都是演讲中的自述或讲者换算，不是独立审计结果。
- 这份 README 写明 24 条原则，并在技能表中列出 34 个其他 skill，合计约 58，与影片“将近 60”相符。仓库变化后重新数，不沿用旧数。
- “约 10 个独立验收者”是讲者对全自动模式的描述，不是 README 里的固定参数。
- 这份 README 的默认是代码委派给 Grok，最难的改动、文案和判断给 Opus 5.5。旧的 setup 规则不会因为仓库更新自动刷新；重跑时还可能保留与新默认不同的角色。使用前看当前配置，不把旧配置当成现行默认。

名称和职责的核对表见 [references/source-map.md](references/source-map.md)。只有需要引用具体 skill 或分辨影片口误时才读它。

## 怎么判定可以进下一阶

用 `scripts/check_ladder.py` 读一份交接记录，不靠口头“感觉可以了”。记录格式见 [references/handoff-format.md](references/handoff-format.md)，可从 [assets/handoff.example.json](assets/handoff.example.json) 复制。

```bash
python scripts/check_ladder.py handoff.json
python scripts/check_ladder.py handoff.json --want 2
```

脚本只认记录里的计数字段。完成条件含模糊词，退出码是 1。`current_rung` 高于记录实际支持的阶，退出码也是 1。作者和审查者是同一个人时，不单独报错，而是最高只能停在第 2 阶；再请求第 3 阶才退出码 1。把“已完成”写进说明文件不能代替这些字段。

阶和字段的对应：

| 想进入 | 记录里必须已经有 |
|---|---|
| 2 | `repeated_errors` 至少 3 条，且每条有 `count >= 2` |
| 3 | 上一阶，再加 `evidence_count >= 1`，并且两边身份去掉大小写、空白后互不包含 |
| 4 | 上一阶，再加连续 3 次不用重做，以及 3 个不用收拾的早晨 |
| 自动合并 | 已到第 4 阶，并且 `merge_requested` 为真 |

没有用户的明确要求时，过夜最高停在 `autopilot-stack`：开好 PR，人回来合并。

## 一段可照抄的最小记录

下面这份只能证明“观察过三种反复错误”，不能证明任何更高的阶。审查者留空是故意的，脚本会拒绝用它进入第 3 阶。

```json
{
  "current_rung": 1,
  "repeated_errors": [
    {"name": "口头说完成但没有运行", "count": 4},
    {"name": "同一盲点换个说法再出现", "count": 3},
    {"name": "把提醒写进说明后仍再犯", "count": 2}
  ],
  "evidence_count": 0,
  "author": "writer",
  "reviewer": "",
  "accepted_without_rewrite": 0,
  "clean_mornings": 0,
  "merge_requested": false,
  "done_definition": "三条失败都有计数"
}
```

## 不该用它的时候

- 用户要的是安装 pstack、给仓库写功能、或解释某一段代码。直接做那件事。
- 错误只出现过一次。先改这一次，不要提前建阶梯。
- 完成条件只有“更好”“好看”“优化一下”。先把它改成可判断过或不过的条件，再谈过夜。

## 一个完整判断

假设记录是：三种错误都出现过两次，交件有 2 份可复核证据，写作者是 writer、审查者是 other，连续 3 次不用重做，也有 3 个干净早晨，但 `merge_requested` 仍是 false。

判断顺序不能跳：

1. 三种反复错误使它通过第 2 阶。
2. 证据和不同审查者使它通过第 3 阶。
3. 连续接受和干净早晨使它停在第 4 阶。
4. 合并开关是 false，所以过夜仍用 `autopilot-stack`，只开 PR，不合并。

把 false 改成 true 之前，先确认那句话来自用户，不是来自 agent 的推断。脚本的 `--want 5` 会把缺这一项打回退出码 1。

仓库版本和影片数字的边界见上文“不能当成事实的说法”。命令职责变了，以新的 README 为准，不以这份记录里的旧数称为准。
