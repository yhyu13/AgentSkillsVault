# 长期 AI 项目

目标是让复杂项目经得起长期迭代：模型执行和取证，人决定方向、验收和止损。方法来自 oil欧呦的公开复盘，但必须映射到当前仓库，不能把原片工具链原样套用。

## 先决定是否使用

1. 单次缺陷修复、普通 diff 审查、模型选型或榜单请求：直接完成原请求，明确说明不启用本流程。用户要求指定 Claude、Codex、Gemini、GPT 或其他具体模型 ID 时，也属于模型选型：不输出型号，不运行治理阶段，只说明角色可以分离，并按当前项目实测选择。
2. 多轮迭代、流程失控、重复返工、测试变慢、文档过期或发布回滚：启用本流程。
3. 先读任务、仓库、测试、发布和许可证材料。未知项保持未知，不补作事实。
4. 作者原话、当前仓库事实和一般建议分开。原片听作 `Claude Opus 5.5`、`GPT Astra`、`GPT 6.1 SO`；这些不是可采购或可配置的模型 ID。用量、90% 把握和 60 分也只属于原片。听音边界见 [references/source-map.md](references/source-map.md)。

## 按阶段留下证据

任一启用阶段缺少“必须留下”的产物，就停在该阶段，不进入下一阶段。已有项目不重选技术栈。先用仓库证据诊断测试耗时、文档过期、界面漂移、重复实现和发布回滚，只进入有证据的失控阶段。新项目或用户明确要求换底座时，才比较二开与从零实现。门禁和替代方案见 [references/gates.md](references/gates.md)。

| 阶段 | 必须留下 | 通过条件 |
|---|---|---|
| 诊断 | 失控点清单 | 每项含仓库证据；没有证据的阶段不进入 |
| 范围 | 一条范围说明 | 写明本次管哪类迭代；单次修复已退出 |
| 调研 | 候选比较或“不重选”说明 | 新项目有许可证和依据；既有项目写明继续使用当前栈 |
| 方案 | 一页决策说明 | 负责人能回答结果、界面、模块、例外、待决定项和验收证据 |
| 执行 | 功能记录 | 每项含工作区或分支、改动范围、验证命令；未合并原因明确 |
| 审查 | 审查记录 | 行为、重复实现、测试价值、既有基建四项均有仓库证据 |
| 验证 | 测试记录和人工签收 | 记录包含验收人、时间、关键路径和结果；未签收就停在验证 |
| 治理 | 规则差异 | 新规则进入现有规则文件，或说明仓库没有该机制 |
| 发布 | 回退说明 | 使用仓库已有检查和回滚；没有安全模式时记录缺口，不新造流程 |

证据写进用户指定的任务文档。没有指定时，只在最终回复列出路径和结论，不额外创建治理系统。

## 把角色映射到现有工具

- 决策会话只保留目标、取舍、结论和下一步。方案用人话写清做法、风险和验收，不复述需求，也不堆无关细节。
- 能使用多个 Agent 时，执行与审查分开，审查结论再回到决策会话。只有一个 Agent 时，用一次独立的只读审查代替，不要求订阅原片中的产品。
- 仓库已有分支或 worktree 时，一个功能使用一条独立线。没有时使用现有 PR 流程，并记录不能并行的原因。
- 当前模型按实测效果选择。原片的 Claude、Codex、Gemini、GPT 分工只说明角色可以分离。

## 人介入的时机

出现以下情况就停止扩大修改：

- 同类问题在审查或两个功能中重复出现。
- 新功能明显变难，或交互和样式偏离既有规范。
- 缺陷多轮仍没有稳定复现和验证。
- 局部修改触发了全量或超长测试。

先取得核心判断、反证和验证步骤。结论冲突或继续修改会增加维护负担时，由人缩小范围、更换实现或取消功能。不使用无法达到的指标驱动反复优化。

## 证据规则

每条证据都要能由另一个 Agent 重新打开或重新运行。仓库路径写绝对路径或仓库相对路径；命令写完整命令和通过时的关键输出。只写“已检查”“看起来正常”不算证据。

诊断阶段至少区分五类信号：测试耗时来自实际运行，文档冲突来自文件差异，界面漂移来自现有组件和新增实现的对比，重复实现来自两处代码，发布缺口来自现有 CI、版本或回滚配置。没有读到对应文件或运行结果时，该信号保持未知。

方案阶段不要求固定版式，但六个答案必须可独立核验。验收方式必须是一条命令、一个测试名称或一条人工操作；“后续再看”不是验收方式。

执行阶段的功能记录要能回答三条：代码在哪条分支或工作区、改了哪些模块、用什么命令验证。审查阶段的四项结论各自引用证据，不能用一句总评代替。验证阶段没有人工签收就保持打开。治理阶段只改仓库已经承认的规则文件；没有规则文件时，把候选条目留在最终回复里。发布阶段只检查现有门禁和回滚路径。

## 工作中的判断

先把请求分成三类。第一类是一次就能结束的编码或审查，完成后退出。第二类是要求指定模型产品、供应商或版本，也直接退出，不把原片听写结果改写成可配置模型。第三类才是长期治理：项目会反复新增功能，而且已有证据显示流程正在退化。

进入第三类后，不按八个阶段平均展开。诊断结果决定路线。测试变慢就走测试门禁，文档过期就走治理门禁，界面不一致就先收规范，发布事故就只查现有回滚。多个信号同时存在时，先处理会阻止其他工作验证的信号，例如无法运行的测试或无法回退的发布。

每个结论都要能回到一个文件、一段差异、一条命令或一次人工签收。Agent 可以起草比较和修复，但不能替负责人宣布体验合格，也不能在证据不足时把下一阶段标记为通过。仓库缺少某种机制时，缺口本身就是该阶段的产物；补机制必须等负责人决定。

## 交付

报告本次实际经过的阶段、证据路径、未启用的阶段和原因。缺证据写“未验证”，不写“已完成”。

记录使用这些固定字段：

```text
阶段:
产物:
证据:
通过条件:
缺口:
下一步:
```

记录格式见 [references/record-template.md](references/record-template.md)。三个典型请求的走法见 [references/examples.md](references/examples.md)。用 [scripts/check_record.py](scripts/check_record.py) 检查阶段记录。

人工签收使用：

```text
验收人:
时间:
关键路径:
结果: 通过 | 退回
```
