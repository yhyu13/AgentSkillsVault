# 阶段门禁

只检查本次启用的阶段。未启用的阶段不补做。任一阶段缺少必需产物，就停在该阶段。任何门禁都先寻找仓库已有机制；没有机制时记录缺口，不发明新的平台、分支模型或发布系统。

## 诊断

既有项目先查五项证据：测试耗时、文档与代码冲突、界面或样式漂移、重复实现、发布或回滚缺口。每项记录文件路径、命令或检查结果。没有证据的项目不进入对应治理阶段。

## 范围

- 请求是单次修复、普通审查或模型选型：立即退出。
- 要求指定具体模型、供应商或模型版本：立即退出，不输出任何模型 ID。
- 请求涉及多轮迭代时，写明本次只治理哪个具体问题，例如测试变慢、界面规范漂移或发布不可回滚。

## 调研

- 已有可运行项目：记录当前技术栈、测试入口、发布入口和许可证约束，并写“本次不重选技术栈”。
- 新项目或用户要求换底座：比较至少一个可二开候选和从零实现。记录修改、商用、闭源义务，以及性能和维护依据。
- GPL、AGPL 等会影响派生作品的许可证单独标出。

## 方案

负责人必须能独立回答：

1. 用户最终能做什么？
2. 界面或操作如何变化？
3. 改哪些模块？
4. 异常和边界如何处理？
5. 哪些事项需要人决定？
6. 哪条命令、测试或人工步骤算验收？

缺一项就停在方案阶段。

## 执行与审查

- 有 worktree 或分支流程时，每个功能一条独立线，合并前处理冲突。
- 只有单分支或 PR 流程时，沿用它，不临时复制仓库。
- 审查记录四项证据：端到端行为、是否重复或绕路、测试是否验证需求、是否复用既有组件和函数。
- 多个 Agent 可用时，执行者和审查者分开；只有一个 Agent 时，先做只读审查再修改。

## 测试

- 找到仓库现有的局部测试和全量测试入口。
- 局部修改运行受影响入口；完整功能完成后才运行重型回归。
- 人工签收记录验收人、时间、关键路径和结果。没有签收时停在验证，不能由 Agent 自行标记通过。
- 没有分离入口时，把“拆出受影响测试”列为候选改动，不在一次功能开发中强制重做测试框架。
- 重复的人工调试链路可以收成参数化命令，但只收本次实际重复的链路。
- 删除测试前要证明它只重复语言或框架保证的行为，且失败不能区分产品回归。

## 治理

- 重复失败优先写入仓库已有的 `AGENTS.md`、审查清单或规范文档。
- 没有这些文件时，先在最终回复给出建议条目，等待用户决定是否新增权威文件。
- 颜色、间距、组件和交互以现有设计来源为准。来源冲突时列出冲突，不自行指定新的视觉系统。
- 代码与文档冲突时以当前代码为准，随后删除或改正过时文档。

## 发布

- 使用仓库已有的测试、版本、标签、CI 和回滚机制。
- 没有程序化门禁时，列出最小缺口，不在本次任务中新建部署平台。
- 只有存在可发布的客户端或服务时，才要求检查安全模式、降级或回滚提示。
