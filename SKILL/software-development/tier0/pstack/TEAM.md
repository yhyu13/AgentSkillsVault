# pstack 团队手册

这套东西不是只给 agent 看的提示词。人和 Cindy 伙伴看同一套规矩，用同一份任务工作区，按同一套证据标准验收。目标是把“agent 说做完了”变成“任何人都能复核它确实做完了”。

## 一、五个角色

| 角色 | 谁来做 | 必须做的事 | 不能做的事 |
|---|---|---|---|
| Owner | 人 | 定目标、范围、验收、风险级别；批准不可逆动作；决定是否加范围 | 把验收标准留给 agent 猜 |
| Driver | agent | 复述目标、选 playbook、写计划、执行、写证据、跑检查 | 没证据就说完成 |
| Reviewer | 人或其他 agent | 看 diff、看证据、跑关键检查、逐条回复评审意见 | 只看“我觉得”或只看代码风格 |
| Verifier | 独立的人或 agent | 按验证 skill 驱动真实产品，采集证据；高风险任务不能和 Driver 同一人 | 用“应该可以”代替实际运行 |
| Maintainer | 人/agent | 定期跑 `maintain-verification-skill`，更新功能地图，清理过期规则 | 让功能地图腐烂 |

小任务可以一人兼多角，但高风险任务必须把 Driver 和 Verifier 分开。黄色和红色任务必须有 Owner 参与。

## 二、任务生命周期

```text
intake
  -> task.md（目标 / 范围 / 验收 / 非目标 / owner / 风险级别）
  -> plan.md（playbook / 步骤 / 验证 / 风险 / 角色）
  -> 执行，证据持续写入 evidence/
  -> result.md（改了什么 / 证据 / 验证 / 风险与回滚 / 状态）
  -> pstack check 通过
  -> reviewer 复核
  -> 合并
  -> 复盘：哪些规则该更新，哪些该删
```

每个阶段都有退出条件：

- intake 退出：`task.md` 的验收标准可判定，非目标写清楚。
- plan 退出：playbook 已匹配，每一步有验证方式，风险已分级。
- 执行退出：验收逐条满足，证据可复跑。
- 检查退出：`node <pstack>/scripts/pstack.mjs check <id>` 退出码为零。
- 复核退出：没有未处理的评审线程，风险与回滚已确认。

## 三、证据标准

可接受的证据：

- 命令输出，带退出码和完整命令。
- 测试日志，能看出跑了哪些用例、哪些失败。
- 截图或录屏，能看出用户可见的结果。
- 测量数字，带口径、方法、样本量、误差。
- 复现步骤，reviewer 按步骤能复现。
- diff 或补丁，能看出改了什么、没改什么。

不可接受的证据：

- “我跑过了。”
- “应该没问题。”
- “编译通过了。”
- 只贴成功的那一行，不贴命令和退出码。
- 用 mock 或代理指标冒充真实产物。
- 截图只截局部，看不出是哪个环境、哪个版本。

证据放在 `.pstack/tasks/<id>/evidence/`。大文件可以放外部存储，但 `result.md` 必须给出可访问的链接和校验方式。

## 四、完成定义

一个任务只有同时满足以下条件才算完成：

1. `task.md` 的验收标准逐条满足。
2. 非目标没有被顺手改。
3. `evidence/` 非空，`result.md` 链接到证据。
4. `pstack check` 通过。
5. 用户可见行为变化时，功能地图或验证 skill 已更新。
6. 风险和回滚写清楚。
7. 没有未处理的评审线程。

不满足就写 `blocked.md`。阻塞不是失败，假装完成才是。

## 五、风险分级与门禁

| 级别 | 判据 | 需要谁批准 | 额外要求 |
|---|---|---|---|
| 绿 | 可逆、局部、无共享状态、自动检查齐全 | 一个 reviewer 或自检 | 证据齐全即可 |
| 黄 | 共享代码或 API、迁移、用户可见变化、跨模块 | 一个 Owner 指定的人类 reviewer | 计划先确认，证据必须可复跑 |
| 红 | 不可逆、安全、删数据、生产部署、客户消息 | Owner 明确批准 | 回滚方案、Verifier 独立、操作前备份 |

红色任务的批准必须是明确文字，不是“你看着办”。批准记录写进 `task.md` 或 PR 描述。

## 六、人和 agent 怎么配合

### 人给 agent 的输入

至少给四样：

1. 目标：用户可感知的结果。
2. 验收：怎么判定做完了。
3. 范围：动什么，不动什么。
4. 约束：安全、合规、时间、不能碰的东西。

可以只说“按 pstack 规矩做”，agent 应该主动补齐这四样并向你复述。复述不对就纠正，不要让它带着错误理解开工。

### agent 给人的输出

至少给四样：

1. 目标复述和最小改动。
2. 选了什么 playbook，为什么。
3. 改了什么，证据在哪。
4. 风险和回滚。

人不需要看全部过程，但必须能通过 `task.md`、`plan.md`、`result.md` 和 `evidence/` 复核。

### 什么时候人可以打断

- 不可逆动作之前。
- 发现验收标准错了。
- 发现 agent 在猜而不是在验证。
- 发现范围膨胀。
- 发现同一个问题修了两次还没修好。

## 七、周维护

每周或每个迭代做一次：

1. 跑 `pstack check --all`，看有没有长期 blocked 或证据缺失的任务。
2. 对活跃项目跑 `maintain-verification-skill`，更新功能地图。
3. 看 `HOST-ADAPTER.md` 有没有新的宿主能力或降级项。
4. 看 `models.md` 的模型映射是否还可用。
5. 把重复出现的教训编码进模板、检查脚本或规则，不要只写在聊天里。

维护也是任务，走同一套 `task.md` 和证据。

## 八、采纳路径

### 第一天

- 把 `pstack` 技能装进团队的技能库。
- 每个人读 `README.md` 和本文件。
- 选一个绿色小任务，完整走一遍 intake 到 check。
- 复盘：哪一步多余，哪一步不清楚。

### 第一周

- 所有非琐碎任务都建 `.pstack/tasks/<id>/`。
- 每个 PR 描述带 `## Why`、`## What changed`、`## Verification`。
- 至少一个黄色任务走人工 reviewer。
- 建第一个项目级验证 skill。

### 第一个月

- 活跃项目都有功能地图。
- 红黄绿分级成为默认。
- 每周维护一次功能地图。
- 把团队自己的补充规则写进 `RULES.md` 的扩展区，不要散落在聊天里。

## 九、升级和阻塞

- 没有匹配的 playbook：走 `figure-it-out`。
- 缺关键信息：写 `blocked.md`，说明缺什么、需要谁、什么时候需要。
- 规则冲突：硬规则优先，冲突写进 `task.md`。
- agent 不同意：给理由和证据，人来决定。
- 连续两次修复失败：停下来，回到 `principle-attack-the-premise`，检查前提，不要加第三个修复。

## 十、这套规矩的边界

- 它不替代代码评审、测试、安全审计和发布流程。
- 它不保证 agent 一定正确，它保证错误更早暴露、更容易复核。
- 它不要求每个小改动都走全套流程，但要求每个“完成”都有证据。
- 它不绑定 Cursor、Claude Code、Grok 或任何插件市场。宿主能力不够时按 `HOST-ADAPTER.md` 降级，并记录缺口。
