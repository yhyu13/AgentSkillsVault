# PR 闸门：让改动无法绕过审查

说明书和代码用同一套门，不需要新工具。缺哪一道，就补哪一道。

## 五道门

| 门 | 具体做法 | 拦的是什么 |
|---|---|---|
| 受保护分支 | Skill 文件放主分支保护下，禁止直推 | 定时任务直接改生产 |
| 状态检查 | 机械闸 + 回归集作为必需检查 | 大改、无证据、链接断、密钥 |
| 人审 | 至少一名 owner approve，写清读了 diff | 橡皮图章与「全绿即合并」 |
| 审批失效 | 新 commit 后旧 approve 自动作废，需重新审 | 先批后改 |
| 回滚路径 | PR 正文写明 revert 命令与影响面 | 「改坏了怎么办」没人答 |

## PR 正文模板

见 `templates/pr-body.md`。必须有六块：

1. **触发的失败证据**：会话 id、维度、一句话引用。
2. **缺口**：缺少或写错的那条规则，说的是哪个表面。
3. **改动**：改前 / 改后各一两行，行为差在哪里。
4. **回归**：harness、基线、结果；没有 harness 就写人工抽检。
5. **风险与回退**：可能影响哪些任务，`git revert` 后恢复什么。
6. **审查请求**：点名的 reviewer 与需要他判断的问题。

## 一次 PR 只做一件事

- 一处规则、一个文件、一个目的。批量改动无法 review，也无法单独回滚。
- 标题格式：`skill(<name>): <规则一句话> [evidence: <session_id>]`。
- 描述里不要贴长会话原文，一句话 + 会话 id 足够；需要细节的人自己回查。

## 审查者该看什么

不要只看「有没有错别字」。按顺序问：

1. 这条规则确实缺失吗？现行文件里真的没有，或写在没人读的位置？
2. 这条规则放在这个文件里吗？还是应该放仓库规范、CI 配置或产品侧？
3. 改动够小吗？能不能更小？
4. 会不会与已有规则冲突或被误读成更宽的范围？
5. 回归是否能覆盖这次失败？没有的话，上线后怎么抽检？

任何一项答不上来，就不合并。**批准意味着你愿意为这条规则带来的行为负责。**

## 合并之后

- 记录合并时长、每个 PR 的成本与质量分，作为回路健康度指标（比「改了多少条」有意义）。
- 同一缺口第二次复发，说明改动没生效或没被读取，先查规则放的位置，别再叠规则。
- 每季度清理一次：删掉过期补丁、合并重复规则、把机械可判的规则降级成脚本。

## 定时任务的安全边界

- 定时任务只允许**开 PR**，不允许合并，也不允许直推。
- 一次运行最多开一个 PR；没有合格证据时开零个，并在报告里说明。
- 失败时停，不发通知轰炸，不自动重试破坏分支状态。
- 任务使用的凭据只能访问目标仓库的必要范围，不携带会话原文。
