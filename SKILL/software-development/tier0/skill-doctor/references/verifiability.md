# 可验证性与回归

先回答一个问题：这次改动**能不能被机器判定好坏**？答案决定回路能自动到什么程度。

## 两类任务，两套做法

| 类型 | 例子 | 做法 | 合并条件 |
|---|---|---|---|
| 可验证 | 改完代码能跑测试、能比对结构化输出、能跑静态检查 | 先搭评测环境与参考语料，改前改后各跑一遍 | 全绿 + 人审 |
| 不可完全验证 | 代码评论质量、文案、方案判断 | 黄金输出集 + 领域专家逐条看 | 必须人点头，没有例外 |

顺序不能反：**harness 没搭好之前，别让 Agent 自己挑自己。** 没有裁判的训练只会跑偏：它会学会让自己
通过的写法，而不是让任务通过的写法。

## 可验证任务的 harness 清单

1. **一组能重复跑的任务**（固定输入，最好来自真实失败会话）。
2. **判定器**：优先代码检查（快、客观、可审计）；再退到结构断言（字段、数量、退出码）；最后才用模型评分。
3. **基线**：改动前的通过率与失败分布，落盘保存。没有基线就没有「变好」。
4. **成本记录**：一次回归跑了多少调用、多少分钟。改一条规则让回归贵十倍，是不划算的。

回归结果要能回答三件事：原先失败的那几条现在过了吗？哪些原先通过的现在挂了？挂的是判定器抖动还是
真实退化？

## 不可验证任务的黄金集

- 20–50 条**真实输出**，由领域 owner 逐条打过「可接受 / 不可接受」并写明理由。
- 改动后重新生成同样输入，逐条对比。允许「等价改写」，不允许「理由变了但结论没变」。
- 新增一类失败，就把它的样本补进黄金集。黄金集只增不减，除非该场景已从产品里下线。

## 三种评分器搭配

这是 Anthropic 评估指南里的分工，落到本 Skill：

| 评分器 | 强项 | 用法 |
|---|---|---|
| 代码检查 | 快、客观、可复跑 | 每次改动都跑，作为第一道回归 |
| 模型评分 | 能抓模糊地带 | 抽样跑，人工抽查评分理由 |
| 人工评审 | 金标准，也最贵 | 校准模型评分 + 最终合并决定 |

不要用其中一种替代另外两种：只用代码检查会漏掉判断类退化，只用模型评分会被措辞骗过去，
全靠人评审则跑不动。

## 回归失败怎么处理

1. 判定器本身有问题 → 先修判定器，撤回本次改动，说明原因。
2. 改动导致真实退化 → 在同一个 PR 里修，或直接 revert。
3. 黄金集样本本身有争议 → 停下，交领域 owner 决定，别在 PR 里悄悄改样本。

## 没有 harness 时怎么办

允许做「小步上线 + 人工抽检」，但要写清：

- 改动只覆盖一处规则，行数尽量少，便于 review 与回退；
- 上线后 3–5 个真实任务内抽检，把结果记进同一份报告；
- 一旦出现同类失败，优先 revert，而不是再叠一条新规则。

## 回归记录写在哪

PR 正文 + 报告目录：

```text
harness: pytest tests/agent_contract  (34 cases)
baseline: 27/34 pass
after:    33/34 pass, 0 regressions
reviewer: @owner (domain), 2026-11-17
```

没有这几行，PR 不算完成。没有 harness 时，写「人工抽检 5 条，4 通过，1 条记录为已知限制」。
