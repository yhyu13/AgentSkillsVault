# 改动纪律：四个动作与最小 diff

一句话：**把 Agent 的每一次改进，当成一次代码提交来管理。**

## 四个动作

| 动作 | 含义 | 反例 |
|---|---|---|
| 可对象化 | 变化是文件上看得见的几行修改 | 在对话里口头「记住」、存进数据库或向量库 |
| 可审 | 走 PR、走 CI、走分支保护，人有一票否决权 | 定时任务直接改生产文件 |
| 可回滚 | 坏了 `git revert` 就恢复 | 只留一份「最新版」，旧行为无从找回 |
| 有证据 | 每条修改背后挂着触发它的失败案例 | 拍脑袋写「最佳实践」 |

四个动作都不需要新工具：Git 与 CI 早就准备好了。缺的是把它们用在说明书上。

## 为什么必须落到文件

| 载体 | 结局 |
|---|---|
| 提示词 | 随会话蒸发，下次从零开始 |
| 数据库 / 向量库 | 黑箱，改了什么、为什么改说不清 |
| 文件（Git 管理） | 有 diff、有 review、有历史、可回滚，成为团队资产 |

## 最小 diff 的写法

- **一处改动只表达一条规则。** 两个独立问题开两个 PR，不要捆绑。
- **替换优先于追加。** 旧句错了就改旧句；在末尾再补一句同义提醒，只会让文件变长、优先级变糊。
- **给行为，不给形容词。** 「交付前跑本次改动涉及的目标测试」可执行；「要更认真」不可执行。
- **写原则，不写死步骤。** 「优先消掉重复代码」比列 200 条命名规范更能约束判断，也更耐模型换代。
  只有那些结果必须逐字一致的操作，才写成硬步骤或脚本。
- **能交给脚本的，不交给判断。** 计数、排序、校验、格式化写成脚本，只把结论交回给模型。
- **不加无主的规则。** 每条规则要能指认「谁负责这份文件、为什么需要它」。指不出来就别写。
- **行数上限。** 单次改动默认不超过 30 行或原文 20%（取较大者）；超过就拆。机械闸按这条判。

## 版本与退役

- 行为有变化就 bump `version`，同一版本号下悄悄改行为，等于让 review 失效。
- 新增规则时，顺手检查有没有被它取代的旧规则；有就删，别并存。
- 模型换代后，先删「为了弥补旧模型弱点」的补丁，再看还需不需要新规则。补丁会过期，原则不会。

## 记忆与 Skill 不要混

- **Skill**：流程与判断原则，相对稳定，改动要慎重，进版本控制。
- **记忆**：推理时的随手写，一直在变，属于运行时状态。

把「这次发现的临时事实」写进 Skill，会让说明书变成日记；把「团队流程」放进记忆，会在下一次会话
消失。两者分开存放，各有各的更新节奏。

## 回滚路径

PR 正文必须写清：

```text
revert: git revert <sha>   → 恢复改动前的说明书与本条 PR 的全部行为
```

同时确认：回滚之后，触发这条规则的那批失败会话会复盘吗？如果会，说明回归集需要补样本，而不是
让规则带着缺陷上线。
