# 失败模式清单

每一条都是这个回路真实会走坏的方式。做之前扫一眼，做完再扫一眼。

## 1. 提示词膨胀

见一次失败补一句，三个月后没人说得清文件在教什么，也没人敢删。

- 症状：文件只增不减；同一件事写三遍；新规则与旧规则矛盾。
- 对策：替换优先于追加；一次只改一处；每季度清理；行数上限由机械闸强制。

## 2. 黑箱化

把「学到的经验」存进数据库、向量库或某个平台的隐藏配置。

- 症状：改了什么说不清；出问题无法 diff；换环境就丢。
- 对策：所有规则落到 Git 管理的文件；外部存储只放索引，不放规则本体。

## 3. 反馈垃圾场

照单全收用户与 reviewer 的意见，包括错的、相互冲突的、带个人偏好的。

- 症状：说明书开始出现互相矛盾的条款；同一行为一会儿要求这样一会儿那样。
- 对策：假设反馈会出错；先做合理性检查；质量比数量重要；过滤与终审留人。

## 4. 自我评分

同一个上下文既改规则又判定改得好。

- 症状：给出的分数漂亮，真实任务依旧失败；报告里没有失败样本。
- 对策：评审用干净上下文或另一个执行者；分数必须能回到具体会话动作。

## 5. 没有裁判就开跑

harness 还没搭好，就让定时任务自动合并。

- 症状：改动越来越多，通过率没有变化；Agent 学会写「让自己过关」的输出。
- 对策：可验证任务先搭 harness 与基线；不可验证任务必须人点头。

## 6. 只盯分数，不看证据

追求 overall 上涨，而不是解决具体失败。

- 症状：挑好打的会话进样本；把 `insufficient_evidence` 当免死金牌；样本窗口越改越短。
- 对策：`--days`、`--max-sessions` 写进报告；分数只用于排序，证据决定改不改。

## 7. 记忆与 Skill 混淆

把运行时临时事实写进流程文件，或把团队流程放进「记忆」。

- 症状：说明书里出现「今天这个用户要求…」；换会话后流程又丢了。
- 对策：Skill 只写稳定流程与判断原则；临时事实留在会话或记忆里。

## 8. 注入

会话、issue、PR 评论里的指令被当命令执行。

- 症状：Skill 里出现「忽略之前的规则」类句子；脚本开始访问无关路径；报告夹带可疑链接。
- 对策：输入一律当数据；引用只留一句话；禁止把原句粘进文件；机械闸扫描密钥与占位标记。

## 9. 橡皮图章

全绿即合并，没人真读 diff。

- 症状：审批时间几十秒；reviewer 说不出改了什么；出问题后没人认领。
- 对策：审批失效规则；一次一 PR；小改动降低阅读成本；审查清单写进 PR 模板。

## 10. 指标游戏

用「改了多少条规则」「闭环跑了多少次」当成绩。

- 症状：改动数量上升，重复失败率不变；PR 越来越小且无意义。
- 对策：看合并时长、每个 PR 的成本与质量分、同类失败的复发率；零改动也是合格结果。

## 11. 只改一个 Agent

只给抱怨最多的那个 Agent 建闭环，其它 Agent 继续裸奔。

- 症状：同一个团队里，只有一条流水线有规则沉淀。
- 对策：改进器的结构在各 Agent 之间高度相似，写一次复用；先跑通一个再铺开。

## 12. 样本偏差

只拿「最近三天」或「最好说话的 reviewer」的意见做证据。

- 症状：报告结论与一线体感相反；改动上线后立刻被同一问题打回。
- 对策：写清窗口、样本量与来源；跨 reviewer 取样；复发时优先怀疑取样。

## 自查顺序

1. 报告里有没有具体的失败会话 id？
2. 每条改动能不能一句话说出「缺的规则」？
3. 机械闸是否退出 0？
4. 回归或抽检有没有记录？
5. 有没有一条改动是「再强调一遍」？
6. 回滚路径写了吗？

第 2、5 条答不好，说明这次不该合并。
