# Companion configuration and operational state

The public market-intel repository describes sources, capabilities and installation
options. A separate PRIVATE companion repository stores the operator's configuration,
installed-tool inventory, account details and real runtime DATA. Keeping these separate
allows the public tool to remain uninitialized and reproducible.

The [formal configuration contract](companion-config-spec.md) defines registry and
template formats. The [current-session evidence contract](host-capabilities.md) defines
when a selected operation is available. Configuration conformance and historical
inventory do not establish current execution, authorization or useful response content.

## Locate and validate the companion

Follow [CONFIG.md’s discovery order](../../../CONFIG.md#discovery-convention-e2):
`MARKET_INTEL_DATA_DIR`, `MARKET_INTEL_CONFIG`, then the
fleet_guards sibling convention. There is no home-directory location and no separate XDG search.
`MARKET_INTEL_DATA_DIR`, when set, must select the same companion’s existing `data/`
child. Explicit invalid or conflicting selectors fail without choosing another root.
A resolved path does not by itself prove configuration readiness or PRIVATE storage.

Before storing real configuration or DATA, confirm once during setup that the
repository is PRIVATE (see the hardening runbook). The runtime only checks that the
resolved destination is inside a Git worktree outside this source tree; the commit
and push hooks enforce PRIVATE publication. A loose directory is not a companion. The
consumer DATA resolver and `CONFIG.md` define the current DATA location contract;
never fall back to a path inside the public source checkout.

Without a configured companion, catalog browsing still works. Research can inspect
tools exposed by the active host and verify a selected read-only operation directly.
Missing inventory does not prove missing host capability. Real outputs still require
the PRIVATE destination.

## Initialize a configuration

Locate the full market-intel checkout before invoking its maintenance scripts.
`scripts/init_config.py --out <absolute-companion-path> --mode B` creates an empty
configuration skeleton. It currently supports Mode B only; Mode A fails before
creating output. The empty registry remains NOT READY until the selected installed tools and their
required templates are configured. Initialization and `scripts/verify_config.py`
check configuration shape, not provider authentication or operation readiness.

The skeleton includes:

- `registry.json` with an empty `tools` list;
- `tools/` for per-tool templates and configuration records;
- `secrets/` for private credential storage and a storage-mode declaration;
- `.gitignore` patterns appropriate to Mode B.

Review the generated files before adding real state. Configure and verify the PRIVATE
remote, then follow the companion's supported credential capture and application
procedure. Keep values out of command arguments, terminal output and public examples.
Public fixtures must be synthetic and generated by `tools/make_fixtures.py`.

## Configuration records and evidence

The registry records what was configured, installed or observed at a particular time.
`health_last` and `health_checked` are historical inventory fields. An import proves
library availability; a transport handshake proves transport behavior. Neither proves
the required source operation worked or returned valid content.

For the selected operation, discover callable tools in the active Claude or Codex
session and verify execution, authentication and content. Preserve host, session,
source, capability, timestamp and method attribution according to
`host-capabilities.md`. A separate `claude mcp list` process provides only installation
diagnostics and cannot attest another host or the current session. Avoid configuration
inspection commands that may echo credentials.

Keep real observations, account records, research history, caches and exports in
PRIVATE versioned DATA. No live data or private fallback copy belongs in the
public matrix. Read-only consumers may report uninitialized state; writers must fail
with setup guidance when a private destination cannot be established.

## Credential storage policy

The configuration spec describes two operator-selected modes:

- **Mode A:** credentials are versioned in the PRIVATE repository. Rotation
  means rotating the credential itself; replacing a file does not remove old values
  from Git history.
- **Mode B:** credentials are excluded from Git and backed up through a separate
  private mechanism. Recovery requires both the repository and that backup.
  A vault projection is the variant the reference deployment uses: an encrypted
  credential vault outside the companion holds the values, `secrets/<slug>.env` is a
  generated gitignored projection per tool, and capture or registration writes to
  the vault and regenerates the projection. Do not edit, commit or hand-restore the
  projected files; recovery restores the vault and its key, then regenerates them.

Document the selected policy in `secrets/README.md` and use tooling that supports it.
The initializer's current Mode B limitation does not prohibit a separately implemented
Mode A companion. Provider behavior and the Git host's current scanning policy should
be verified instead of inferring automatic revocation from a token prefix.

The choice concerns credentials. Real runtime DATA still belongs in a versioned
PRIVATE companion under either mode. Check the existing repository policy before
changing ignore rules, hooks, scanning settings or backup behavior; do not disable a
gate to make a credential operation pass.

## Verification and recovery

Validate configuration structure, then separately test the required operation through
the active host. Record each result at its actual scope. Keep failure types visible;
an empty result is useful only when the request completed and its content was valid.

Before reporting recovery complete on a new machine, verify the selected credential
policy's restore path and run a bounded authorized operation. A successful clone,
installed binary, import, or registry entry alone is not a recovered service.
