## 4 · 约束（硬红线）

1. **零外部资源**：B 组产物不许下载模型/贴图/HDRI/天空盒；一切像素在代码里生成。
2. **单 HTML**：不许 `import` / ESM `export` / 外部 `<script src>` / 外部 `<link href>`；three.js 内联。
3. **确定性**：不许 `Math.random()`；seeded PRNG，种子从 id 派生或写死为常量。
4. **不写死坐标/数字**：岛的量只能来自 `shape.json` / `scene.schema.json` / `style.json`。
5. **判据必须可证伪**：任何统计量都要能回答「什么样的坏输入会让它转红」；**不许恒为 0 的假通过**；缺参数必须显式转红。
6. **「不适用」≠「通过」**：没跑的检查要**明写没跑**。
7. **只认机器读数，不认文档里的 ✅**：完成度靠脚本复算。
8. **看图**：截图必须**逐张看过**才能说「画面成立」。
9. **行尾**：Windows 上写文件一律 `newline='\n'` 或 `write_bytes`（`Path.write_text()` 会把 LF 翻成 CRLF）。
10. **行尾引号**：写 `Path.write_text()` 之前先确认目标文件原本的行尾风格；不翻转已跟踪文件。

## 6 · 口径（本次实验的公平性设计）

- **几何输入相同**（同一 `shape.json`）⇒ 隔离变量是「场景怎么被生成出来」：
  - A 组 = 数据（蓝图）→ 通用引擎 → 装配；
  - B 组 = 按 skill 方法论（Clay 白模 → Full 全程序化）写的场景代码。
- **材质/调色板不同不是实验误差，是路线差异**（A 从概念图量调色板，B 程序化生成）—— 但必须在报告里**明写这个混淆项**。
- 完成度口径：达成 = 1 / 部分 = 0.5 / 未达成 = 0；「不适用」不计入分母，也**不等于通过**。
- 引用分级：`[来源: 1-官方]` / `[来源: 2-权威媒体]` / `[来源: 3-博客]` / `[来源: 4-社媒]`；4 级只作线索，不能单独成立。
- 核心依据 ≤ 2 级才可写「高确定性」。

## 7 · 本轮实测补充（2026-11-01 · 第一次真跑这个 prompt 的教训）

上面 §4 的红线是**写下来的**，这一节是**跑出来的**——每一条都是闸自己犯的错，
而且**全都表现为「判绿」，不表现为「判红」**。

| # | 坑 | 机制 | 修法 |
|---|---|---|---|
| 1 | **「外部请求 = 0」恒为 0** | 闸里 `external = []` 收集了请求，**但没写回 `out`**；判定时 `None` ⇒ 当 0 ⇒ 有没有外部请求都绿。**被测方自己反而有更严的检查**（`performance.getEntriesByType('resource')`）⇒ 闸比被测方弱 | 读数**必须写回**再判定；配负对照：注入 `<img src="https://example.invalid/…">` + `fetch`，必须转红 |
| 2 | **多机位对比根本没发生** | 机位参数（`?az=…&el=…&dist=…`）是页面**加载时**读的；只 `set_viewport_size` 不重新 `goto` ⇒ **6 张截图是同一张**，而「像素标准差 > 0」照样绿 | 每个机位**重新 goto**；加判据「同尺寸机位 sha256 必须互不相同」+ 负对照（机位全改成同一个 ⇒ 必须转红） |
| 3 | **测的是过期产物** | 闸直接读 `dist/`，不先构建 ⇒ 测的不是当前源码 | 测之前先构建；构建失败直接 exit 2 |
| 4 | **跨 agent 抢目录** | 闸把截图写进被测 agent 的目录 ⇒ 产物互相覆盖，谁也说不清哪张是谁的 | 闸的输出统一落 `.cache/`；对方目录由 owner 清。**源码之外的产物也算文件所有权** |
| 5 | **读数口径不统一** | `info.get('render', info.get('calls'))` 在 `render` 是 dict 时返回 **dict**；三角形读到带小数的值；A 侧自检表**根本不提供渲染帧时间**（只有「单帧生成 ≤ 16.667 ms」，那是生成耗时） | 两种形状都认；三角形优先 `scene.triangles_est` 并标来源；缺失写「本侧不提供」，**绝不写 0** |
| 6 | **探针脏了被测方的画面** | 注入的 `<pre id="__probe_out">` 是可见元素 ⇒ 截图顶部裸露一行 JSON | 注入后把它设 `display:none!important`（只改副本，不动被测产物） |

### 7.1 · 必须机器验证的「实验前提」

A/B 的全部意义建立在「**只变了一个变量**」上 ⇒ 这个前提本身**必须机器验证**，不能靠读代码：

> **跨组契约**：两份产物内嵌的 `window.__SHAPE` **规范化后逐字节相同**
> （JSON parse → `sort_keys` + 紧凑分隔符 → sha256）。
> A 组是多行 pretty-print、B 组是单行 ⇒ **比原始文本必然假失败**，要比语义。
> 这一条不通过 ⇒ 整个 A/B 无效（哪怕所有读数都绿）。

同理还要验证「A、B 读数是不是同一口径」——口径不同就**不能比**，
写进表里的两个数字必须各自标出来源。

### 7.2 · 「不适用」不等于「通过」，也不等于「0」

A 组自检表**没有**渲染帧时间这一行 ⇒ 表里就写「本侧不提供」。
填 0 会被读成「快得离谱」或「没测过但绿」，两种都是**假读数**。

### 7.3 · 结论怎么写

- **只列读数，不判定优劣** —— 优劣靠**逐张看图**。
- 视觉差异是**路线差异**（材质/调色板不同），不是实验误差 ⇒ 必须在报告里**明写这个混淆项**。
- 公开基准里的「一句话做游戏」分数往往**自带 skill 辅助** ⇒ 不能当裸模型能力引用。
- 判定「谁更厉害」之前先分清两件事：**生成能力** vs **可验证性**（逐字节可复现 / 外部请求 0 / 可判定闸表）。
  公开侧至今**未找到**同时满足这三条的游戏产物宣称。

### 7.4 · 判据「恒真」的两种形态，和唯一可靠的解法

判据永远绿（恒真）有两种，症状完全不同：

- **① 读数恒为 0** —— 闸里收集了外部请求数，**但没写回 `out`**；
  判定时 `None` ⇒ 当 0 ⇒ 有没有请求都绿。
- **② 读被测对象自己的账** —— 判据量的是「被测对象用来生成它的那个中间量」，
  差值**结构上**恒为 0。本轮实例：B 组自检表的 `★ 无悬空建筑` 原来算
  `|baseY - groundY(中心)|`，而 `baseY` **就是** `groundY(中心)`
  （落位时同一个函数算出来的）⇒ 恒为 0 ⇒ 这行永远转不了红。

解法只有两条，**两条都要做**：

1. **独立重算** —— 判据用的量，不能是被测对象用来生成它自己的那个中间量。
   本轮把「悬空」改成 `baseY` vs 四角地面高度的**上下包络**
   （`baseY` 走另一条路算，不问落位过滤的账），
   并补一条**只沉不抬**的「埋土」判据 —— 保证它不会顺带把另一条也弄红。
2. **注入坏输入的负对照** —— 当被测系统里有**落位过滤**（把坏输入提前滤掉），
   「摆得对不对」的判据**结构上**无法自己红 ⇒ 必须有一条**真的被加载**的坏输入路径。

⇒ **判据恒真不是「阈值定松了」，是「这条判据没有信息量」。**
⇒ **负对照必须和被验证的闸跑在同一条命令里**，否则它只是某个人的记忆。
   本轮踩过：`--mutations` 原来是个独立模式，闸表里没带 ⇒ 自动化流程里一次都没跑过。

### 7.5 · 比大小之前，先确认两边是同一种单位

本轮另一条 major：闸拿 **shape 的平面像素**半宽去比**世界单位**的半径，
差 `1 / world_scale = 1.667` 倍 —— 而**读数上看不出来**
（24 < 84 看着很正常，24 < 50 才是真的）。

⇒ 比大小之前先问一句「这两个数是同一种单位吗」。
⇒ 换算系数缺失时**显式转红**，不许静默按 1.0 兜底 —— 那正好复现同一个 bug。
⇒ 负对照要挑一个**旧口径会放过、新口径会转红**的坏输入，
  才能证明修的是**口径**而不是阈值。

### 7.6 · 字段名也要审计

同一个字段名在两个文件里量的是两件事 —— 本轮：`determinism_identical`
在**建工具**里是「两次**独立加载**」（强口径），在**闸**里是「同一次加载内连拍」（弱口径）。
⇒ 闸实际断言的永远是**最弱**的那条，而强口径算出来了却只当读数打印。

⇒ **判据从「读数」升级成「契约」的那一刻，它的负对照必须同批补上。**
⇒ 同名字段跨文件复用时，先确认两边量的是同一件事。
