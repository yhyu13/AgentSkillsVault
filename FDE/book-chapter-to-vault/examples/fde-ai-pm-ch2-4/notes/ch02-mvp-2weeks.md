# 第二章 · 快速原型——两周交付 MVP

> **本章定位**：FDE 的核心动作不是"写代码"，而是"判断什么值得写"。两周节奏的 MVP 交付能力，是 FDE 区别于普通外包工程师的入门门槛。
>
> **本章用时**：约 3 小时阅读 + 1 个周末动手（48 小时从零到 Demo）
>
> **本章目标**：把一个模糊的客户需求，两周内变成能跑能看的 Demo，让客户愿意用第二个版本。

## 🧠 核心概念（5 段）

### 概念 1 · 快速原型的本质 = 判断，不是写代码

> **原文金句**：「很多工程师听到"快速原型"第一反应是：不就是把代码写快点吗？大错。快速原型的核心不是写代码，而是判断什么值得写。」

**我的理解**：FDE 的产速瓶颈在"决策密度"不在"键盘速度"。90% 的返工不是因为写错，而是因为一开始就不该写。

**怎么用**：拿到需求后 30 分钟内问自己——"如果我只能写 50 行代码，会写哪 50 行？"这 50 行就是 MVP 的最小骨架。

**复述题**：客户说"我要一个智能客服"，最快的 50 行代码应该长什么样？

---

### 概念 2 · 需求捕获 = 需求五问法

> **原文金句**：「面对任何一个模糊需求，你都要问自己/问客户这五个问题」（指 2.2 节的实操模板——把客户口语翻译成可执行需求）

**我的理解**：模糊需求 = 客户自己也不知道要什么。FDE 的价值不是"接需求做"，而是"把模糊问成清晰"。

**怎么用**：把客户的第一句口头禅（"我们想搞个 AI"）当作信号，而不是 PRD。**80% 的客户会被迫重新思考，20% 会给清晰答案——你两种情况下都赢。**

**复述题**：客户说"我们报表太慢"，你准备问哪 5 个问题？

---

### 概念 3 · 技术选型 = 选最快能跑起来的，不是最酷的

> **原文金句**：「FDE 选技术的核心原则：选你最快能跑起来的方案，不是选最酷的方案。」

**我的理解**：FDE 的反义词是"过度工程化"。React + D3 + PostgreSQL + Docker 听起来很工程，但客户要的是"能先看看"。

**反面案例**：3 周还没部署。**正面案例**：Streamlit + Pandas + CSV，2 天出效果。

**怎么用**：技术栈速查表——
- **能本地跑**：Streamlit / Gradio / FastAPI
- **要存数据**：先用 CSV / SQLite，要正式上线再上 PostgreSQL
- **要部署**：能 Docker 化就先 Docker 化
- **要前端**：能用现成模板就别自己写

**复述题**：你手头要做"内部员工知识库 ChatBot demo"，最快方案用什么栈？预计几天出 Demo？

---

### 概念 4 · MVP 的三条铁律

> **原文金句**：
> - **铁律 1**：先让客户说"yes"。第一个版本的唯一目标是让客户想用第二个版本。
> - **铁律 2**：每行代码都要回答一个问题——写这行代码是为了验证什么？回答不出来就不要写。
> - **铁律 3**：假数据也比没数据好——客户数据太乱？先用假数据搭 Demo。

**我的理解**：这三条铁律是"反完美主义"的操作化表达。FDE 的产品哲学 = 减法哲学。

**怎么用**：写代码前做"减法清单"——
- ❌ 这个错误处理客户真的关心吗？
- ❌ 这个 UI 细节客户能等吗？
- ❌ 这个功能在第二个版本再说可以吗？
- ❌ 假数据能不能骗过客户的第一次验收？

**复述题**：客户数据需要 3 天清洗才能用，但 Demo 明天就要。怎么用"铁律 3"破局？

---

### 概念 5 · 两周节奏 = 双周循环 + 早会三问

> **原文金句**：「两周一版迭代，不要两个月出一个完美产品。」+ 「第三问最重要——帮客户砍需求也是 FDE 的核心价值。」

**我的理解**：节奏感 = FDE 的元能力。客户买的是"看得到进度"，不是"看得到完美"。

**怎么用**：
- **周一早会三问**：① 上周客户用了什么？② 本周要交付什么？③ 上周做的东西里能砍掉哪些？
- **每周交付一个可见版本**（哪怕只是 1 个按钮）
- **每两周一次大复盘**（哪条需求砍了？哪个判断错了？）

**复述题**：第三问为什么是"最重要"的？它解决了 FDE 工作中的什么根本矛盾？

## 🚫 反模式 / 常见坑

| 坑 | 表现 | 危害 | 破解 |
|----|------|------|------|
| **技术选型炫技** | 一上来就上 K8s + 微服务 | 3 周还在搭环境 | 强制 24h 内能跑出 Demo 才允许选 |
| **拒绝假数据** | "等客户清洗完数据再做" | 项目死锁在数据上 | 假数据先跑通 → 真数据替换 |
| **完美主义第一版** | 想做出"客户能直接用"的产品 | 第一个版本 3 个月才出 | 铁律 1：第一个版本 = 让客户用第二个版本 |
| **接模糊需求就开干** | 客户说"搞个 AI"就开写 | 70% 返工 | 需求五问法 30 分钟 |
| **砍需求不好意思** | 客户加需求全接 | 节奏崩盘 | 概念 5 第三问，强迫自己每周砍 |

## ✅ 本周行动清单

> **承诺：读完本章后 7 天内完成以下 5 件事。**

- [ ] **D1** 写一份"需求五问法"模板（Notion / 飞书 / 任何地方），下次见客户直接用
- [ ] **D2** 找 1 个"想搞 AI"的真实朋友（或者就在群里找个痛点），跑一遍五问法
- [ ] **D3** 列出自己过去 3 个月做的项目，按"铁律 2"逐行代码复盘——哪些代码其实不该写？
- [ ] **D4** 用 Streamlit/Gradio 做一个"假数据驱动的 Demo 模板"（任意业务，准备下周复用）
- [ ] **D5** 在自己工作场景里实验"早会三问"——连续 5 个工作日问自己

## 🧪 Self-Test（闭卷）

> **规则**：用大白话回答，不要背原文。答不出就回去重读。

1. 客户说"我想要一个 AI 助手"，你怎么用 5 问把这句话拆成可执行需求？（列出 5 个问题）
2. 客户要"个性化推荐系统"，最快出 Demo 的技术栈是什么？预计几天？
3. 客户数据全是乱码/缺字段，但你明天要给 VP 演示。怎么办？
4. 你做了一个 80 分的 Demo，客户没反应。你接下来一周该做什么？
5. 客户第三周加了个"很重要"的新需求。你的标准回应模板是什么？
