# Amazon · 两个披萨团队（Two-Pizza Team）

> 用两个披萨能喂饱的团队规模，约束出敏捷、自主与发明力

## 核心理念

两个披萨团队解决的核心问题是：**组织规模增长后，如何避免沟通成本吞噬生产力？**

贝索斯的规则极其简单：如果一个团队两个披萨喂不饱，说明团队太大了。这个看似随意的比喻背后，是对组织沟通数学的深刻洞察——团队内沟通路径数 = n(n-1)/2，10人团队有45条沟通路径，20人团队飙升到190条。规模每翻一倍，沟通复杂度接近四倍。

但两个披萨团队不只是"小团队"的别名。它的深层逻辑是**约束催生创新**——贝索斯原话："Constraints breed resourcefulness, self-sufficiency and invention"。当团队小到没有冗余人力，成员被迫自力更生、被迫用更聪明的方式解决问题，发明就从约束中长出来了。这与Amazon领导力原则中的Frugality（节俭）一脉相承——Frugality的定义正是"用更少做到更多，约束激发创造力"。

两个披萨团队还是Amazon组织架构的原子单位，它向上承接单线程领导（Single-Threaded Leader）——单线程领导是100%专职负责一件事的人，两个披萨团队是这个人的建议团队规模；向下催生了AWS微服务架构——当每个小团队需要独立部署、独立迭代时，单体架构撑不住了，微服务成为必然的技术响应。

核心公式：**小规模约束 → 低沟通成本 + 高自主性 + 约束驱动发明**

## 框架结构

```
两个披萨团队 = 约束驱动的组织原子
│
├── 规模约束层
│   ├── 硬规则：6-10人（两个披萨能喂饱）

│   └── 沟通数学：n(n-1)/2，规模与沟通成本非线性增长

├── 目的层
│   ├── 敏捷：小团队决策快、转向快
│   ├── 自主：端到端拥有权，减少跨团队依赖
│   └── 低沟通成本：信息在团队内部高效流转
│
├── 约束创新层
│   ├── 人力约束 → 自力更生（不依赖外部资源）

│

│   └── 单线程领导（STL）—— 两个披萨团队是STL的规模建议
│

│   └── 微服务架构 —— 小团队需要独立部署的技术架构
│
└── 原则呼应
    └── Frugality（节俭）—— 约束激发创造力的领导力原则
```

## 关键模块

### 模块1：规模约束（硬规则与认知依据）

- 定义：团队人数上限由"两个披萨能喂饱"这一具象标准决定，通常6-10人
- 输入：业务需求+功能范围
- 输出：一个端到端负责的小型自治团队
- 关键动作：
  - 用"两个披萨"作为直觉校验——如果午餐订餐需要三个披萨，团队就该拆分
  - 规模上限的底层依据是邓巴数——人类大脑能维持的亲密协作关系约15人，两个披萨团队留出了余量
  - 沟通路径公式 n(n-1)/2 是数学硬约束——不是管理偏好，是组合数学
  - 6人团队15条沟通路径，10人团队45条，20人团队190条——从10人到20人，人数翻倍但沟通成本超四倍
  - 规模不是唯一标准——有些团队5人就够了，有些复杂领域可能需要12人，但超过15人几乎一定违反两个披萨原则
- 常见误区：把"两个披萨"当成精确的数字规则——它是一个方向性约束，核心精神是"足够小以保持敏捷"，不是"必须恰好8人"

### 模块2：约束催生创新（深层逻辑）

- 定义：人力和资源的有限性不是需要解决的问题，而是激发发明力的条件
- 输入：约束条件（人力少、时间紧、资源有限）
- 输出：创造性解决方案和自力更生的团队文化
- 关键动作：
  - 贝索斯原话："Constraints breed resourcefulness, self-sufficiency and invention"——约束催生足智多谋、自给自足和发明
  - 与Frugality原则的直接呼应——Frugality的完整定义："Accomplish more with less. Constraints breed resourcefulness, self-sufficiency, and invention. There is no extra credit for growing headcount, budget size, or fixed expense."
  - 反面验证：资源充足的团队倾向于堆人解决问题而非发明更好的方案——"人多力量大"在创新领域是伪命题
  - Amazon早期没有钱做物流基础设施，被迫发明了第三方卖家平台——约束直接催生了新商业模式
  - 约束创新不是"故意不给资源"——而是承认资源永远有限，在有限中寻找最优解本身就是发明
- 常见误区：把约束创新等同于"压榨团队"——约束是激发创造力的条件，不是削减成本的借口

### 模块3：与单线程领导的关系（上游衔接）

- 定义：两个披萨团队是单线程领导（Single-Threaded Leader, STL）的组织载体
- 输入：STL的专职授权
- 输出：一个100%专职+小规模+端到端的自治单元
- 关键动作：
  - STL的定义：一个领导者100%专职负责一件事，没有其他职责分散注意力
  - 两个披萨团队是STL的团队规模建议——STL负责方向，两个披萨团队负责执行
  - STL+两个披萨团队 = 完整的自治单元：方向专职（STL）+ 规模可控（两个披萨）+ 端到端拥有权
  - 没有STL的两个披萨团队容易陷入方向摇摆——小团队需要专职领导者保持聚焦
  - 没有两个披萨约束的STL可能带一个庞大团队——规模失控后STL也无力保持敏捷
  - 两者是互补关系：STL解决"专注"问题，两个披萨解决"规模"问题
- 常见误区：把两个披萨团队等同于STL——STL是角色（一个人），两个披萨是规模（一个团队），两者互补但不等同

### 模块4：与微服务架构的关系（下游催生）

- 定义：两个披萨团队的组织约束催生了AWS微服务架构的技术响应
- 输入：小团队独立部署、独立迭代的需求
- 输出：去中心化的微服务技术架构
- 关键动作：
  - 因果链：两个披萨团队 → 每个团队需要独立部署 → 单体架构无法支持 → 微服务架构成为必然
  - 这不是"先有微服务再配小团队"——是组织约束倒逼技术架构演进
  - Conway定律的实证：系统架构复制组织沟通结构——小团队→小服务，松耦合团队→松耦合架构
  - AWS本身是最大的微服务实践——每个AWS服务背后就是一个两个披萨团队
  - API作为团队间契约——团队内部怎么实现是自己的事，对外只暴露API，这与微服务的服务契约完全同构
  - 反面验证：如果用大团队+单体架构，任何小改动都需要跨团队协调，两个披萨团队的敏捷优势荡然无存
- 常见误区：把微服务当成两个披萨团队的"前提"——微服务是结果不是原因，是组织约束的技术响应

## 决策启发式

| 场景 | 判断规则 | 来源 |
|------|---------|------|
| 团队是否需要扩编 | 如果两个披萨喂不饱→拆分而非扩编 | 规模约束 |
| 团队拆分方向 | 如果功能边界清晰→按功能拆分；如果边界模糊→先理清边界再拆 | 自主性原则 |
| 资源不足时 | 如果人力不够→优先发明更好的方案，而非申请更多人 | 约束创新 |
| 团队间依赖 | 如果一个团队需要频繁等待另一个团队→接口设计有问题，考虑API化 | 微服务逻辑 |
| 是否需要STL | 如果团队方向经常摇摆→缺STL；如果STL管的人太多→违反两个披萨 | STL+两个披萨互补 |
| 跨团队协作 | 如果协作频率超过每周一次→考虑合并或重新划分边界 | 低沟通成本 |
| 新项目启动 | 如果初始团队超过10人→范围太大，缩小MVP范围 | 规模约束 |

## 适用场景

### 最适合

- 互联网/软件行业的产品开发——功能边界清晰、部署独立、迭代快速
- 需要快速试错和创新的环境——约束激发创造力
- 组织规模增长后出现沟通成本爆炸、决策变慢的症状
- 技术架构支持微服务/独立部署——组织约束与技术架构匹配
- 有明确的单线程领导机制——方向聚焦+规模可控

### 不适合

- 高度合规/安全要求的行业——某些场景需要多人交叉审核，小团队无法满足
- 需要大规模协作的基础设施项目——修桥、造车无法拆成6人团队
- 团队成员能力差异大——小团队容错率低，每个成员都必须是强个体
- 缺乏API/契约文化的组织——团队间依赖靠人际协调而非技术契约，拆小后反而更混乱
- 硬件开发等物理约束强的领域——迭代成本高，小团队快速试错的优势无法发挥

## 实施检查清单

- [ ] 每个团队是否都能被两个披萨喂饱（6-10人）？
- [ ] 团队是否端到端负责一个功能/产品，而非只负责一个环节？
- [ ] 团队间是否通过API/契约协作，而非通过会议和邮件？
- [ ] 是否有单线程领导100%专职负责团队方向？
- [ ] 团队规模超过10人时，是否拆分而非扩编？
- [ ] 资源不足时，团队是否优先发明更好的方案而非申请更多人？
- [ ] 技术架构是否支持团队独立部署（微服务/模块化）？
- [ ] 团队是否有足够的自主权做决策，还是事事需要上级审批？
- [ ] 跨团队依赖是否最小化——每周跨团队协作不超过一次？
- [ ] 是否定期审视团队规模——业务增长后团队是否在不知不觉中膨胀？

## 诚实边界

1. **规模崇拜的陷阱**：两个披萨团队不是越小越好——6人以下可能缺乏必要的能力覆盖，导致频繁跨团队依赖。约束催生创新的前提是团队内有足够的多样性来完成端到端交付。

2. **Amazon特有条件的不可复制性**：两个披萨团队能在Amazon奏效，与Amazon的高密度人才（Bar Raiser招聘）、微服务技术架构、API文化、以及飞轮效应带来的现金流支撑深度绑定。剥离这些条件谈两个披萨，容易沦为"把团队拆小"的表面模仿。

3. **与华为PDT的对比边界**：华为PDT 20-40人看似"太大"，但华为面对的是通信设备/企业级产品——硬件+软件+供应链+认证的复杂度远超纯软件产品。PDT的"重量级"是业务复杂度的函数，不是管理落后。两个披萨和PDT是不同业务域的最优解，不是谁优谁劣。

4. **微服务的代价**：两个披萨团队催生微服务架构，但微服务带来分布式系统的复杂性——服务间调用、数据一致性、监控告警、故障排查的成本不容忽视。组织收益（敏捷）和技术成本（复杂度）之间需要权衡。

5. **约束创新的适用范围**：约束催生创新在"0到1"阶段有效，但在"1到100"的规模化阶段，适度冗余（备份、冗余设计、灰度机制）是必要的。过度约束在规模化阶段可能导致脆弱性。

6. **邓巴数的简化**：邓巴数（150人）描述的是社交关系上限，两个披萨团队（6-10人）远低于此。用邓巴数论证两个披萨的规模合理性，逻辑链不够严密——邓巴数支持的是"组织不应超过150人需要重组"，而非"团队必须小于10人"。
