## 〇、结论先行

1. **HyperFrames 是真的，而且是最贴本题的那个**：HeyGen 开源的 HTML→MP4 引擎（Apache-2.0），composition 就是普通 HTML + `data-*` 时间属性 + GSAP 时间轴，渲染是 headless Chrome 逐帧 `beginFrame` 抓取后交给 FFmpeg 编码——**同一输入永远同一输出**。
2. **上游自带 7 个 skill，本仓装了 5 个**：`hyperframes`（工程契约）、`hyperframes-cli`（命令手册）、`hyperframes-registry`（组件目录）、`remotion-to-hyperframes`（**从 Remotion 迁过来**）、`slideshow`（deck）。没装 `media-use` / `figma`，理由见 §四。
3. **本机环境只差一样：Chrome Headless Shell**。Node 22.14、ffmpeg+ffprobe 9.0.2、32 核 / 64 GB 内存 / 819 GB 空闲**全部就绪**。装 Chrome 的命令：`npx.cmd hyperframes browser ensure`（约 150 MB）。
4. **MCP：现在没有给你我这种客户端直连的 HyperFrames MCP server**。官方设计是"CLI 就是 agent 接口"（flag 驱动、`--json` 输出、fail-fast）。存在的 MCP 只有三类：Studio 内的 **WebMCP**（W3C Origin Trial 阶段，规范未稳）、**Figma MCP**、以及**外部 CDP 挂载**。结论：本仓暂不接，优先用 CLI。详见 §五。
5. **对本仓最关键的一条判断**：HyperFrames 不是"再开一个视频工具"，而是**替换本仓 `tools/video/pipeline.py` 里的渲染层**（`render_slides` + `render_pipe`），把"HTML 出图 + Python 手写逐帧插值"换成"HTML + GSAP 时间轴 + 引擎逐帧"。稿子解析、Edge TTS、字幕、混音那半条链路可以留着。
6. 生态侧还有一批**不基于 HyperFrames** 的纯代码视频 skill 与提示词合集，见 §二末尾。

## 四、MCP：调研结论（本仓建议暂不接）

### 4.1 现状

| 形态 | 是什么 | 状态与限制 |
|---|---|---|
| **独立 MCP server** | 让 Claude/Kilo 直接调用 HyperFrames 工具的 MCP 服务器 | **不存在**。官方口径是"CLI 就是 agent 接口"：flag 驱动、纯文本输出、fail-fast、多数命令 `--json` |
| **WebMCP** | 浏览器原生 Model Context Protocol。Studio 往 `document.modelContext` 注册工具，让**浏览器页面内**的 agent 直接操作时间轴 | W3C 规范 **Origin Trial 阶段、未稳定**；上游代码注释明确指出 API 挂在 `document` 而非 `navigator`，且"拒绝不是可用的错误通道"；Studio 只注册自己用到的那部分（`packages/studio/src/webmcp/`） |
| **Figma MCP** | `hyperframes figma` 把 Figma 设计上下文转成动效上下文 | 需要 Figma 侧 MCP server；本仓无 Figma 资产 |
| **外部 CDP 挂载** | `preview` / `play` 可用 `--browser-path` / CDP 端点挂到外部 Chromium，接 Playwright / Puppeteer / browser-MCP | 上游明确：**HyperFrames 自身不做 CDP 自动化**，只暴露端点，"接什么、怎么接是使用者的事" |
| **外部视频模型 MCP** | 例：Runway MCP，让 Opus 当导演、模型出镜头 | 生态玩法（博客 H3 提到），不在本仓默认范围 |

### 4.2 建议

**暂不接 MCP**，优先级：

1. **CLI + `--json`**——HyperFrames 的命令全是 flag 驱动、带 JSON 输出、失败即非零退出，这本来就是给 agent 用的接口。再套一层 MCP 只会多一层 schema 维护，且丢掉了 `check --json` 的原始结构。
2. **外部 CDP + Playwright**——若要"自动审片"（自动抽帧、检查字幕是否压边、导出审片结论），用本机已有的浏览器自动化更直接；本仓已有 `webapp-testing` / `playwright-testing` skill 可复用。
3. **WebMCP**——等规范稳定再说，现在接入等于押注在 Origin Trial 的 API 形状上。

如果将来确实要接 MCP，最小可行形态是**只读**的（暴露 `timeline --json` / `check --json` / `snapshot` 三个只读能力），写操作仍走 CLI——这样 MCP 挂了也不会毁掉工程。

## 五、与本仓现有管线的关系

本仓 `tools/video/pipeline.py` 已经是一条完整的"HTML → 视频"管线：

```
讲解稿 md → parse_script → Edge TTS 逐句合成 → 词级字幕时间戳
  → 每场 HTML 1920×1080 无头 Edge 截图 → numpy 配乐 → 按语音能量闪避混音
  → plan_timeline（音频实测定时） → render_pipe（逐帧几何插值 + 编码）
  → libass 烧字幕 → verify_video（时长/命中/抖动） → check_subs（三轴对齐）
```

与 HyperFrames 的重合与差异：

| 维度 | 本仓现有管线 | HyperFrames |
|---|---|---|
| 画面源码 | HTML（每场一页） | HTML（一个 composition + 子 composition） |
| 时间轴 | Python 手写：实测音频时长 → 逐帧几何插值 | **数据**：`data-start` / `data-duration` / `data-track-index`，GSAP 负责编排 |
| 渲染 | Edge 截图 PNG → ffmpeg | headless Chrome `beginFrame` 逐帧 → ffmpeg |
| 确定性 | 时长靠音频实测兜底 | 帧 = `floor(time × fps)`，无 wall-clock 依赖，**同输入同输出** |
| 自检 | `verify_video` + `check_subs`（本仓自研） | `check --json`（lint/runtime/layout/contrast）+ `snapshot` 审帧 |
| 字幕 | libass 烧制 | `captions` track（词级对齐） |
| 组件复用 | 无目录 | registry 50+ block |

**判断**：HyperFrames 的增量价值集中在**动效编排精度**、**组件复用**、**内置 lint/审帧**三件事；本仓已经做好的 TTS、字幕、混音、验收逻辑不必推倒。迁移的正确切法是**换渲染层、留内容层**，而不是整体换栈。

## 六、[判断与建议]

以下是判断，不是已核实事实：

1. **先别动现有 6 支讲解视频**。它们已跑通、有验收证据。换栈的收益要到"要做出带真实动效的新片"时才兑现，而那时再切代价更低。**先拿 day1024 的新内容做试点**。
2. **不要为了"环境齐全"去装 Kokoro/MusicGen/whisper.cpp**。那是本地兜底能力，本仓已有 Edge TTS + numpy 配乐；装 torch/transformers 是纯成本。**只装 Chrome**。
3. **`remotion-to-hyperframes` 是本仓最值钱的那一个 skill**——不是"要不要换栈"，而是"万一要换，怎么迁、迁完怎么证明没跑偏"。它自带 4 档测试语料和 SSIM 逐帧比对脚本，比任何口头论证都硬。建议**先拿仓库里没有的 Remotion 样例做一次迁移演练**，把踩到的坑记下来再决策。
4. **审片用"多 agent 各盯一类问题"的分工，比让一个 agent 自己审更有效**。博客那套（节奏/质感/合规各一个审片 agent）正好对上本仓的红线——**"像 demo 的地方"**、**"文字与安全区"**、**"素材与事实合规"**。本仓的视频要讲企业方案，"像 demo"和"合规"正是评审会挑的刺。
5. **别装两个叫 `hyperframes` 的 skill**。nexu-io 那版与 HeyGen 版同名且契约不同（前者 daemon 耦合、后者 CLI 契约），装在一起必然踩坑。需要它的创作手艺时，**只取参考文件**（typography / transitions / motion-principles / house-style），不装它的 SKILL.md。
6. **遥测这件事应该跟用户说清楚**：默认开、只收匿名用量、可一键关。涉及企业内容时，团队会想知道"东西有没有被传出去"——官方声明是"文件路径与 composition 内容从不采集"，但**信不信要靠人去读代码**（`packages/cli/src/telemetry/`）。
